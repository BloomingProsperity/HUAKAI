# 分阶段交付说明

这个项目确实很大，不能一口气做完。正确方式不是砍功能，而是分阶段交付。

核心原则：

- Sub2API、New API、All API Hub 这些项目是功能地图，不是第一版任务清单。
- 完整功能都要保留。
- 第一版只做最小闭环。
- 暂时不做的功能必须进入路线图、功能开关、插件、实验模块或安全等价方案。

## 功能等级

- L0：知道有这个功能，但还没开始。
- L1：MVP，最小可用版本。
- L2：生产可用版本。
- L3：参考项目功能对齐。
- L4：比参考项目更好。

## 第一版最小闭环

第一版只需要打通这条链路：

1. 用户拿本系统的 API Key 请求。
2. 系统接收 OpenAI-compatible 请求。
3. 系统校验 key。
4. 系统选择一个 provider account。
5. 系统转发请求给上游模型。
6. 上游返回结果。
7. 系统返回结果给用户。
8. 系统记录请求状态、模型、provider account 和用量估算。

这就是最小 MVP。

## 分阶段路线

Phase 0：治理基础  
已经完成规则、clean-room、agent 分工、中文说明。

Phase 1：参考证据和功能地图  
把 Sub2API、New API、All API Hub 的功能拆成 clean-room 证据和功能矩阵。

Phase 2：MVP 范围锁定  
确定第一版到底做什么、不做什么、怎么验收。

Phase 3：项目骨架和测试框架  
选技术栈、建骨架、建测试，但需要 Owner 确认运行时依赖。

Phase 4：Gateway Core MVP  
做最小 OpenAI-compatible 请求转发。

Phase 5：Provider Account Hub + Routing Lite  
做 provider key 管理、启用禁用、基础路由。

Phase 6：Usage + Quota Lite  
记录用量，做简单额度限制，不急着做完整计费。

Phase 7：Admin Lite  
做最小后台或管理 API，能查 key、provider、route、usage、log。

Phase 8：生产强化  
补健康检查、失败切换、审计、安全、告警。

Phase 9：高级功能对齐  
补齐复杂计费、插件、完整后台、智能路由等高级功能。

## 最重要的判断

不是“不做完整功能”，而是“不在第一版一次性做完整功能”。

完整功能全部保留，按 L1 到 L4 慢慢完成。
