# AI 协作流程说明

三个 AI 的职责分工：

- Claude：项目经理、总架构、功能不缩水负责人。
- Gemini：前端 UI 和运营后台负责人。
- Codex：生产审查、场景测试、功能不缩水审计、小范围安全修补。

标准流程：

1. Claude 收集参考证据并更新文档。
2. Claude 定义能力和验收标准。
3. Gemini 做后台 UI 和运营工作流。
4. Codex 做功能对齐、风险、clean-room 和测试审查。
5. Claude 统一做发布决策。

Codex 默认不要承担大型功能主实现，除非你明确指派。

# Owner 确认开始后，AI 可以主动推进

这个项目现在采用 Owner Start Gate + Agent Proactive Execution 模式。

意思是：AI 不需要每一步都问你。只要你明确说某个阶段、任务或模块可以开始，例如“开始”“确认开始”“可以开始写”“Proceed”“Start Phase 1”，AI 就应该在规则范围内主动推进。

不需要额外脚本也可以实现这种自动化。自动化主要靠两件事：

- 规则文件明确授权。
- Owner Start Gate 明确判断什么时候可以开始。

你说“开始”后，Claude PM 可以主动做计划、更新文档、分配 Claude / Codex / Gemini 的工作、更新风险登记、整理任务板和准备合并建议。Claude 不能跳过 clean-room、发布门禁，也不能自己批准自己的实现。

主动执行规则（Proactive Execution Rule）：Owner 确认后，AI 应该读取相关规则、理解目标、安全时执行到完成、做合理工程判断、记录假设、记录风险、更新必要文档、尽量运行可用检查，最后给 Owner 中文总结。

Codex 不要被限制得太死。Owner 确认开始后，Codex 应该从真实生产使用角度做审查、写场景测试、发现阻塞点、做小范围安全修补，并在规则冲突时提出可执行的安全替代方案。

Gemini 可以主动做前端和运营后台，包括页面、组件、样式、UI 文档、mock UI 数据、API 假设文档。但 Gemini 不能碰后端核心，尤其不能改供应商路由、配额、计费、认证、数据库 schema、LICENSE 或真实密钥。

风险分级确认规则（Risk-Based Confirmation Rule）：

- 低风险：直接做，不需要再次问你，例如文档、测试、提示词、类型修复、UI 文案、小重构、非敏感配置示例。
- 中风险：需要就做，但要记录原因和风险，例如小实现改动、新 helper、UI 结构变化、非破坏性 API 合同更新、mock 数据、实验逻辑。
- 高风险：必须停下来问你，例如删除文件、改 LICENSE、改数据库 schema、改认证核心、改计费账本、改配额执行、加运行时依赖、碰真实密钥、破坏性命令、生产部署。

功能保留规则（Feature Preservation Rule）：功能不能因为风险被删除。许可证风险和安全风险只能改变实现方式。可选方式包括安全等价、插件、功能开关、人工优先、实验模块、强制路线图。

每次任务完成后，AI 必须用中文总结：做了什么、改了哪些文件、为什么这样做、有没有功能缩水、有没有 clean-room 风险、有没有安全风险、哪些地方需要你确认、下一步建议。
