## 0. 定位与阅读方法

### 0.1 本手册解决什么问题

白皮书回答“HUAKAI 是什么、服务谁、总体怎样联动”；本手册回答“主线具体怎样运行、为什么这样
运行、失败后会怎样”。它记录：

- 进程、模块和数据域的责任边界；
- 每条核心业务链的调用顺序；
- 选号、路由、限流、计费、健康、恢复等核心算法；
- 事务、锁、幂等键和多副本租约；
- 成功、拒绝、重试、回退、部分成功和人工恢复语义；
- 修改某个模块时必须同时检查的影响范围。

它不记录某次测试输出、某个 PR 的改动清单或某次会话进度。这些属于 CI、Issue、PR、commit
和 Release。

### 0.3 状态词

本手册只使用以下状态：

- **存在**：源码或 schema 存在。
- **已接线**：组合根注入并由生产路由、worker 或热路径调用。
- **有测试合同**：仓库有能够区分正确与错误行为的测试源码；不等于本次已运行。
- **已验证**：当前提交有实际运行结果。
- **目标合同**：Owner 已确定，但当前代码可能仍未完全落实。
- **缺口**：当前主线与目标合同、完整链路或生产要求存在差异。

### 0.4 工程工作项与交接

本项目不把 AI 会话记录、临时进度和操作流水写进设计手册。工程事实按以下链路保存：

```text
一个 GitHub Issue
  -> 一个最新主线功能分支
  -> 一个 PR
  -> 小提交与 CI 证据
  -> Owner 批准
  -> 主线验证
  -> Issue 关闭
```

Issue 是当前计划与状态源，PR 是实现和验证源，白皮书是合并后的现行决策源。多人或多个 AI
不能同时修改同一目标；不永久指定模型分工，由 Owner 当前指定写入负责人。

发生交接时不得新建 Markdown 交接稿。原负责人在 Issue 或 PR 记录分支、最后可信 SHA、已完成、
未完成、验证、阻塞、工作树状态和外部副作用；接手者从远端重新核实主线、分支、diff 和测试，
再继续实施。共用一个 GitHub 账号时，执行会话与独立复核会话必须在 PR 明示，不能把同账号评论
当成平台可证明的人工批准。

## 1. 进程与组合根

### 1.1 生产进程

当前生产主进程是 Go Gateway。`backend/cmd/gateway/main.go:26-82` 依次完成：

1. 建立结构化日志；
2. 把 `slog` 接入统一日志门面；
3. 校验 release mode 和开发令牌回显开关；
4. 读取配置；
5. 建立进程级取消上下文；
6. 调用 `buildGatewayRuntime` 装配依赖；
7. 挂载路由；
8. 启动 HTTP 服务；
9. 收到终止信号后按生命周期停止。

`backend/cmd/gateway/wiring.go` 是当前最主要的组合根。它只应做依赖构造、注入和生命周期接线，
不应承载新的领域算法。当前文件体量很大，修改时必须检查：

- 构造是否真实成功；
- 依赖是否写入 `deps`；
- 路由是否挂载；
- worker 是否加入启动和停止序列；
- readiness 是否覆盖关键依赖；
- 多副本任务是否有数据库租约；
- nil 或配置缺失时是拒绝启动、端点 503 还是明确降级。

### 1.2 启动门

启动门采用“不能证明安全就拒绝启动”的原则。当前关键门包括：

- release mode 必须显式有效；
- 生产环境禁止开发令牌回显；
- 数据库连接和迁移版本可用；
- 凭据加密密钥能够解开现有活跃凭据；
- Rust Sidecar 的 IPC 版本、能力和内置 profile 完整；
- 关键签名、会话和配置材料有效。

Sidecar 当前是全局启动与 readiness 依赖：

- `backend/cmd/gateway/wiring.go:949-959` 在启动时和 `/readyz` 中调用
  `mimicry.ProbeSidecarReadiness`；
- `backend/internal/transport/mimicry/profile_catalog.go:114-128` 要求完整能力和全部内置 profile；
- 因此即使某个请求走标准 TLS，Sidecar 故障仍会阻止 Gateway 就绪。

这属于**当前实现事实**。Owner 已确定的目标边界是 Rust 只服务确实需要客户端形态的账号转 API
能力；当前 CRS 传输复用和全局 readiness 是否继续保留，属于后续代码收口项，本轮文档不替代码
做结论。

### 1.3 停机与排空

进程关闭必须先停止接收新工作，再等待在途 HTTP 和后台任务结束，最后关闭数据库和 Redis。
设计目的：

- 防止请求已经交付给用户但结算 worker 先被切断；
- 防止凭据刷新或账号状态更新在事务中途失去连接；
- 防止 DLQ/outbox 尚未落库就结束进程；
- 防止多个 worker 在关闭期间重新获取租约。

任何新增 worker 都必须同时提供：

1. `Start` 或等价启动入口；
2. 接收父级 `context`；
3. 有界单轮执行；
4. 明确停止等待；
5. 多副本所有权；
6. 可观察的成功、失败和最后运行时间。

## 2. 身份、租户与授权

### 2.1 三类业务身份

业务上只有：

1. 部署者：代码主要角色 `platform_admin`；
2. 下级租户管理员：代码主要角色 `tenant_operator`，绑定 `ScopeTenantID`；
3. 最终用户：绑定唯一 `tenant_id` 和 `user_id`。

技术凭据可以是用户会话、用户 Key、管理员 token、管理员会话、Hermes 内部令牌等，但它们只能
投影到上述三类业务身份，不能形成第四种经营角色。

### 2.2 入站用户 Key

用户 Key 的基本链路是：

```text
Authorization
  -> 提取 bearer
  -> 哈希查找，不以明文查库
  -> 检查吊销、过期和环境
  -> 恢复 tenant_id / user_id / key_id
  -> 加载 Key 级模型、IP、额度和分组约束
  -> 写入请求上下文
```

核心入口在 `backend/internal/auth/api_key_resolver.go`，用户自助 Key 管理在
`backend/internal/userkey` 与 `backend/internal/userkeyhttp`。Key 只代表下游身份和权限，
不保存上游账号凭据。

影响半径：

- 租户隔离；
- 模型可见性；
- 池组选择；
- IP 白黑名单；
- 速率和预算；
- 用量归属；
- 账单、回执和争议归属。

### 2.3 用户会话

用户会话用于注册、登录、个人资料、Key 管理、用量、订单、订阅、兑换和争议。会话 token 的
服务端事实必须支持：

- 哈希存储；
- 过期和吊销；
- 刷新与重放防护；
- 设备或安全策略；
- 用户和租户归属；
- 删除或安全事件后的会话失效。

HTTP 入口集中挂在 `backend/cmd/gateway/routes.go` 的 `/v1/auth`、`/v1/sessions` 和 `/v1/me`
路由，领域实现位于 `userauth`、`usersession`、`passkey`、`twofa` 等包。

### 2.4 管理身份

`backend/internal/admin/operator_auth.go:140-158` 的通用
`CanIssueForTenant` 当前允许：

- `platform_admin` 指定任意租户；
- `tenant_operator` 只能指定自己的 `ScopeTenantID`。

该方法只用于系统资源和平台监督读取，例如上游账号、模型、池组、路由和租户经营状态；部署者
本来就负责这些全局资源。它不能用于会修改下级租户最终用户资料、会话、Key、余额、订单、
订阅、兑换、争议或通知的写动作。

最终用户域统一使用 `CanOperateOwnedTenant` /
`CanManageFinalUsersForTenant`：

- `platform_admin` 只可写平台工作租户的最终用户资源；
- `tenant_operator` 只可写自己的 `ScopeTenantID`；
- 平台给下级租户增减的是租户经营钱包，不能越级改该租户最终用户余额；
- 平台可以按租户读取订单、兑换、订阅和争议用于监督、对账与日志，但读取能力不能被复用成写权限。

当前用户管理、用户 Key、余额、支付、订阅、兑换、争议处理、用户通知、社交身份安全变更和人工
恢复入口均复用上述严格写边界。账号、模型、池组等系统资源继续使用通用租户能力和 capability
合同，这不是第四种身份，也不能旁路到最终用户数据。

后续鉴权变更仍必须横向检查用户、Key、争议、订单、退款、日志、账号、池组和 Hermes，不能只修
一个 handler；新增最终用户写口若使用 `CanIssueForTenant` 或仅凭请求体 `tenant_id`，应直接阻断
review。

### 2.5 fail-closed 原则

以下情况必须拒绝，不能为了可用性回退到更宽权限：

- 无法解析租户；
- 管理角色与 scope 不匹配；
- 平台工作租户未配置；
- capability 查询失败；
- 分组路由配置读取失败且可能造成越级用池；
- Hermes 内部令牌、真实管理员或租户主体无法同时验证；
- 目标对象不属于请求租户。

## 3. 用户、注册与 Key 生命周期

### 3.1 注册与登录

公开注册、密码登录、社交登录和补邮箱流程必须复用同一组输入规范：

- 邮箱规范化；
- 密码强度和长度；
- 显示名称限制；
- 邀请、验证码和 CAPTCHA 政策；
- 注册限流；
- 用户创建、社交身份绑定和日志的事务边界。

注册限流位于顶层入站限流体系，不应因 handler 内没有限流代码就误报为缺失。判断入口防护必须
从路由最外层中间件一直读到 handler。

### 3.2 Key 创建

最终用户通过 `/v1/api-keys` 管理自己的 Key；管理员入口另有管理 API。Key 创建必须：

1. 从认证身份得出租户和用户，不能信任用户请求体覆盖；
2. 验证名称、过期时间和策略；
3. 只在创建成功响应中展示一次明文；
4. 数据库存哈希；
5. 为后续用量、模型和 IP 策略建立稳定 `key_id`；
6. 写分类明确的日志。

管理员入口额外涉及三身份越级边界，不能简单复用“平台管理员可操作任意租户”的旧通用判断。

## 4. 上游账号接入与凭据生命周期

### 4.1 统一目标

所有账号导入方式最终必须进入同一条主链：

```text
输入来源
  -> 解析与规范化
  -> 上游身份提取
  -> 同租户身份消歧
  -> 创建 / 更新 / 跳过 / 冲突 / 失败计划
  -> 计划哈希和人工确认
  -> 单账号事务
  -> 账号 + 凭据版本 + 日志 + 订阅投影
  -> 提交后触发配额/模型/健康采集
```

主服务是 `backend/internal/gatewayhttp/accountintake`，HTTP 入口位于
`backend/internal/gatewayhttp/accountintakehttp`，输入解析与模式合同位于 `credentialacq`。

### 4.2 导入来源

当前统一入口覆盖的来源包括：

- API Key、JSON、CSV 和 CLI 文件；
- Codex 批量与 Agent Identity；
- Claude Setup Token；
- Claude Cookie；
- OAuth 授权码、设备码和 token 交换；
- CRS；
- 加密账号迁移包。

厂商协议存在不等于导入方式已开放。是否发布以 `credentialacq` 的模式计划、HTTP handler、
上游交换器和执行链同时存在为准。

### 4.3 计划阶段

`backend/internal/gatewayhttp/accountintake/service.go:94-164` 的计划阶段执行：

1. 规范化输入；
2. 为 Codex 账号补默认值并解析车道；
3. 严格校验账号和调度参数；
4. 查询 provider 协议族；
5. 读取本租户现有上游身份库存；
6. 解析凭据候选；
7. 计算同渠道风险；
8. 检查更新是否与现有 provider 协议兼容；
9. 生成动作和风险提示；
10. 对输入和计划计算稳定哈希。

计划阶段不能写账号、凭据或上游副作用。它的产物是“如果现在执行会发生什么”，不是执行结果。

### 4.4 身份消歧

上游身份匹配只能在同一租户内进行。可用证据按模式包括上游账号 ID、subject、邮箱和凭据指纹。
判断规则：

- 明确命中一条可兼容账号：计划更新；
- 没有命中：计划创建；
- 同一上游身份命中多条账号：显式冲突，要求人工消歧；
- 身份证据互相矛盾：显式冲突；
- 协议族或凭据模式不兼容：失败，不得把旧账号改成另一种协议；
- 仅弱证据不能静默覆盖强身份。

该规则的目的不是“尽量自动合并”，而是避免把一份新凭据写到错误账号。批量导入可以部分成功，
但每个冲突项必须单独可见。

### 4.5 执行阶段

`backend/internal/gatewayhttp/accountintake/execute.go:27-111` 的执行阶段：

1. 校验计划哈希格式；
2. 重新生成当前计划；
3. 常量时间比较计划哈希，计划漂移则拒绝；
4. 检查每项所需明确确认；
5. 必要时刷新即将过期的导入凭据；
6. 补齐项目和订阅档案；
7. 逐项执行创建或更新；
8. 每项返回 created、updated、skipped、conflict 或 failed；
9. 事务提交后异步通知配额等采集器。

批量不是一个跨账号大事务。设计原因是单个坏账号不应回滚已确认的其他账号；代价是调用方必须
正确展示部分成功，并能只重试失败项。

### 4.6 凭据事务与加密

`backend/internal/credentialstore/postgres_store.go:212-292` 提供事务包装：

- 业务变更和凭据日志在同一事务中；
- 失败路径使用独立、有限时长的回滚上下文；
- 已在外层事务时复用外层事务，避免嵌套事务造成假原子性。

凭据写入前必须：

- 规范化 vendor 和 auth mode；
- 由模式 handler 校验 payload；
- 验证账号属于当前租户；
- 使用版本号、AAD 和密钥 ID 加密；
- 保存可查询但不敏感的上游身份元数据；
- 对明文 payload 及时清零。

更新凭据使用期望版本控制，防止两个刷新或导入并发互相覆盖。

### 4.7 订阅与系统标签

OAuth/Session 账号可从可信上游响应、项目元数据或刷新结果形成订阅观测。投影至少区分：

- 原始套餐；
- 规范套餐；
- 来源；
- 可信度；
- 校验状态；
- 作用域或工作区；
- 观测时间。

系统标签由观测生成，例如厂商与套餐标签；人工标签不能伪造系统标签。官方 API Key 没有个人
订阅等级，应该显示“不适用”，不能伪造成免费或未知订阅。

当前订阅投影不等于订阅到期日。凭据 `expires_at` 是访问凭据失效时间，不能冒充套餐到期时间。

### 4.8 凭据刷新

凭据刷新链必须具备：

- 按账号租约避免同一账号并发刷新；
- 刷新风暴预算；
- `refresh_before_at` 和退避；
- 成功时原子轮换版本和日志；
- 失败分类、下次尝试时间和健康回流；
- 终态撤销保护；
- 上游副作用成功但本地提交不确定时禁止无脑重复。

## 5. 模型目录、分组和账号池

### 5.1 模型解析

请求中的模型名不是直接上游地址。模型解析需要：

1. 确定租户；
2. 读取租户目录版本和继承策略；
3. 解析规范模型、别名和能力；
4. 应用 Key 级模型限制；
5. 解析模型路由 override；
6. 形成后续池组 binding 所需的稳定模型身份。

领域实现位于 `registry`、`routingmodel`、`modelroutingadminhttp`、`modeladminhttp` 等包。
解析失败必须返回明确的未知模型、不可见模型或配置错误，不能退回到任意默认模型。

### 5.2 分组与池组

用户或 Key 不能直接绑定上游账号。运行时关系是：

```text
租户 / 用户组 / Key / 规范模型
  -> 路由策略
  -> 池组 binding
  -> 池内账号候选
```

控制面写入的模型、路由、分组和 binding 必须被热路径实际读取。只有表、CRUD 或按钮但没有
运行消费者，视为空心能力。

### 5.3 选号 gate

候选账号进入评分前至少经过：

- 租户和池组归属；
- 启用和手工暂停；
- 账号模型允许列表；
- 模型注册表中的模型/协议能力；
- 凭据可用性；
- 账号健康和冷却；
- RPM/TPM 预检；
- 额度和窗口成本；
- 上下文窗口；
- 最大会话；
- 并发 slot；
- 临时不可调度规则。

任何 gate 的失败都应保留稳定原因码，供日志、Hermes 和运营界面解释“为什么这个账号没被选中”。

chat 的 stream、tools、vision、JSON 和 audio-input 是模型/协议属性，不进入账号级
`capability_flags` gate。账号能力是多模型并集，把这些 chat 特性当账号门既会误过滤默认空标记账号，
也会在同一账号的其他模型上形成跨模型误授权。图片、embeddings、rerank、countTokens、音频和视频
同样是模型属性：各入口统一调用 `internal/modality.Supports` 检查请求模型的注册表能力，能力为空或未知
时 fail-closed；媒体选号还要求账号 `model_allow_list` 明确包含请求模型。账号级 gate 只保留池归属、
凭据、健康、冷却、额度、上下文、会话和并发等真实账号事实。

### 5.4 评分与选择

当前选号实现分布在 `backend/internal/pool/router`：

- 静态权重提供基础偏好；
- 健康、错误率、延迟、额度余量和并发余量调整动态分；
- locality 和前缀段用于提高缓存命中与会话稳定；
- HRW 等稳定映射减少候选集合轻微变化造成的大面积会话迁移；
- aging 防止长期低分账号永久饥饿；
- PASR、shadow、canary 等模式由运行配置选择。

评分只能在已通过硬 gate 的候选之间比较。不能用“高分”覆盖租户、凭据、额度或能力禁用。

PASR 当前主评分可写成：

```text
基础分 = 缓存局部性 + 0.3 × (1 - LoadRate) - 降级惩罚
总分 = 基础分 + 自适应贡献
```

- 命中缓存的局部性为 `1.0`；
- 降级惩罚为 `2.0`；
- 自适应容量余量最高 `0.30`；
- 15 分钟内有样本时，可靠性最高 `0.35`、响应速度最高 `0.10`；
- 2 小时内已知且可用的上游额度贡献最高 `0.20`；
- 上游成本倍率按 `-0.025 × log2(ratio)` 计算，并限制在 `[-0.05, 0.05]`；
- 低额度且一小时内即将重置时，恢复贡献最高 `0.05`。

贡献值来自 `adaptive_score.go`，超过新鲜度窗口的信号不参与评分。总分相同时，优先选择最久未用
账号。该公式只描述当前 PASR 路径，不能冒充所有 selector 的统一公式。

会话前缀段使用 HRW 稳定映射：

```text
mixed_account = splitmix64(account_id)
score = uint64(SHA256(seed || prefix_hash || mixed_account)[0:8])
```

每个前缀取分数最高的三个账号。账号集合轻微变化时，HRW 减少大面积重映射；段内无可用账号时
才回到全 ring 排序。HRW 只负责稳定候选关系，仍必须重新经过租户、适用的账号级能力、健康、额度
和 slot gate。

### 5.5 并发 slot 与排队

slot 是真实并发占用，不是统计数字：

1. 选号前预检容量；
2. 选中后原子获取；
3. 获取失败时换候选或进入有界排队；
4. 请求结束、失败或取消时释放；
5. 进程崩溃后由租约或恢复任务处理孤儿占用。

排队必须有最大等待、最大队列和取消传播，不能让请求无限挂起。当前模块目录显示 queue wait 在
chat 与其他协议的接线并不完全一致，因此不能把 chat 的排队能力自动宣称为所有入口共有。

### 5.6 重试与回退

一次请求的 retry 不是简单重发。执行顺序必须区分：

- 同账号可安全重试；
- 同池换账号；
- 按 binding 进入后备池；
- 按模型策略进入替代模型；
- 客户端错误、权限错误和不可重放请求不重试；
- 流已经交付给客户端后不得透明重放整次请求；
- 每次尝试受请求级 retry budget 限制。

每次 attempt 必须保留账号、池、模型、错误类、耗时和是否交付的证据。

## 6. 协议、能力与出站

### 6.1 协议入口

生产路由已挂载：

- OpenAI Chat Completions、Completions、Embeddings、Rerank；
- Images generations/edits/variations；
- Audio speech/transcriptions/translations；
- Responses 与 compact；
- Anthropic Messages 与 count tokens；
- Gemini `v1beta`；
- Video 和异步媒体任务；
- 模型目录、用量、回执等控制入口。

路由存在只证明入口可达。每个入口仍需分别证明身份、模型、池、账号、凭据、出站、计费、健康
和恢复完整经过主链。

### 6.2 规范中间形态

多协议应尽量先变成内部稳定请求和响应合同，再由 provider adapter 生成上游形态。核心原则：

- 不在 handler 中直接拼厂商请求；
- tool、thinking、system、metadata、图片、音频等能力必须显式标注可无损、可降级或不支持；
- lossy 转换不得静默；
- 流式和非流式必须共享错误、用量和终止语义；
- 上游真实模型与对外模型要分别记录。

### 6.3 出站模式矩阵

`backend/internal/gateway/upstream_dispatcher.go:156-190` 当前按 provider 和账号模式选择：

- 官方 API Key 和普通兼容上游：标准 Go TLS；
- 需要 HTTP/1.1 但不需要仿真：标准 TLS + 独立 H1 连接池；
- Claude/Codex/Gemini Advanced 等指定会话模式：Rust mimicry；
- Antigravity 推理：标准 TLS + H1，模型发现等控制请求走标准协商；
- Cursor、Copilot、Kiro、Windsurf 的仿真模式仍受各自发布状态约束。

`backend/internal/transport/factory.go:148-180` 先验证 provider/mode 组合，再选择 transport。mimicry
模式缺 Socket、profile 或能力时拒绝，不能静默回到标准 TLS。

### 6.4 代理与 SSRF

账号代理必须由账号或租户的代理解析器显式绑定。标准 `http.Transport` 禁止读取环境变量中的
全局代理，防止未绑定账号被部署环境偷偷改道。

管理员可配置上游地址必须执行：

- scheme 和 host 校验；
- DNS 解析；
- 禁止不允许的目标；
- 解析结果与真实拨号绑定，阻止 DNS rebinding；
- 代理和直连策略明确；
- 错误信息不泄漏凭据。

显式代理失败默认不应静默直连，否则会改变账号出口 IP。

### 6.5 Rust Sidecar

Sidecar 使用 Unix Socket 接收版本化控制帧，完成 TLS 后把连接流交还 Go HTTP 栈。
`backend/internal/transport/mimicry/sidecar_client.go:175-260` 的关键约束：

- profile ID 与 inline profile 必须二选一；
- 目标、端口、固定 IP 和代理有严格上限；
- 上下文取消会中断 ACK 等待；
- ACK 协议版本和未知字段严格校验；
- 失败不回退进程内 TLS；
- 每次拨号记录阶段和关联 ID。

Sidecar 是网络能力，不负责租户、模型、余额或账号选择；这些决定必须在 Go 侧完成。

## 7. 一次同步或流式调用

### 7.1 主顺序

```text
边缘接入
 -> 请求 ID / 来源 IP / 体积 / 解压 / 安全头
 -> 用户 Key 身份
 -> 模型和能力
 -> 路由与池组
 -> claim / 额度预留
 -> 候选账号 gate 和选号
 -> slot
 -> 凭据、代理、协议和 transport
 -> 上游 attempt
 -> 流式或非流式交付
 -> 用量归一
 -> 结算、回执、健康和日志
 -> 异步副作用失败进入恢复
```

### 7.2 交付边界

资金与重试必须知道响应是否已经交付：

- 上游建立连接前失败：通常可换账号；
- 收到上游状态但未向客户端写 body：按错误类决定；
- 已向客户端写入流式 token：不能透明重放整次请求；
- 客户端断开：取消上游，按已交付量和上游已产生用量结算；
- 上游流缺少正常终止：记录明确的流结束类型，不能伪装成功。

### 7.3 用量

用量来源按可信度区分：

1. 上游明确返回的 usage；
2. 协议流结束事件；
3. 本地 tokenizer；
4. 估算。

结算和回执必须保存来源及是否估算。估算值不能冒充上游精确值；后续得到真实用量时必须走可追踪
重定价或补偿。

## 8. 异步媒体任务

图片、音频、视频和其他媒体能力不应被塞进 chat 协议。同步生成可走对应能力入口；长任务采用：

```text
提交
 -> 身份、模型和能力
 -> claim / hold
 -> 选择账号和上游任务
 -> 保存任务与租约
 -> 轮询或接收回调
 -> 保存进度和结果
 -> 结算或退款
 -> 过期、孤儿和人工恢复
```

任务状态必须区分已受理、上游处理中、成功、失败、取消、过期和恢复中。轮询端点只读取本租户、
本用户任务。任务创建和资金预留要么同事务，要么有持久化恢复意图。

当前 Grok 视频提交在 POST 出站报错时只能标记 `provider_submit_outcome_unknown`。如果上游实际已经
创建任务但响应在返回前丢失，本地没有上游任务 ID，不能自动证明“可重试”或“已创建”；这类窗口
必须进入未知副作用恢复，而不能直接重复提交。

## 9. 额度、资金与结算

### 9.1 三层余额

资金层级目标合同：

- 平台可给下级租户钱包增减；
- 平台可管理平台自有用户余额；
- 下级租户管理员只能在本租户钱包与本租户用户间划转；
- 平台不得越级修改下级租户最终用户余额。

`backend/internal/balanceledger/service.go:375-411` 对四类操作做显式分类，非法角色、scope、目标
组合直接拒绝。

当前存在两套容易混淆的余额口径：

- `user_balances` 是实际用户钱包，包含管理员下发、兑换码、支付入账和其他业务来源；
- `/v1/payments/balance` 只计算 `payment_credits - payment_refunds`，表示支付充值来源净额。

后者当前仍使用通用字段名 `balance`，不能把它展示成用户总可用钱包。

### 9.2 管理员余额调整算法

`backend/internal/balanceledger/service.go:134-310` 使用：

1. 输入规范化和金额边界；
2. 角色与目标分类；
3. 请求指纹；
4. Serializable 事务；
5. 基于租户、操作者和幂等键的事务级 advisory lock；
6. 幂等重放读取；
7. 锁租户和钱包/用户余额行；
8. 双边账本分录；
9. 提交；
10. serialization、deadlock 和唯一冲突的有界重试。

同一幂等键但请求指纹不同必须冲突，不能把旧结果返回给不同金额或目标。

### 9.3 在线调用资金状态

在线调用分为：

- **Tx1 / claim**：请求交付前，验证政策并预留可消费额度；
- **上游执行**：产生尝试、交付和 usage；
- **Tx2 / settle**：按最终可计费事实结算、释放预留、写用量和回执；
- **补偿**：未交付、少交付、重复或结算失败时退款、补扣或恢复。

claim、settle、refund 和 recovery 必须共享稳定请求 ID、租户、用户、Key、模型和金额事实。

### 9.4 退款与累计补偿

退款不是直接给余额加钱。它必须基于原始已结算事实计算：

- 可退上限；
- 已退款累计；
- 本次退款；
- 原始租户、用户和币种；
- 幂等键；
- 原因和操作者；
- 对应账本分录。

部分退款多次执行时，累计值不能超过原始可退金额。并发退款必须通过行锁、唯一约束或等价串行化
保证不会双退。

当前内置 manual、淘宝/闲鱼跳转、HMAC 和 test provider 的 `Refund` 都返回不支持。现有退款会
冲正 HUAKAI 内部钱包，但不会向外部支付渠道发起原路退款；界面、日志和状态不得把“内部钱包已冲正”
描述成“外部渠道已退款”。

### 9.5 永久事实与普通日志

以下是永久业务事实，不受 30 天日志清理影响：

- 钱包和用户余额；
- 账本交易与分录；
- claim、settlement intent 和幂等结果；
- 订单、退款和争议金额；
- 用量与成本回执；
- DLQ 中尚未完成的资金恢复事实。

### 9.6 人工重定价

当前 `RepriceService` 会使用 Serializable 事务锁定用量记录，计算权威成本和差额，并插入
`usage_record_reconciliation_events`。它不会同步改写：

- `user_balances`；
- `billing_events`；
- 钱包 hold；
- quota reservation 或 quota window。

因此它是**成本差异核算记录**，不是完整财务冲正。后续若要自动补扣或退款，必须另建受三身份边界、
幂等、余额锁、账本分录、配额逆转和人工确认保护的动作，不能仅把 reprice 的状态改名。

## 10. 健康、限流、重试与恢复

### 10.1 健康信号来源

账号健康不能只靠主动探测。信号来源包括：

- 真实请求成功与错误；
- 凭据刷新；
- 配额采集；
- 主动探测；
- 管理员手工状态；
- 上游限流和余额耗尽 reset 时间；
- 代理和 TLS 结构检查。

不同来源要带时间、分类和置信度，旧信号不能覆盖更新事实。

Legacy 凭据行没有 `account_credentials` 主键，无法满足健康表的外键与版本唯一约束；当前实现会把
健康 subject 留空并跳过落库，直到账号迁入 v2 凭据存储。因此“请求成功或失败一定会更新账号健康”
只对具有稳定凭据身份的账号成立。

### 10.2 状态与冷却

健康状态至少区分：

- active；
- degraded；
- cooling_down；
- ramping；
- disabled；
- manual_pause 或等价手工状态。

限流、余额耗尽、认证失败、封禁、网络故障和协议错误的冷却时间不同。优先使用上游明确 reset，
没有 reset 时才使用对应错误类默认值。

用户可见健康分由两个不同来源组成：

```text
业务分 = 平均(错误率线性分, TTFT P99 线性分)
基础设施分 = 可服务自动渠道数 / 自动托管渠道数 × 100
总分 = 0.70 × 业务分 + 0.30 × 基础设施分
```

错误率 `<=1%` 取满分、`>=10%` 取零分；TTFT P99 `<=1s` 取满分、`>=3s` 取零分；
手工暂停渠道不进入基础设施分母。没有可用渠道数据时当前实现返回 100，这表示“不误报基础设施
全挂”，不能解释成“已证明健康”。

### 10.3 分阶段恢复

冷却到期不能立即全流量恢复。恢复过程：

1. 进入 ramping；
2. 允许小比例真实请求；
3. 根据成功率和错误类扩大流量；
4. 新失败触发回滚；
5. 达到门槛后恢复 active；
6. 手工暂停不由自动任务解除。

### 10.4 DLQ、outbox 和恢复意图

异步或事务后副作用失败时必须分类：

- 可以安全自动重试；
- 需要等待依赖；
- 需要重新 claim；
- 已交付但结算未完成；
- 无法确定上游副作用；
- 必须人工处理。

恢复处理器必须以幂等键重新读取当前事实，不能盲目重放旧 payload。成功后要标记恢复结果；
再次失败要更新次数、下一次时间和最终人工状态。

账号“完整恢复”当前不是一个覆盖账号行和渠道行的数据库原子事务。实现先在事务内恢复账号状态、
清理限流轴并写操作日志，然后再调用渠道控制器把关联渠道强制恢复；第二段失败时返回
`ErrPartialRecovery`，账号行已经提交。重试会重新读取当前事实并继续收敛，但运维端必须明确展示
“部分完成”，不能把错误响应解释成“什么都没改”，也不能无脑回滚已经成功的第一段。

## 11. 日志、观测与保留

### 11.1 产品口径

产品统一称“日志系统”。技术实现可以分为运行日志、请求 attempt、管理员操作、资金证据、
安全事件和恢复记录，但界面和手册必须按分类统一检索。

### 11.2 必要字段

可行动日志至少包含：

- 时间；
- 类别和事件类型；
- 结果；
- 错误类和是否可重试；
- 恢复状态；
- request ID / trace ID；
- 租户、用户、Key 的安全引用；
- 模型、池、账号和 attempt；
- 操作者角色和 scope；
- 不含秘密的原因。

### 11.3 30 天清理

普通运行和操作日志默认保留 30 天，由后台任务分批清理。清理必须：

- 有界批次；
- 可重复运行；
- 不长时间锁表；
- 多副本只由一个拥有者执行；
- 记录删除数量、耗时和失败；
- 不触碰永久账本、订单、退款、争议、幂等和未完成恢复事实。

当前运行日志 sink 采用异常优先双队列，不反压业务；队列满、数据库失败或 sink panic 时允许丢弃
并计数。因此它适合运行排障，不得作为资金、权限或恢复完成的唯一证据。

## 12. Hermes 运维助手

### 12.1 定位

Hermes 使用官方 Runner。HUAKAI 不重新开发模型代理；HUAKAI 负责：

- 给官方 Runner 提供租户隔离的 MCP 工具；
- 从真实管理员身份恢复租户和权限；
- 对高风险动作生成预览和确认；
- 限流、并发、超时、日志和恢复；
- 隔离 Runner 的网络和宿主权限。

最终用户无 Hermes 入口。部署者和获授权的租户管理员可以配置自己的外部 OpenAI 兼容
URL + Key；租户 Hermes 只能看见并操作本租户。

外部模型 URL + Key 由官方 Runner 直接使用。只有部署者或租户把该 URL 配成 HUAKAI 网关时，
Hermes 的模型推理才进入 HUAKAI 账号池和计费；MCP 运维工具无论模型来自哪里都必须回到 HUAKAI
并重新校验租户和角色。

### 12.2 身份链

```text
管理会话
 -> platform_admin / tenant_operator
 -> tenant capability
 -> Hermes principal
 -> 短时内部令牌
 -> 官方 Runner
 -> /internal/hermes/mcp
 -> 从令牌恢复固定租户与真实管理员
 -> 工具注册表再次授权
```

Runner 不能自行传入另一个租户 ID 覆盖令牌。内部令牌、管理员、租户 capability 任一不成立即拒绝。

### 12.3 工具分级

- 只读工具：查日志、账号健康、配额、凭据状态、DLQ、池组和服务器状态；
- 提议工具：生成结构化变更计划，不直接写；
- 修改工具：必须满足开关、角色、scope、预览、确认、限流、并发和事务恢复。

确认必须绑定：

- 租户；
- 操作者；
- 工具；
- 参数摘要；
- 计划摘要；
- 过期时间；
- 单次消费。

参数变化、换人、换租户、过期或重放都必须拒绝。

### 12.4 修改恢复

Hermes 修改动作不能只靠聊天记录证明。持久化事实需要记录：

- tool call；
- dry-run / preview；
- confirmation；
- 实际变更；
- 日志写入；
- 事务提交；
- 不确定提交或日志失败的恢复记录。

Hermes 修改守卫当前是进程内实现：默认每实例最多 4 个并发修改、等待槽位 2 秒、事务上限 90 秒，
并按管理员令牌限制每分钟 30 次已确认修改。它能保护单个 Gateway 实例，但多副本部署时每个实例
各自维护信号量和滑动窗口，集群总预算会随副本数放大；数据库事务、advisory lock、确认绑定和恢复
日志仍负责最终一致性。运维容量规划不能把单实例限额误当成集群级全局限额。

## 13. 后台任务与多副本

### 13.1 通用 worker 合同

每个 worker 需要明确：

| 项目 | 要求 |
| --- | --- |
| 是否默认启动 | 不允许能力存在但永远不启动 |
| 首轮时机 | 需要立即采集的任务不能等完整 ticker |
| 周期 | 可配置且有安全上下限 |
| 批次 | 有界，避免长事务 |
| 所有权 | PostgreSQL 租约、advisory lock 或幂等任务 |
| 超时 | 单轮和单项都有限时 |
| 停止 | 响应父 context 并等待退出 |
| 可观测 | 最后成功、失败、数量、耗时和错误类 |
| 恢复 | 自动重试、DLQ 或人工入口 |

### 13.2 当前主要 worker

当前组合根包含或构造的任务覆盖：

- 凭据刷新与轮转；
- 配额采集；
- 模型同步；
- 账号/渠道恢复；
- 代理健康；
- TLS profile 结构健康；
- 订阅到期；
- 结算与 settlement intent；
- DLQ/outbox；
- 日志和用量保留；
- 服务器监测；
- Hermes 恢复；
- staged OAuth 清理；
- 账号自动上架等。

“构造了 worker”不等于“生产启动了 worker”。核实时必须从构造追到生命周期注册。钱路 worker
即使有紧急停机开关，也必须区分“默认运行”和“显式停用”，不能根据存在环境变量就推断默认关闭。

当前必须单独识别的默认值：

| 能力 | 当前默认 | 关闭时的实际影响 |
| --- | --- | --- |
| 支付过期订单清理 | 开启，默认每分钟扫描；显式周期 `0` 才停用 | 过期订单不会自动扫描收口 |
| 订阅自动续费 | 开启；显式 `false` 才停用 | 到期与提醒仍运行，但不会自动扣钱包续期 |
| settlement intent 正向写入与 sweeper | 开启；显式 `false` 才停用 | 同步计费协议失去交付前崩溃恢复证据，也不扫描悬挂意图 |

三者均为默认部署的运行保障，并保留显式应急停用口。发布说明和 readiness 必须展示实际运行
状态，不能仅根据环境变量是否存在推断 worker 已启动。

TLS profile 健康 worker 当前只读取 active profile，并调用 `ValidateProfileFields` 检查字段是否能
组成受支持的动态 profile；失败时标记 `drift_detected`。它没有向真实厂商发起 TLS 握手，也不证明
JA3/JA4、ALPN、HTTP 版本或上游策略仍然接受该 profile。因此“结构校验通过”只能表示配置可执行，
不能展示为“真实上游健康”。

## 14. 数据库、迁移与并发

### 14.1 PostgreSQL 权威性

以下事实只以 PostgreSQL 为准：

- 租户、用户、Key 和权限；
- 账号、凭据版本、模型、池和 binding；
- 余额、账本、用量、订单、退款和争议；
- 日志索引和恢复事实；
- worker 租约和多副本协调；
- Hermes profile、会话、确认和恢复。

Redis 与内存只保存可重建的短期限流、缓存或进程状态，不能成为第二账本。

### 14.2 迁移

生产升级由一次性 migrate 任务先执行，Gateway 不在多副本启动时竞争迁移。迁移要求：

- 顺序不可跳；
- 新代码声明所需版本；
- 失败阻止接流量；
- destructive down migration 不作为生产回退保证；
- 回退优先使用兼容代码和前向修复迁移；
- 测试库即用即建、迁移到当前版本、用后删除。

### 14.3 并发工具选择

| 场景 | 优先机制 |
| --- | --- |
| 单行余额、凭据版本、任务状态 | `SELECT ... FOR UPDATE` 或版本条件更新 |
| 幂等键串行 | 唯一约束 + advisory transaction lock |
| 跨实例周期 worker | PostgreSQL 会话租约或 advisory lock |
| 可安全重试事务冲突 | 有界重试 + context 取消 |
| 事务后副作用 | outbox / recovery intent |
| 批量账号导入 | 每项独立事务 + 部分成功结果 |

## 17. 当前已确认的设计偏差

本节只保存尚未被代码解决、会影响理解当前架构的偏差；具体修复进度放 Issue/PR。

1. **Sidecar 目标边界与当前依赖不完全一致**：目标是只服务需要客户端形态的账号转 API；
   当前还被 CRS 复用并成为全局启动/readiness 依赖。
2. **账号创建型 OAuth start 弱幂等**：Start 没有接收稳定幂等键，随机 flow ID 又成为默认
   幂等摘要；`provider_account_id` 为空时现有唯一索引不能阻止重复短期流程。最终写账号仍有身份
   消歧，但重复授权流程本身没有收敛。
3. **协议入口链路颗粒度不一致**：chat 主链最完整并具备模型级回退；Completions、Embeddings、
   Rerank、Images、Audio 等兄弟协议主要只有当前模型内的池/账号重试，不能宣称同等回退合同。
4. **Legacy 凭据健康回流缺口**：没有稳定凭据 ID 的旧行会跳过健康落库。
5. **模块静态目录陈旧**：`module-catalog.json` 来自 2026-05-30 的旧功能树，多个状态已被
   后续主线推翻；运行探针可用于判断接线，但静态 `status/parity` 不能作为当前完成度真相。
6. **业务前端尚未实现**：旧业务前端、静态嵌入和 SPA 回退在本变更中退役；后端能力不能因页面
   尚未实现被误判不存在，反之也不能因 OpenAPI 有路径就宣称运营体验已闭环。
7. **真实厂商矩阵不足**：源码和测试合同不能证明所有厂商、协议、模型和能力已活体验证。
8. **资金能力名称大于实际效果**：`/v1/payments/balance` 不是总钱包；reprice 不是完整财务冲正；
    当前退款不是外部渠道原路退款。
9. **账号完整恢复存在部分提交窗口**：账号状态和操作日志先提交，渠道强制恢复随后执行；第二段
    失败会返回部分完成，依赖重试收敛，当前没有跨两套状态存储的单事务。
10. **Hermes 修改预算不是集群级限额**：并发和按管理员滑动窗口均在单进程内，多副本总预算随
    Gateway 副本数增加；事务锁和幂等只防止冲突与重复效果，不等价于全局流量配额。
11. **TLS profile 健康只验证结构**：worker 不进行真实目标握手，不能据此证明上游可达或指纹被接受。

## 19. 前端重构能力规格

### 19.1 定位和判定口径

本变更删除旧业务前端、静态嵌入和 SPA 回退，新的业务前端尚未建立。本节不是某一版页面草图，
也不规定最终视觉稿；它把当前后端能力和已核实缺口翻译成前端必须承接的产品合同。

`/home/ubuntu/main-frontend-style.zip` 中的运营服务台、运维服务区和账号与 IP 代理样例只用于提取
功能项。最终前端不得照搬它们的页面结构、卡片密度、排版、视觉风格或交互方式。能在同一业务
工作台用标签页、抽屉和弹窗完成的能力，不拆成大量孤立页面。

本节只使用以下前端状态：

| 状态 | 含义 |
| --- | --- |
| **已有可接** | 生产路由、鉴权、数据和错误合同已经存在；当前只是没有业务前端入口。 |
| **已有但未接 UI** | 后端能力完整或基本完整，但前端还需要组合多个 API、补状态机和操作确认。 |
| **后端部分具备** | 底层事实或单项 API 已有，页面需要的聚合、批量、恢复或作用域合同还不完整。 |
| **前后端都缺** | 主线没有可证明的生产入口和前端实现。 |
| **已领先** | HUAKAI 已有比对标功能更细的隔离、状态、恢复或安全合同，前端必须保留。 |
| **不适用** | 对标行为与 HUAKAI 的租户、安全或资金合同冲突，不应照搬。 |

“已有”必须同时有生产路由和真实运行依赖；OpenAPI、测试或数据库字段单独存在不算已接线。

旧版把多个身份、多个方法和多个生命周期塞进同一行后得到“88 项”，这个数字已经废弃。它会把
“有 CRUD”误算成“创建、更新、删除、日志和恢复都完整”，也会漏掉首装、认证安全、公共站点、
通知社区、媒体任务、租户生命周期等整块能力。

现行统计分两层：

1. **HTTP 操作面**：当前 OpenAPI 有 487 个 `method + path` 操作，实际使用 69 个 tag；顶层只
   声明了 45 个 tag，说明合同元数据仍需收敛。操作数包含兼容别名和技术端点，只用于发现漏接
   入口，不能直接当产品功能数。
2. **产品能力面**：按 `path + method + actor + lifecycle` 拆成原子单元；只有身份、运行接线、
   数据事实、失败恢复和运营状态完全相同的操作才允许合并。本轮从当前生产路由、DI、存储、
   worker 和状态回流交叉核实出 158 个原子能力，统计如下。

| 后端与前端状态 | 数量 | 当前结论 |
| --- | ---: | --- |
| 已有可接 | 56 | 后端入口和运行合同可供新前端直接消费，业务前端实现仍为空。 |
| 已有但未接 UI | 61 | 后端已具备主要能力，新前端还需组合 API、状态机、确认和部分成功交互。 |
| 后端部分具备 | 17 | 已有底层事实或局部入口，仍缺聚合、全协议覆盖、集群口径或恢复闭环。 |
| 前后端都缺 | 10 | 当前生产源码没有完整入口，属于明确后端缺口和后续前端能力。 |
| 已领先 | 12 | HUAKAI 已有更细的隔离、恢复或安全合同，新前端必须完整承接。 |
| 不适用 | 2 | 对标行为与 HUAKAI 的安全、租户或资金合同冲突，不进入实现。 |
| **合计** | **158** | 其中 27 项存在后端实现缺口；除 2 项不适用外，156 项均需新前端承接。 |

当前业务前端实现为空。因此“已有可接”只表示后端可供新前端消费，不表示已有界面。适用能力应
集中到少量业务工作台、标签页、抽屉和弹窗中，不按接口或原子能力拆成数百个页面。

### 19.2 三身份和页面范围

前端只出现三种业务身份，不新增“代理商”等第四身份：

| 身份 | 可见范围 | 前端硬约束 |
| --- | --- | --- |
| 部署者 `platform_admin` | 部署者工作租户和被明确授权的管理能力 | 不能默认越级处理下级租户最终用户；切换目标租户时必须显示当前作用域。 |
| 租户管理员 `tenant_operator` | 自身租户、其用户、Key、账号、池和日志 | 所有列表、聚合、导入、恢复和 Hermes 上下文都固定在认证作用域。 |
| 最终用户 `user` | 自己的资料、Key、用量、配额、余额、订阅和争议 | 不能读取账号、凭据、上游池内部、代理、其他用户或运营成本。 |

建议的信息架构如下。它是业务容器清单，不是强制的路由数量：

| 业务容器 | 部署者 | 租户管理员 | 最终用户 |
| --- | --- | --- | --- |
| 总览 | 运营服务区、运维服务区 | 本租户经营与运行总览 | 我的余额、用量、配额和近期调用 |
| 上游与模型 | 账号、凭据、模型、池、代理、健康、导入和恢复集中工作台 | 同一工作台但固定本租户 | 不可见 |
| 用户与 Key | 租户、用户、Key、余额授权和能力授权 | 本租户用户、Key 和余额 | 自己的 Key 与安全控制 |
| 资金与商品 | 费率、余额、兑换码、订阅、订单、退款、争议 | 本租户允许的经营能力 | 余额、兑换、订阅、订单、退款申请和争议 |
| 日志与恢复 | 全局或明确租户作用域的日志、告警、DLQ 和对账 | 本租户日志、告警和获授权恢复 | 自己的调用记录、收据和争议进度 |
| 系统与助手 | 节点、备份、配置、模块、Hermes | 本租户 Hermes 和租户设置 | 不开放 Hermes 运维面 |

### 19.2.1 多角度核验矩阵

每个原子能力必须从以下角度同时判断。任一关键角度只有表、类型、测试或文档而无生产消费者时，
状态最多只能是“后端部分具备”：

| 角度 | 必须核实的生产事实 | 常见假完成 |
| --- | --- | --- |
| 身份与作用域 | 三种身份谁能调用，目标租户和用户从哪里取得 | handler 有角色判断，但平台身份可越级指定下级用户 |

| 数据与事务 | 权威表、唯一约束、锁、业务写与日志是否原子 | 先改业务再写日志，日志失败却返回整体失败 |
| 外部副作用 | 是否真的发上游请求、成本上限、超时和秘密边界 | “测试账号”只刷新凭据，未实际验证模型请求 |
| 异步与恢复 | worker 默认值、租约、多副本去重、重试、DLQ 和人工恢复 | worker 写了但默认不启动，或失败后只有一条进程日志 |
| 状态回流 | 健康、额度、计费、结果和新鲜度是否写回唯一事实 | 请求成功但账号健康和运营投影仍停在旧状态 |
| 前端合同 | 加载、空、未知、过期、冲突、部分成功、权限拒绝和重试 | 只有成功 toast，批量失败无法知道哪一项出错 |

当前已确认的“表面存在、链路未闭合”：

1. `channel_test_templates` 有表、CRUD、路由、OpenAPI 和同事务操作日志，但没有运行时消费者，
   也没有执行、结果、恢复或状态回流；它不是已经可用的频道测试能力。
2. 用户 Key 批量撤销原先遇到首个非“不存在”错误就中断，也没有完整逐项结果；本 PR 已补成
   有序逐项状态、稳定错误码和批次总状态，非法集合在任何副作用前整体拒绝。
3. 内容审核只注入 Chat 执行族；Completions、Embeddings、Rerank、Images、Audio 和 Video
   没有等价前置审核，不能把“规则、命中、封禁、解封”描述成全协议闭环。

账号真实探测已在本 PR 补齐：它固定命中指定账号，复用统一凭据、代理、TLS、协议、错误分类和
健康状态机，使用短提示和 8 个输出 Token 上限，不进入用户选号、fallback、重试、claim、余额、
配额或结算。主动探测时间、延迟与操作日志同事务落地；上游超时后健康信号仍使用独立短时上下文
回流。该项从“后端部分具备”升级为“已有可接”，但不等于频道测试模板或定时探测已经完成。

### 19.11 全局前端交互合同

所有管理页共同遵守：

1. 每个异步操作都有 `idle/loading/success/partial/error/retryable/operator_required` 状态；
2. 批量操作返回逐项结果，不能只弹“成功”或“失败”；
3. 自动刷新档位、倒计时、列显隐和本地筛选属于前端能力，不为此新增后端配置；
4. 服务端分页、聚合、权限和秘密脱敏不能下放给前端模拟；
5. 危险操作使用前端二次确认并展示影响范围，不重新引入后端 TOTP/step-up 合同；
6. `404`、`409`、`429`、`503` 和部分成功必须使用不同恢复建议；
7. 未知、未采集、过期、不适用和真实零值使用不同展示状态；
8. URL 中的 `tenant_id` 不是权限来源，界面只使用认证上下文允许的作用域；
9. 所有金额显示币种、精度和口径；所有时间显示时区和新鲜度；
10. 账号、Key、凭据、代理秘密和原始敏感请求体绝不出现在页面、导出或浏览器日志。

### 19.11.1 前端安全基线

前端开工前必须先接受一个事实：浏览器、页面状态、URL、隐藏按钮、TypeScript 类型和本地缓存都
不是可信边界。目标不是声称“绝对攻不破”，而是让常见注入和越权难以成立，并在某个页面或依赖
被攻破时把凭据寿命、租户范围、可写对象和资金影响压到最小。

1. **会话只走浏览器模式。** 登录、二次验证、OAuth、Telegram、Passkey 和刷新统一发送
   `X-HUAKAI-Session-Mode: browser`。短期访问令牌只保存在进程内状态，不写
   `localStorage`、`sessionStorage`、IndexedDB、URL、Service Worker 缓存或持久状态库；
   页面刷新后通过 `__Host-huakai_refresh` 的 `HttpOnly + Secure + SameSite=Strict`
   Cookie 换取新短令牌。刷新请求同时提交 `X-HUAKAI-CSRF`，刷新令牌不得出现在 JSON。
2. **前端权限只负责可见性。** 路由守卫和按钮隐藏不是授权。每次读取或写入仍由后端从认证上下文
   重算角色、租户、对象归属、字段权限和能力授权；页面不得把 URL、表单或缓存里的 `tenant_id`、
   `user_id`、`role` 当成权限事实。收到 `401/403` 后清除内存令牌和敏感页面状态，不能静默换成
   更高权限接口重试。
3. **DOM 默认只写文本。** 业务组件禁止 `innerHTML`、`dangerouslySetInnerHTML`、
   `document.write`、`eval`、字符串定时器、动态脚本和字符串拼接 URL。模型名、账号标签、日志、
   Markdown、上游错误和用户资料都按不可信输入处理；普通内容使用框架文本转义，确需富文本时只
   能经过唯一、测试覆盖的清洗器和 Trusted Types 策略，并限制链接协议为 `https/http/mailto`。
4. **不加载任意第三方脚本。** 生产包从锁文件可复现构建并以内嵌哈希资源发布，不从 CDN、租户
   配置或上游响应动态加载 JavaScript。确需新增监控或编辑器依赖时，先做维护状态、许可证、传递
   依赖和已知漏洞审查；禁止把真实请求体、令牌、Cookie、Key 或账号凭据发送给埋点服务。
5. **浏览器网络面默认拒绝。** 正式浏览器会话只连接同源 API；内嵌部署天然同源，页面与 API
   使用不同主机时必须由页面入口反向代理 `/v1`，不能用 CORS 绕过 `SameSite=Strict` Cookie
   边界。`HUAKAI_CORS_ALLOWED_ORIGINS` 只给不使用 Cookie 会话的 API 浏览器客户端授予精确
   HTTPS 来源，HTTP 仅允许 loopback 开发地址。服务端对跨源 `browser` 会话、不可信 `Origin`、
   方法和预检请求头在业务 handler 前直接返回 `403`，不回显调用方自报请求头。CSP 保持脚本
   同源、禁止脚本属性、插件对象、frame 和外部表单目标；生产必须使用 HTTPS/HSTS。Trusted Types
   必须与前端唯一富文本清洗策略、构建产物和浏览器端攻击测试同批原子启用，未建立策略前不得只开
   响应头导致白屏，建立策略后也不得通过放宽 `default` 策略绕过集中清洗。
6. **接口合同由 OpenAPI 生成。** 页面不手写第二套 URL、字段名、角色枚举和错误码；请求只发送
   端点允许的字段，金额使用后端规定的最小单位/精度，未知字段和未知枚举进入明确错误态。支持
   `Idempotency-Key`、版本冲突或部分成功的写操作必须复用统一请求封装，禁止按钮重试重新制造
   一次逻辑操作。
7. **秘密永不进入展示链。** Key 只接收后端“一次展示”响应，随后立即从组件状态清除；输入框
   默认不自动填充、不复制到查询参数、不进入错误上报。浏览器日志、Redux/Query 调试器、网络
   mock、截图、导出和剪贴板提示均不得保留 refresh token、完整 Key、Cookie、账号凭据和原始
   敏感请求体。
8. **危险操作有真实影响预览。** 删除、停用、批量变更、余额调整、退款和恢复先展示目标租户、
   对象数量、金额、不可逆部分和预期版本，再由用户明确确认；确认弹窗只防误操作，不作为授权
   或后端校验替代品。提交后按逐项结果展示成功、失败、未执行、可重试和需人工处理。
9. **文件与外链隔离。** 导入先校验大小、类型、条目数和解析错误，预览不执行其中内容；下载使用
   后端确定的类型和文件名。外链使用固定协议白名单及 `noopener,noreferrer`，OAuth 回调严格校验
   本地保存的 state，不把 token 带回任意跳转地址。
10. **发布前主动攻击。** 除组件和端到端功能测试外，必须覆盖存储型/反射型/DOM XSS、CSRF、
    CORS 来源伪造、跨租户 IDOR、批量字段注入、重复提交、旧版本覆盖、OAuth state 重放、退出后
    刷新、依赖漏洞和源码映射泄密。只验证“按钮看不见”或“浏览器拦住响应”不算通过。

前端第一版不得通过放宽 CSP、把令牌改存本地或开放通配 CORS 来解决开发便利问题。确需把页面
部署到不同主机时，部署层必须把 `/v1` 反向代理到页面同源；把来源加入
`HUAKAI_CORS_ALLOWED_ORIGINS` 不会、也不应解锁 Cookie 浏览器会话。该配置不接受通配符、远端
HTTP、路径、查询串、userinfo 或 `null` 来源。

当前后端已经提供上述浏览器模式会话、刷新 CSRF 绑定、显式来源 CORS、安全响应头、严格 JSON
解码、三身份租户作用域和 OpenAPI 参数合同。它们是前端开工基线，不等于前端成品已经通过安全
验收；真实依赖树、DOM 行为和浏览器攻击场景只能在页面实现后验证。

#### 19.13.1 产品需求文档（PRD）

**产品目标**

1. 为部署者提供可扫描、可追踪、可恢复的集中运营和运维工作台。
2. 为租户管理员提供严格限定在本租户的经营、用户、上游资源、日志和 Hermes 管理面。
3. 为最终用户提供 Key、模型、用量、配额、余额、订阅、调用记录和安全自助。
4. 把 HUAKAI 已有的健康、配额、恢复、信任证据和三身份隔离完整呈现出来，不退化成只有 CRUD
   的普通中转站面板。
5. 所有危险动作都能看到目标、作用域、影响、版本、部分成功和恢复结果；所有未知状态均明确
   显示为未知，不伪造成零值、满额或成功。

**非目标**

1. 不把前端作为授权、金额、配额、租户归属或模型能力的权威来源。
2. 不恢复历史前端、旧分支页面、占位 HTML、mock 类型或旧构建产物。
3. 不提供任意 SQL、Shell、任意 URL 探测、任意 Header/Body 出站或明文凭据浏览器存储。
4. 不在当前阶段宣称公共 MCP、Realtime、Cursor、Copilot 或 Windsurf 已上线。
5. 不为了减少一级页面而隐藏权限、失败、恢复或操作日志。

**核心产品指标**

| 指标 | 计算口径 |
| --- | --- |
| 任务成功率 | P0 用户旅程中无需人工绕过即可完成的比例 |
| 错误可解释率 | 后端稳定错误码能映射到明确原因、影响和下一步的比例 |
| 恢复闭环率 | 可恢复失败能从原业务对象进入重试、对账或人工解决并看到终态的比例 |
| 权限误导数 | 页面显示可执行但后端必然拒绝，或隐藏实际可执行能力的次数，目标为 0 |
| 合同漂移数 | OpenAPI、生成客户端、运行路由和页面调用不一致的阻断缺陷数，目标为 0 |
| 秘密泄漏数 | Key、Cookie、refresh token、上游凭据或敏感原文进入持久浏览器状态、日志或导出的次数，目标为 0 |

#### 19.13.3 项目角色、进入条件与完成定义

正式前端项目按交付责任分工，不把“产品、设计、开发、测试、运维”压成一个模糊状态：

| 责任 | 必须产出 | 不得替代 |

| 产品与交互 | 用户旅程、信息架构、逐页规格、状态和异常流、验收标准 | 不替后端发明数据或权限 |
| 视觉与设计系统 | Token、组件、关键页面、响应式和可访问性标注 | 不只交成功态截图 |
| 前端工程 | 技术设计、生成客户端、页面实现、监控、测试和构建产物 | 不手写第二套 API 合同 |
| 后端工程 | OpenAPI、权限、聚合、幂等、错误码、恢复和测试环境 | 不要求浏览器自行补业务真相 |
| 测试与安全 | 合同、E2E、越权、攻击、可靠性、性能和可访问性证据 | 不以按钮隐藏证明授权 |
| 运维与发布 | 同源代理、环境配置、监控、灰度、回退和故障手册 | 不在发布时临时放宽 CSP/CORS |

切片进入开发前的 Definition of Ready（DoR）：

1. PRD 范围、用户旅程、页面归属和明确非目标已经确认；
2. 相关 operation 在生产路由与 OpenAPI 中一致，身份、租户和 capability 来源明确；
3. 正常、空、加载、权限拒绝、冲突、限流、依赖失败、部分成功和人工恢复均有设计；
4. 设计稿覆盖目标断点与组件状态，文案不泄露秘密或混淆金额、日志和权限；
5. 后端缺口已经进入当前唯一计划，不能用 mock 永久绕过。

切片完成的 Definition of Done（DoD）：

1. 页面、生成客户端、真实 API、权限和失败恢复接通，未新增平行请求层或状态真相；
2. 逐页验收、合同、E2E、安全、性能和可访问性测试通过；
3. 指标与错误可关联到页面、operation ID 和 request ID，浏览器日志不含秘密；
4. 依赖、构建、同源部署、灰度、回退和运行手册具备可执行证据；
5. OpenAPI、工程设计手册与实现一致，已完成事项不继续留作旧计划或重复报告。

#### 19.14.1 逐页规格

**`FE-PG-001` 首装与认证**

- 首装页只在 `/setup/status` 返回未安装时出现；安装成功后不可再次进入。
- 登录保留 `password -> challenge -> 2FA/device confirmation -> session` 状态，不重复发起密码阶段。
- refresh token 只在受保护 Cookie，短访问令牌只在内存；OAuth state、CSRF 和一次性秘密均在终态后清理。
- 包含邮箱验证、重发、密码重置、Passkey、TOTP、Telegram/OAuth 绑定和会话撤销。
- 必测：限流、防枚举、失效 challenge、OAuth 重放、退出后刷新、最后登录方式解绑风险。

**`FE-PG-002` 总览**

- 最终用户显示余额、用量、配额、Key、近期调用、通知和订阅。
- 租户管理员显示本租户用户、Key、账号、池、请求、费用、错误、告警和恢复状态；后端投影未完成的
  指标明确标“待后端提供”，不得调用平台接口或在浏览器聚合内部明细。
- 部署者运营服务区显示请求、Token、费用、模型和用户排行、成功率、性能、活跃用户/Key/租户。
- 部署者运维服务区显示节点、数据库、Redis、Sidecar、模块、账号/池健康、配额、代理、日志和 DLQ。
- 所有图表共享时间范围、时区、新鲜度和导出口径；“无数据”与“统计不可用”分开。

**`FE-PG-003` 上游与模型**

- 一个集中工作台承接账号列表、详情抽屉、账号模式导入向导、凭据续期、5h/7d 配额弹窗、套餐标签、
  健康状态、模型发现/同步、账号测试、池和路由、代理及恢复动作。
- 列表支持服务端筛选、游标分页、列显隐、自动刷新和逐项批量结果；不做前端假分页。
- 导入必须先 plan 后 execute；创建、更新、冲突和跳过逐项展示，身份冲突禁止默认选第一条。
- 官方 Key 不显示 TLS mimicry；只有模式合同要求的账号显示指纹档案。
- 池与路由显示 `模型 -> 池 -> 账号` 关系、优先级、限速、生效窗、健康和 fail-closed 原因。
- 删除代理、租户、池或引用资源前先读取影响，提交时仍由后端重新校验版本和引用。

**`FE-PG-004` 用户与 Key**

- 部署者的租户标签包含租户列表、创建抽屉、生命周期、能力授权、经营钱包和默认代理。
- 部署者不得获得调整下级租户最终用户余额的按钮；租户管理员只管理自身租户最终用户。
- 用户详情集中显示资料、状态、分组、2FA/Passkey、通知偏好、余额历史、已结算用量、Key 和违规状态。
- Key 详情集中编辑名称、到期、配额、分组、模型白名单、IP 白名单/黑名单；明文只在创建成功时显示一次。
- 批量撤销按有序逐项结果呈现 `success/failed/not_executed/retryable`。

**`FE-PG-005` 资金与商品**

- 金额组件必须显示币种、精度、正负方向、前后余额、业务原因、幂等标识和永久事实链接。
- 区分租户经营钱包、最终用户余额、支付订单余额效果和模型调用结算，禁止都叫“余额”。
- 当前默认以管理员手工确认和兑换码为主；没有支付 provider 时不出现在线支付入口。
- 退款明确标为内部余额退款，不宣称外部渠道原路退回。
- 订单、退款和争议展示状态机、累计效果、永久操作日志、可重试动作和人工恢复入口。

**`FE-PG-006` 调用与媒体**

- 测试台按后端模型能力动态开放 Chat、Responses、Anthropic、Gemini、Embeddings、Rerank、图片、音频和视频。
- 原生 tool/function calling 显示工具请求、流式事件、终止原因和用量；不命名为公共 MCP。
- 图片、音频和视频使用各自输入控件、结果预览、下载和费用，不塞进一个 JSON 文本框。
- 异步媒体显示排队、执行、成功、失败、待对账、孤儿和恢复；页面卸载后可从任务列表继续追踪。

**`FE-PG-007` 日志与恢复**

- 产品统一称“日志”；按操作、资金、安全、错误、访问和恢复分类。
- 用户只看自身调用和收据；租户管理员只看本租户脱敏事实；部署者按明确作用域查看。
- 普通日志标注 30 天保留；账本、支付、退款、争议效果和幂等事实不提供清理按钮。
- DLQ、观测重放、结算恢复和媒体孤儿分栏，不能合并成一个无上下文的“重试”。
- 每个恢复动作显示幂等键、失败原因、影响范围、执行人、终态和再次验证结果。

**`FE-PG-008` 系统与助手**

- 系统标签包含节点、模块、readiness、备份清单、运行版本、日志级别和 allow-list 平台设置。
- 租户设置只包含本租户邮件、通知、内容规则和被授权能力；不提供服务器、数据库、Shell 或全局配置。
- 部署者可以为指定租户配置内容规则；租户管理员只读取本租户规则效果、查看脱敏违规和解封本租户 Key。
- Hermes 只在部署者和租户管理员面板出现，配置任意有效 OpenAI-compatible URL + Key；
  HUAKAI 只提供受权限、确认、预算和日志约束的内部工具。

### 19.15 设计系统与公共组件

设计系统必须先于业务页面落地，避免每个页面重新发明状态、权限和危险动作。

| 类别 | 必须交付 |
| --- | --- |
| Design Token | 语义颜色、字体层级、间距、边框、阴影、密度、层级、动效时长和响应断点 |
| 页面外壳 | 单侧栏、作用域提示、面包屑、全局搜索、通知、用户菜单和移动端导航 |
| 数据展示 | `DataTable`、游标分页、列显隐、筛选器、排序、空态、骨架屏和新鲜度 |
| 状态表达 | 统一 `StatusBadge`、健康/配额矩阵、错误分类、未知/过期/不适用和恢复进度 |
| 详情与操作 | 详情抽屉、标签页、时间线、影响预览、版本冲突、批量结果和危险确认 |
| 秘密组件 | 一次性秘密弹窗、脱敏字段、受控复制、自动清除和禁止持久化 |
| 金额与用量 | 金额、Token、费率、余额前后值、时间窗口、成本口径和精度组件 |
| 链路与日志 | 调用链路图、结构化日志查看器、请求 ID 跳转、DLQ/恢复动作条 |
| 表单 | schema 驱动字段、服务端错误映射、脏状态保护、文件导入预览和逐项校验 |
| 反馈 | 页面级错误、内联错误、toast、部分成功面板、重试倒计时和权限拒绝 |

组件验收必须覆盖键盘操作、焦点管理、屏幕阅读器名称、对比度、缩放和减少动效。页面区块不使用
卡片套卡片；工具栏优先图标和 tooltip；固定格式控件有稳定尺寸，动态文本不得推动布局。

### 19.16 前端技术设计

#### 19.16.1 代码与部署边界

1. 新前端使用独立 `frontend/` 工程；业务代码语言固定为启用严格模式的 TypeScript，UI 框架
   固定为 React，构建工具固定为 Vite。新业务代码不使用 JavaScript，也不手写第二套 DTO；
   初始化 PR 再锁定精确版本，并执行维护状态、许可证、传递依赖和漏洞审计。
2. Gateway 保持 API-only，不恢复 Go `embed`、SPA fallback 或 Node 构建阶段。
3. 生产静态站点由独立构建产物提供，并在入口层把 `/v1`、`/admin/v1`、`/internal` 中允许的
   浏览器路径反向代理到 Gateway；Cookie 浏览器会话必须同源。
4. 路由按业务容器懒加载；三身份共享组件和数据模型，只在路由、查询和动作层应用真实权限矩阵。

#### 19.16.2 状态与数据所有权

| 状态类型 | 权威位置 | 前端策略 |
| --- | --- | --- |
| 身份、角色、租户、能力 | 后端认证上下文 | 只读投影；切换页面不允许自改 |
| 服务端资源 | PostgreSQL/服务端投影 | 查询缓存；写成功后按资源键失效或用返回值更新 |
| 时间范围、筛选、分页 | URL | 可分享但不得包含秘密和未经授权的目标 ID |
| 表单草稿 | 组件内存 | 离开提示；秘密字段不持久化 |
| 一次性 Key/凭据 | 单次响应内存 | 展示后主动清除；不进入全局 store |
| 实时任务 | 服务端任务状态 | 轮询或流式更新；页面重载后按任务 ID 恢复 |

不建立包罗万象的全局状态仓库。服务端状态、URL 状态、表单状态和会话状态必须分层；乐观更新仅
用于后端可安全幂等且失败可完全恢复的低风险动作，资金、权限、删除和恢复动作禁止乐观宣告成功。

#### 19.16.3 API 接线合同

1. 从 `docs/openapi/openapi.yaml` 生成 TypeScript 类型和基础客户端，CI 检查生成结果与 spec 一致。
2. 手写代码只负责浏览器会话 Cookie/CSRF、SSE、文件上传下载、二进制媒体和统一错误映射。
3. 每个 operation 的 `后端模块 -> actor -> 菜单 -> 页面 -> 子场景 -> 方法/路径` 归属以
   [`前后端双向追踪矩阵.md`](前后端双向追踪矩阵.md) 为准；正常态、错误码和恢复动作继续由
   OpenAPI schema 与逐页验收合同约束。OpenAPI 未声明或生产路由未挂载的接口不能进入页面。
4. 请求封装统一注入 request ID、短访问令牌、CSRF、`Idempotency-Key` 和取消信号；禁止页面自己
   拼 Authorization、tenant scope 或重试策略。
5. `401` 进入会话恢复或退出，`403` 显示作用域拒绝，`404` 区分资源不可见与不存在，`409` 重新
   获取版本/影响后再确认，`429` 尊重 `Retry-After`，`503` 显示依赖或配置不可用，部分成功保留
   已成功项并只重试 `retryable` 项。
6. Query Key 必须包含认证作用域和资源作用域；退出、换租户或权限撤销时清空相关缓存。

#### 19.16.4 质量属性

- 可访问性：目标 WCAG 2.2 AA，所有核心旅程可仅用键盘完成。
- 性能：P0 路由首屏 JavaScript gzip 预算 250 KiB；路由拆包后单个异步块不超过 300 KiB；
  生产相似环境 p75 目标为 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1。
- 兼容性：明确支持当前两个主版本的 Chromium、Firefox 和 Safari；不以静默 polyfill 掩盖缺失能力。
- 可观测：采集页面、operation ID、request ID、耗时、结果和稳定错误码；不采集请求原文、秘密和凭据。
- 可维护性：业务模块按页面容器分包，公共组件只承载稳定跨域行为，禁止把业务权限塞进通用表格。

埋点与运行观测使用同一事件合同：`event_name`、页面编号、operation ID、角色类型、结果、稳定
错误码、耗时区间和 request ID。租户 ID、用户 ID 只能使用不可逆或服务端批准的关联标识；Key、
Cookie、请求原文、账号凭据、金额输入明细和上游响应不得进入前端分析事件。产品指标、错误告警
和后端追踪通过 operation ID 与 request ID 关联，不再建立一套只能在浏览器解释的错误分类。

### 19.18 测试、验收与发布门

| 层级 | 必须覆盖 |
| --- | --- |
| 静态 | TypeScript 严格模式、lint、格式、未使用代码、循环依赖、依赖许可和漏洞 |
| 单元 | 格式化、错误映射、权限投影、金额/时间、Query Key、状态归约和输入校验 |
| 组件 | loading/empty/error/stale/conflict/partial/denied/recovery、键盘与焦点 |
| 合同 | 生成客户端与 OpenAPI、operation 覆盖、错误码、枚举和分页信封 |
| E2E | §19.13.2 六条旅程，三身份各自正向、越权和作用域切换 |
| 安全 | XSS、CSRF、CORS、IDOR、OAuth 重放、批量字段注入、秘密持久化和源码映射泄漏 |
| 可靠性 | 断网、超时、取消、重复提交、过期数据、版本冲突、部分成功和页面重载恢复 |
| 性能 | 路由包预算、长表格、图表、日志流、内存泄漏和生产相似环境 Web Vitals |
| 可访问性 | 自动扫描加人工键盘、屏幕阅读器、缩放、对比度和减少动效 |
| 发布 | 独立静态产物、同源反向代理、HTTPS/CSP、API readiness、灰度、回滚和监控 |

页面只有在真实 API、真实权限、失败恢复和浏览器 E2E 同时通过后才标记完成。设计稿、静态截图、
mock 数据、Storybook 或单个 200 响应均不能独立证明交付。发布候选必须输出页面/operation
覆盖矩阵、未验证清单、依赖清单、性能报告、安全报告和已知风险，并由 Owner 批准进入生产。
灰度期间按错误率、登录成功率、核心旅程成功率、Web Vitals 和后端稳定错误码设停止线；触线即
回退静态前端版本，不回退数据库事实、不切换到已退役页面，也不放宽后端权限、CSP 或 CORS。
