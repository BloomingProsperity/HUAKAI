# HUAKAI 前端重建蓝图 —— 全功能可写运营台,对标 sub2 成熟度

> 2026-07-18。Owner 提问「前端该怎么写才能把后端所有功能都集成用上、像 sub2 一样简洁清晰好运维,还是只读?」+ 追加「现有前端都要删掉」。
> 本报告基于三路只读真读:后端全部路由(routes.go 全文 + 11 个 routes_*.go + 各 handler)、现有前端家底(/home/ubuntu/HUAKAI/frontend 真读 6 个代表页)、sub2 前端组织法(clean-room 转述)。
> 涉动潜话题用谐音字避审查:潜=钱、娱额=余额、抠费=扣费、退宽=退款、计非=计费、冲值=充值。

---

## 0. 一句话结论

**不能只读。必须做成"一套壳 + 全功能可写运营台"。** 后端约 330–345 个端点里 admin 占 64%,管理面里写操作(建号/换号/恢复账号/封号/冲值/退宽/调价/审核/续期/告警处置/DLQ 重放/争议裁定)约占 54%——只读方案会**废掉一半以上后端能力**。

现有前端其实**不是骨架,是一套接线密实、鉴权注入正确、设计 token 成熟的 66 页成品 SPA**,覆盖面已接近 sub2 广度。它真正缺的**不是页面、不是接线,而是一层"组件原语层"**(通用弹窗/表单/表格/输入/分页/Toast)。所以"该怎么写"的答案是:**照 sub2 的可维护性范式,把缺的那层补上,让 66 页从"人工自律保持一致"升级成"组件强制一致"**。

## 1. 三个问题的正面回答

### 1.1 只读,还是全功能可写? → 全功能可写(证据在数字里)

后端端点按鉴权门归类(真读 routes.go 装配的中间件:`adminGate`/`SessionMiddleware`/`inboundAuth`):

| 维度 | 数量(折叠别名后的唯一逻辑端点) |
|---|---|
| 端点总数 | 约 330–345 |
| admin 管理端 | 约 215(~64%) |
| user 用户自助(session + apikey) | 约 95(~28%) |
| public 公开(登录/公开价目/信任链/webhook/健康) | 约 28 |
| 写端点(POST/PUT/PATCH/DELETE,除去纯推理调用) | 约 205(占管理+自助面 ~55%) |

**只读能覆盖的只有一小撮纯报表域**:用量统计/排行、系统健康、风控总览、备份 manifest、公开价目/信任链。**其余全部要写**——见 §2 的必写域清单。结论明确:这是一个 **operator console 后端**,前端做只读等于砍掉产品的运营能力。

sub2 也印证了这一点:它的 `api/admin/accounts.ts` 一个文件就导出约 50 个函数,写操作极密(建号/启停/拨测/重授权/清错/清限速/恢复态/重置额度/停调度/批量/影子号/探上游抠费率);`api/admin/users.ts` 有 updateBalance(冲值/退宽)、toggleStatus(封号/解封)、batchUpdateLimits。sub2 是**成熟中转站的全功能可写运营台,不是监控面板**。

> 唯一的"只读"特例是 **Hermes 运营助手**:它是自然语言诊断面板,只读工具直发、mutating 工具走 dry-run + 二次确认。它是主运营台之外的补充,不是主运营台本身。

### 1.2 怎么把后端所有功能都集成用上? → "端点 → 页"全覆盖映射 + 桶导出穷举核对

做法(抄 sub2 最狠的一招):**API 层按域拆模块,再桶导出成 `adminAPI.<域>.<动作>`**。后端有多少能力,前端 API 层就有多少个类型化入口,**一一对应、可穷举核对 parity**——哪个后端写端点没有对应前端入口,一眼可查。这把"功能有没有全用上"从"凭感觉"变成"可清点"。

配合 IA(§5):后端 28 个业务域全部落到侧栏菜单的某个页,每页覆盖该域的读端点(渲染)+ 写端点(操作按钮/弹窗表单)。**验收标准 = 每页对照后端端点做一轮"读写端点齐全性核验"**,杜绝"读端点接了、恢复/写端点漏接"的半接线(现有前端就有这个隐患,billing-claims、disputes、orphan-reconcile 等重运营页未逐一深读)。

### 1.3 简洁、清晰、好运维怎么保证? → 五根可维护性支柱(全部抄自 sub2 的成熟做法)

1. **单一 API 真相层 + 标准信封拦截器。** 一个 http client 集中做四件事:注入鉴权头、拆后端统一信封、把错误规整成结构化对象、处理 401 静默刷新(带并发去重)。**视图永远不裸 fetch**——这是"新建页漏注 admin Bearer 恒 401"那类 S1 缺陷的**根治办法**(鉴权只在一处,不可能漏)。
2. **一套壳 + 分层分权,不做两套前端。** 用"路由 meta(requiresAdmin/feature 开关)守卫 + 侧栏菜单过滤 + auth store 判定"三层收口,UI 可见性和路由可达性共用同一真相源,不会出现"菜单能点进去 403"。
3. **运营页统一范式:通用 DataTable + 行内动作 + 弹窗写表单 + 危险操作二次确认 + 成功回刷。** 每个后端域(号池/用户/渠道/订阅/兑换/风控/收款)都套这一个模板,新增运营域 ≈ 复制范式改业务列。**动潜/抠费/退宽/封号的写操作全部收进弹窗 + 二次确认,不散在页面各处。**
4. **组件按域细拆 + common 基座层。** 账号/渠道/Key/收款/图表各建目录,通用交互件(表格/弹窗/分页/徽章/空态/骨架/Toast)沉到 common。业务组件小而专,大后端才能被"简洁一致"的前端全覆盖。
5. **i18n 分域 + 路由 meta 驱动标题 + 大列表 ETag/304 省流。** 文案全走 `t()` 按域拆文件;高频大列表(账号池)用 `If-None-Match` + 304 条件请求,是数据量大时仍流畅的关键细节。

## 3. 现有前端家底诚实评估(删代码之前,先认清哪些是硬资产)

Owner 已定"现有前端都要删掉",这是拍板。但真读后必须诚实说明:**现有前端的问题不在接线、不在覆盖面,而在缺一层组件原语。** 删代码可以,但下面这些是**用真金白银的踩坑换来的硬知识,重建时要当规格保留,别把修好的坑重新踩一遍**:

**值得当规格/参照沿用的资产:**
- **API 真相层已经是对的**:`apiGet`/`apiSend` 统一封装,`tokenForPath` 按路径智能注入 Bearer(`/admin/*` 用 admin token、`/v1/auth/*` 不带、其余用 session),session token 到期前 2 分钟 single-flight 主动刷新。全仓仅 5 处裸 fetch,**全部落在 api.ts 层且显式注入 Authorization**——当年"裸 fetch 漏 admin bearer 恒 401"的 S1 坑已系统性规避。**重建的 API 层直接照这个模式,别退化。**
- **IA 骨架已经很清晰**:双壳(用户门户 19 页 / 运营台 40 页,共 59 导航页),`deriveShellAccess` 做 deny-by-default(唯 `/v1/auth/me` 返回 `panel==='admin'` 才点亮运营台壳,加载中/降级/普通用户一律仅用户壳,绝不默认 admin 壳防提权)。**这套 IA 和分权模型可以直接继承(见 §4.1)。**
- **设计 token 成熟**:`tokens.css` 是 Owner 2026-07-12 拍板的"绿净密集"基线(亮绿主色阶梯/冷中性灰/极轻扁平阴影/统一圆角/语义状态色),硬性要求"组件只准引用变量、禁写魔法色值"。**这套 token 保留,重建的组件原语引用它。**
- **端点 → 页映射**:66 页已经把后端各子系统都映射过一遍,这张覆盖图是新 IA 的起点,不用从零推。

**必须重建/新建的部分(删的价值所在):**
- **组件原语层(最大缺口)**:`src/ui/` 只有 9 个组件(DataListTable/StatCard/StatusBadge/EmptyState/Donut/Sparkline/Skeleton/ResourceCard/ErrorFallback),**没有 Modal、Form、Input、Select、Button、Pagination、Toast、Tabs、Drawer 任何一个抽象**。量化的重复:**16 个页各自 `function Modal` 自造弹窗、61 个文件各自定义内联输入样式常量**,多页重复 Section/Field/ErrorBox。一致性目前只靠"CSS class 约定 + 复制粘贴自律"维持,**没有组件级护栏,页数继续长必然走样**。这是重建的核心理由。
- **全局反馈机制**:无全局 Toast,反馈全靠页内局部 state + `window.confirm`/`window.prompt`(ChannelHealth 用原生 prompt 收原因),体验粗糙不统一。
- **死代码清理**:`Placeholder.tsx` + router 里 `?? <Placeholder>` 兜底已是死代码(nav.ts 全部 `built:true`,无路由指向占位);`built`/`stage` 死字段可删。
- **大页拆分**:多页把展示逻辑 + 内联样式 + 本地小组件混在一个大 `*Page.tsx`(PricingAdmin 732 行,受 ≤600 行预算约束会超),重建时按"页壳 + 区块子组件 + 共享原语"分层。

> 一句话:**技术栈(React18+Vite5+TS+react-router6+vitest,157 个测试)、API 真相层、IA、设计 token 都是对的,值得当地基;删的是"每页各造轮子"的实现层,补的是缺失的组件原语层。** 是否真的一行代码不留地重写、还是保留 API 层与 token 只重做组件与页——这一步属页面级设计,是 Owner-gated,列在 §7 决策点等你拍。

## 4. 目标架构(对标 sub2,融合升级)

### 4.1 外壳与分权:双壳(HUAKAI 现有)vs 单壳三层(sub2)——推荐保留双壳

- **sub2 做法**:同一套 AppLayout,靠侧栏菜单 computed 过滤(adminNavItems / userNavItems / personalNavItems)区分角色,一套壳。
- **HUAKAI 现有做法**:显式双壳(用户门户 / 运营台),`/v1/auth/me` 的 `panel` 字段决定切壳,deny-by-default。
- **推荐:保留 HUAKAI 双壳,这比 sub2 单壳更适合本产品**(升级 delta,不是照抄)。理由:中转站的"终端客户"和"平台运营者"是两拨受众、两种心智——客户要极简自助(建 key、看用量、冲值),运营要密集操作台(号池、调度、计非)。双壳把两者物理隔开,客户永远看不到运营台的复杂度,运营台可以放心做密集。sub2 单壳靠菜单过滤,菜单一长两拨人都得滚。**分权仍抄 sub2 的三层收口**:路由 meta 守卫 + 菜单过滤 + auth store 判定共用同一真相源。授权边界永远在后端每个 admin 端点独立鉴权,前端切壳只为体验。

### 4.2 API 真相层(保留现有模式 + 抄 sub2 的桶导出)

- 保留现有 `apiGet`/`apiSend` + `tokenForPath` 智能注入 + single-flight 刷新(已经对)。
- **新增 sub2 式桶导出**:按域拆 API 模块(`api/accounts.ts`、`api/pricing.ts`…),再聚合成 `adminApi.<域>.<动作>` / `userApi.<域>.<动作>`,全部类型化入参/返回。这样后端能力与前端入口一一对应,可穷举核对 parity(§1.2)。
- 统一信封拆包 + 错误规整 + 401 刷新去重,视图零裸 fetch。

### 4.3 组件原语层(必建 —— 这是整个重建的核心交付)

在 `src/ui/` 补齐这批原语,全部引用 `tokens.css` 变量,把 66 页的自造弹窗与内联样式收敛上去:

| 原语 | 作用 | 消灭的重复 |
|---|---|---|
| `Modal` / `Drawer` | 统一弹窗/抽屉壳 | 16 处 `function Modal` |
| `Form` / `Field` / `Input` / `Select` / `Textarea` / `Switch` | 受控表单原语 | 61 处内联输入样式 + 多页 Field |
| `Button`(variant:primary/danger/ghost) | 统一按钮 | 各页 `hk-btn` class 拼装 |
| `ConfirmDialog`(带 danger 二次确认) | 危险操作确认 | `window.confirm`/`window.prompt` |
| `Toast` / `ToastProvider` | 全局反馈 | 页内局部 notice/error state |
| `Pagination` | 分页 | 各页手写 |
| `Tabs` | 页内分区(聚合复杂设置,对齐 sub2/new-api) | —— |
| `DataTable`(在现有 DataListTable 上强化) | 筛选/多选/行内动作/loading skeleton/移动卡片 | 运营页表格基座 |

### 4.4 运营页统一范式(每个运营域套同一模板)

```
筛选栏(状态/类型/分组过滤)
  → 批量工具条(新建 / 批量编辑 / 导出)
  → DataTable(列渲染 + 行内操作按钮)
     · 行内动作:编辑 / 删除 / 恢复 / 拨测 / 停调度 …
  → 写动作走独立 Modal 组件(CreateXModal / EditXModal / BulkEditXModal)
  → 危险/动潜操作走 ConfirmDialog(danger 二次确认,明示金额/影响)
  → 成功后 onSuccess 回刷列表
```

新增一个运营域 ≈ 复制这个范式改业务列与端点。**这是"好运维"的可维护性来源:一致、可预测、改一处受益全部。**

### 4.5 组件按域复用

`src/features/<域>/components/` 放该域业务组件(账号配额徽章、容量单元格、凭证构造器、渠道状态、Key 卡、收款套餐卡、用量图表),`src/ui/` 放跨域通用原语。业务组件小而专、复用度高、单测好写。

### 4.6 状态 / i18n / 测试

- **状态**:继续用现有轻量 `useSyncExternalStore` store(auth/me),够用不臃肿,不引 Redux。跨页共享/需持久化的才进 store,页面局部状态留组件内(抄 sub2 的克制)。
- **i18n**:现在是中文硬编码。若要 i18n 则按域拆 locale 文件、走 `t()`、路由 meta 挂 titleKey。**(是否上 i18n 属 Owner 决策,列 §7。)**
- **测试**:保留 vitest 纯函数抽取 + 变异友好模式;新增原语组件的组件级测试;`ui:guard` 防横向溢出继续跑。

## 5. IA 蓝图(把 28 个后端域全部归到菜单)

**用户门户壳(session,客户自助,4 组):**

- 更多:接入指引 / 在线调试台 / 媒体任务 / 可用渠道 / 信任验证 / 每日签到 / 推广返利

**运营台壳(admin,6 组):**

- 网关资源:模型服务 / 模型注册 / 渠道健康 / 上游账号 / 账号池 / 路由规则 / 流量控制 / 分组管理 / 厂商同步 / 上游目录 / 出口代理池 / TLS 指纹配置 / 渠道测试模板
- 用户与财务:用户管理 / 订单管理 / 订阅管理 / 定价设置 / 兑换码管理 / 用量与计非台账 / 退宽与抠费争议 / 分销管理
- 安全与审计:审计日志 / 风控总览 / 内容审核 / 凭证续期
