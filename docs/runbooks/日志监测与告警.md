# 日志、服务器监测与告警手册

## 1. 先确认三种状态

```text
/healthz                    进程是否存活
/readyz                     当前实例是否可以接流量
/v1/admin/system/health     各业务组件是否健康
```

`/v1/admin/system/health` 即使 HTTP 200，响应体仍可能标记 `unhealthy`；必须读取 JSON 状态和原因。

## 2. 运行日志

部署者入口：

```text
GET  /v1/admin/ops/runtime-logs
GET  /v1/admin/ops/runtime-logs/health
POST /v1/admin/ops/runtime-logs/cleanup
```

重点检查：

- 异常队列深度。
- `dropped` 和 `failed_batches`。
- 最近一次成功清理时间。
- 连续失败次数和失败表。
- `category`、`event_type`、`result`、`severity`、`error_class` 和恢复状态。

普通日志固定保留 30 天。手工 cleanup 也只能触发相同固定策略，不能输入任意日期或清空全部表。
资金账本、订单、退款、争议、幂等效果、恢复任务不属于普通日志。

## 3. 节点监测

生产默认启用服务器监测：

```text
HUAKAI_SERVER_MONITOR_ENABLED
HUAKAI_SERVER_MONITOR_NODE_ID
HUAKAI_SERVER_MONITOR_DISPLAY_NAME
HUAKAI_SERVER_MONITOR_INTERVAL
HUAKAI_SERVER_MONITOR_OFFLINE_AFTER
```

管理入口：

```text
GET /v1/admin/system/nodes
GET /v1/admin/system/nodes/{node_id}/history
```

多副本必须为每个实例配置唯一、稳定且不泄漏宿主信息的 `NODE_ID`。重复 ID 或首次采集写库失败
会阻止安全启动。节点离线时先判断是进程停止、数据库写入失败、采集权限变化，还是监测 worker 停止。

## 4. 告警

```text
/v1/admin/alert-rules
/v1/admin/alert-events
/v1/admin/alert-silences
```

处理顺序：

1. 找到 firing 事件和指标来源。
2. 识别影响租户、账号、池组、协议和钱路。
3. 只有确定是重复噪声时才临时 silence。
4. 修复根因后观察状态回落。
5. 人工标记解决时记录原因和操作者。

告警评估器默认开启；没有规则时循环为空操作。关闭评估器会让已配置规则静默失效，只能作为
短时应急动作，并要有恢复时间。

## 5. 告警风暴或日志丢弃

1. 不先扩大队列或无限保留日志。
2. 检查 PostgreSQL 延迟、连接池、磁盘、批写错误和重复事件源。
3. 按 `event_type` 聚合，确认是否一个 worker 或账号状态循环抖动。
4. 必要时先暂停产生副作用的具体 worker，而不是关闭全部日志。
5. 恢复后确认 dropped 不再增长、失败批次清零、30 天清理继续运行。
