# 账号池、凭据与出站恢复手册

## 1. 诊断顺序

```text
用户 Key
 -> 模型与分组政策
 -> 模型到池组 binding
 -> 池内候选
 -> 账号健康与额度
 -> 凭据版本与到期
 -> 代理与 TLS profile
 -> Dispatcher 与上游响应
 -> 计费、配额和恢复
```

不要一看到 401 就强制账号 active，也不要一看到 429 就删除重建账号。

## 2. 动态恢复建议

先查询：

```text
GET /v1/admin/provider-accounts/{id}/recovery-actions
```

响应会根据当前状态给出可执行 method/path。典型动作包括：

- 启用账号。
- 清除限流。
- 完整恢复状态。
- 轮转或重新认证凭据。
- 恢复渠道。

严格使用当前响应提供的动作；`revoked` 不能靠“清限流”恢复，凭据被拒绝也不能只强制 active。

## 3. 常见错误

| 现象 | 先查 | 处置 |
| --- | --- | --- |
| 401/403 | 凭据版本、刷新状态、上游身份、账号模式 | 刷新、重新认证或人工消歧；不要重放旧 OAuth flow |
| 429 | `Retry-After`、额度窗口、账号级限流和池内其他候选 | 等待 reset、清理已过期限流或切换候选 |
| credits exhausted | 厂商重置时间和配额事实新鲜度 | 按重置时间冷却；没有时间时使用厂商合同的保守回退 |
| 池无候选 | 租户、池、模型、协议、能力、凭据、过期和健康 SQL 条件 | 修真实阻断，禁止绕过租户或分组门 |
| 模型列表空 | 账号模式、模型发现端点、凭据和 Dispatcher | 先跑账号能力检查，不直接改模型目录 |
| proxy 错误 | 绑定、目标、SSRF 策略、代理健康 | 质检代理并按明确 fallback 合同恢复 |
| Sidecar 不就绪 | Unix Socket、Sidecar 进程、profile | mimicry 账号 fail-closed；标准 TLS 流量不应长期被全局阻断 |

## 4. 凭据刷新

凭据 worker 使用账号级租约，默认周期扫描。处理时确认：

- 当前版本没有被并发刷新覆盖。
- 新凭据先加密落库，再退出旧版本。
- OAuth flow 与租户、操作者、模式绑定且未重放。
- 静态 Key 不假装能够自动轮转，只做过期和健康告警。
- 刷新后重新发现模型、订阅和额度，不只改 access token。

## 5. auth 降级车道:鉴权失败的退避与硬禁

请求时鉴权失败(401、撤销/坏 Key 铁证、Grok 400-auth)不写健康分,而是进入 auth 降级车道:
每个退避窗口至多升一次 strike,封顶指数退避(默认 30s 起、30 分钟封顶);铁证类连续 3 次或
凭据刷新拿到永久失效即硬禁;普通 401 永不硬禁。车道真相在 `provider_account_auth_cooldowns`
表,跨副本共享、重启后仍在:选号候选查询直接排除硬禁与未过期退避(`disable_cooling` 只豁免
软退避),各网关副本的进程镜像每 5 秒从真相表重载。

诊断与处置:

- 查看:`GET /admin/v1/provider-accounts/{id}/health` 的 `auth_cooldown` 轴(`persistence=postgres`
  表示读的是跨副本真相;`process_local` 表示写库失败、只有该副本在本地保护,同时会有
  `auth cooldown lane persistence failed` 日志)。按池汇总看 `GET /admin/v1/pools/health-summary`
  的 `auth_cooldown_accounts`。
- 自动恢复:软退避到期回池,一次成功请求清除软退避(strike 归零);成功请求**不解除硬禁**——
  在途请求的迟到成功不能复活刚被确认永久失效的账号。请求失败带来的更高凭据版本会重置 strike;
  显式轮换凭据(导入更新 / 重新授权)在同一事务内清空该账号的车道状态,新凭据立即回到候选。
- 人工恢复:硬禁账号只能由 ForceActive / ManualResume 或显式轮换解除。ForceActive / ManualResume
  把真相行清成带 `resumed_at` 墓碑的无状态行,所有副本在一个重载周期内放行;某副本因写库失败仍持有的
  旧本地硬禁在补写时会被墓碑拒绝并丢弃,不会撤销这次人工恢复;resume 之后新到达的永久失效仍会重新
  硬禁(说明凭据确实已失效,应重新授权)。不要为了绕过硬禁去开 `disable_cooling`,它不豁免硬禁。
  `auth_cooldown.failure_class / last_escalated_at / hard_disabled_at` 说明为什么、什么时候被移出。
- 已知有界竞态:副本 A 刚为账号写入软退避、副本 B 同一时刻用它成功,B 的成功不会删除 A 写的行
 (B 的镜像尚不知道该行,不为每次成功请求付一条删除语句),该账号保留到软退避自然过期,最长一个
  退避窗口;硬禁不受影响。
- resume 时若真相写入失败只记 `auth cooldown lane persistence failed` 日志,候选查询继续排除该账号,
  请重试 resume;诊断接口显示 `persistence=process_local` 与 `replica_id` 表示该状态只由那个副本持有
 (写库失败后的兜底),下一轮重载会自动补写回真相表(或被更晚的 resume 墓碑 / 凭据轮换拒绝后丢弃),
  可稍后重查或等一个重载周期(默认 5 秒)。
- 时钟要求:resume 墓碑与失败证据按时间先后比较(墓碑取数据库时钟,证据取产生失败的副本时钟),
  各网关副本必须 NTP 同步;偏差超过"失败到 resume 的间隔"时,某副本的旧本地硬禁可能压过 resume,
  表现为 resume 后数秒内再次硬禁,重做一次 resume 即可。
- 紧急逃生阀:`HUAKAI_AUTH_COOLDOWN_ENABLED=false` 关闭整条车道(退回"鉴权失败不移出选号"),
  只在车道本身误伤大量账号时使用,处理完立即恢复默认。注意:关闭后不再写入新状态,resume 也不再
  清理真相行,但候选查询仍按真相表排除存量硬禁与未过期软退避;要立即放行存量账号,先在车道开启
  时对其 resume / 轮换凭据,或由 DBA 清空 `provider_account_auth_cooldowns` 中对应行。

## 6. 按请求 ID 追链路

用户或租户报告某次请求异常时,先拿请求标识——HUAKAI 有两把:响应头 `X-Request-Id` / 收据里的网关
HTTP 请求标识,以及账本 claim 的逻辑标识(客户端 `Idempotency-Key`,没有则由网关生成);两把任一可查,
响应 `request.logical_request_id` / `request.http_request_ids` 同时回传。用
`GET /admin/v1/requests/{request_id}/trace`(租户管理员锁本租户;部署者可省略 `tenant_id` 跨租户查;
含一个斜杠的幂等键直接放在路径里)拿到时间线:头部(入口族、模型、池、状态、预估/实际费用)→ 每次已结算
尝试(账号代号、渠道、结束分类、用量与费用分项、时间点、选号摘要)→ 账本事件(提交/中止/对账追加)→
账号级审计(健康转换、限流、凭据刷新;路由审计来源为预留,当前网关无写入者)→ 信任链收据与用户费用
收据;失败尝试与已中止请求带九类粗分类 `failure_category`(用户也可见),原始分类码只给运营侧。看 `coverage`:
`attempts_detail=partial` 表示有拿到账号前就中止的尝试只留了账本事件、账号未知;`final_only` +
`detail_retention=pending` 表示刚结算、用量还在异步落盘;`expired` 表示用量明细已不在(过保留期或落盘
进了死信),只剩账本与收据;`unknown_account_attempts` 是账号未知的尝试数;`multiple_claims_for_id`
表示同一标识命中多条账本行(取最新)。最终用户走 `GET /v1/me/requests/{id}/trace`,只看模型、池、状态、
用量与费用;凡无权、不存在、过期无账本一律同一 404,不要据此推断请求是否存在。点查依赖迁移 0239 的
标识索引(在事务内普通建索引,`billing_ledger_claims` / `billing_events` 为热表,升级请放在低峰)。在途
(尚未结算)的请求还没有账本事件,用逻辑标识查会看不到审计半边,请用响应头里的 HTTP 请求标识查。用户
面 `end_class` 是网关结束分类(如 `upstream_error_5xx`),与 `failure_category` 一起可见;更细的中止分类码
`terminated_reason` / `aborted_reason` 只给运营侧。

## 7. 账号导入冲突

稳定上游身份匹配到零条时创建，一条时按版本和确认合同更新，多条时必须返回冲突并人工消歧。
禁止取第一条自动覆盖。迁移包、CRS 和批量导入允许部分成功，但每个账号必须独立事务，并返回
成功、失败和冲突明细。

## 8. 恢复后验证

1. 账号详情、列表和健康接口使用相同投影。
2. 额度事实新鲜，未知值没有被显示成满额。
3. 账号重新进入正确租户和池组候选。
4. 使用测试 Key 跑最小成本完整请求。
5. 余额、配额、usage、账号健康和日志状态均收敛。
