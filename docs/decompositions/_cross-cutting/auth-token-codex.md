## 3. High-Level Finding

- Sub2API has a shared OAuth refresh coordinator that wraps provider refreshers with local mutexes, optional distributed refresh locks, DB rereads, secondary "still needs refresh" checks, token-version stamping, and invalid-grant race recovery (`backend/internal/service/oauth_refresh_api.go:21`, `backend/internal/service/oauth_refresh_api.go:74`, `backend/internal/service/oauth_refresh_api.go:76`, `backend/internal/service/oauth_refresh_api.go:83`, `backend/internal/service/oauth_refresh_api.go:99`, `backend/internal/service/oauth_refresh_api.go:111`, `backend/internal/service/oauth_refresh_api.go:118`, `backend/internal/service/oauth_refresh_api.go:138`, `backend/internal/service/oauth_refresh_api.go:171`).
- Sub2API still keeps provider-specific request-path token providers and provider-specific refreshers, so common locking exists but the provider behavior is not a single shared base class (`backend/internal/service/token_refresh_service.go:60`, `backend/internal/service/token_refresh_service.go:66`, `backend/internal/service/token_refresh_service.go:73`, `backend/internal/service/claude_token_provider.go:20`, `backend/internal/service/openai_token_provider.go:78`, `backend/internal/service/gemini_token_provider.go:18`, `backend/internal/service/antigravity_token_provider.go:26`).
- OpenAI and Claude are fail-open on request-path refresh errors by continuing with existing access tokens, while Gemini and Antigravity fail the request-path token fetch on refresh error (`backend/internal/service/refresh_policy.go:25`, `backend/internal/service/refresh_policy.go:33`, `backend/internal/service/refresh_policy.go:41`, `backend/internal/service/refresh_policy.go:49`).
- Antigravity has the strictest request-path guard: it wraps request-path refresh in an 8-second timeout and marks the account temporarily unschedulable on refresh failure (`backend/internal/service/antigravity_token_provider.go:14`, `backend/internal/service/antigravity_token_provider.go:20`, `backend/internal/service/antigravity_token_provider.go:100`, `backend/internal/service/antigravity_token_provider.go:107`, `backend/internal/service/antigravity_token_provider.go:198`).
- Sub2API's token persistence is not DB-CAS based: the helper clones credentials and calls `UpdateCredentials`, and the repository update is a direct account update by id with `SetCredentials` and `Save` (`backend/internal/service/account_credentials_persistence.go:9`, `backend/internal/service/account_credentials_persistence.go:14`, `backend/internal/service/account_credentials_persistence.go:16`, `backend/internal/repository/account_repo.go:407`, `backend/internal/repository/account_repo.go:408`, `backend/internal/repository/account_repo.go:409`, `backend/internal/repository/account_repo.go:410`).

## 5. Shared Refresh Coordinator

- The shared coordinator derives a cache key from the provider executor, then takes a process-local mutex keyed by that cache key (`backend/internal/service/oauth_refresh_api.go:74`, `backend/internal/service/oauth_refresh_api.go:76`, `backend/internal/service/oauth_refresh_api.go:77`, `backend/internal/service/oauth_refresh_api.go:78`).
- When a token cache is available, the shared coordinator attempts a distributed refresh lock with a default 60-second TTL (`backend/internal/service/oauth_refresh_api.go:21`, `backend/internal/service/oauth_refresh_api.go:39`, `backend/internal/service/oauth_refresh_api.go:40`, `backend/internal/service/oauth_refresh_api.go:83`).
- If distributed lock acquisition errors, the shared coordinator logs a degraded-lock warning and continues under the process-local mutex (`backend/internal/service/oauth_refresh_api.go:83`, `backend/internal/service/oauth_refresh_api.go:84`, `backend/internal/service/oauth_refresh_api.go:85`, `backend/internal/service/oauth_refresh_api.go:94`).
- If another worker holds the distributed lock, the shared coordinator returns `LockHeld` without refreshing (`backend/internal/service/oauth_refresh_api.go:90`, `backend/internal/service/oauth_refresh_api.go:92`).
- After lock handling, the shared coordinator rereads the account from DB before calling the provider refresher (`backend/internal/service/oauth_refresh_api.go:99`, `backend/internal/service/oauth_refresh_api.go:111`, `backend/internal/service/oauth_refresh_api.go:118`).
- After successful provider refresh, the shared coordinator stamps `_token_version` and persists the new credential map (`backend/internal/service/oauth_refresh_api.go:136`, `backend/internal/service/oauth_refresh_api.go:138`, `backend/internal/service/oauth_refresh_api.go:139`).
- If a provider refresh returns an invalid-grant-style error, the shared coordinator rereads the account and treats the result as recovered if the DB refresh token differs from the token just used (`backend/internal/service/oauth_refresh_api.go:122`, `backend/internal/service/oauth_refresh_api.go:123`, `backend/internal/service/oauth_refresh_api.go:171`, `backend/internal/service/oauth_refresh_api.go:172`, `backend/internal/service/oauth_refresh_api.go:176`).

## 6. Provider Duplication and Shared Pieces

- Sub2API has a `TokenRefresher` interface with provider-specific `CanRefresh`, `NeedsRefresh`, and `Refresh` methods (`backend/internal/service/token_refresher.go:9`, `backend/internal/service/token_refresher.go:11`, `backend/internal/service/token_refresher.go:13`, `backend/internal/service/token_refresher.go:17`).

- The background service also registers matching OAuth refresh executors in a parallel slice, which creates an implicit index dependency between refreshers and executors (`backend/internal/service/token_refresh_service.go:73`, `backend/internal/service/token_refresh_service.go:74`, `backend/internal/service/token_refresh_service.go:75`, `backend/internal/service/token_refresh_service.go:76`, `backend/internal/service/token_refresh_service.go:77`).
- Request-path access-token retrieval remains provider-specific: Claude, OpenAI, Gemini, and Antigravity each have their own provider object and cache / refresh handling (`backend/internal/service/claude_token_provider.go:20`, `backend/internal/service/openai_token_provider.go:78`, `backend/internal/service/gemini_token_provider.go:18`, `backend/internal/service/antigravity_token_provider.go:26`).
- Repository-layer OAuth clients are also hand-rolled by provider: OpenAI posts URL-encoded forms to its token URL, Claude posts JSON to its token URL, and Gemini posts URL-encoded forms with OAuth-type-specific client configuration (`backend/internal/repository/openai_oauth_service.go:89`, `backend/internal/repository/openai_oauth_service.go:102`, `backend/internal/repository/claude_oauth_service.go:239`, `backend/internal/repository/claude_oauth_service.go:254`, `backend/internal/repository/gemini_oauth_client.go:83`, `backend/internal/repository/gemini_oauth_client.go:110`).

HUAKAI-DESIGN: Use a provider-neutral refresh state machine plus provider adapters. Keep adapter differences explicit, but avoid a parallel-slice registry because the ordering dependency in `refreshers` and `executors` can be broken by future edits (`backend/internal/service/token_refresh_service.go:66`, `backend/internal/service/token_refresh_service.go:73`).

## 7. Refresh Token Rotation Semantics

- Claude builds new credentials with `refresh_token` only when the refresh response contains one (`backend/internal/service/oauth_refresh_api.go:210`, `backend/internal/service/oauth_refresh_api.go:217`, `backend/internal/service/oauth_refresh_api.go:218`).
- OpenAI builds new credentials with `refresh_token` only when the refresh response contains one (`backend/internal/service/openai_oauth_service.go:332`, `backend/internal/service/openai_oauth_service.go:339`, `backend/internal/service/openai_oauth_service.go:341`).
- Gemini builds new credentials with `refresh_token` only when the refresh response contains one (`backend/internal/service/gemini_oauth_service.go:879`, `backend/internal/service/gemini_oauth_service.go:884`, `backend/internal/service/gemini_oauth_service.go:885`).
- Antigravity builds new credentials with `refresh_token` only when the refresh response contains one (`backend/internal/service/antigravity_oauth_service.go:459`, `backend/internal/service/antigravity_oauth_service.go:464`, `backend/internal/service/antigravity_oauth_service.go:465`).
- The merge helper copies old credential keys only when the new credential map lacks that key, so an upstream-rotated refresh token replaces the old token while a missing refresh token preserves the existing value (`backend/internal/service/oauth_refresh_api.go:182`, `backend/internal/service/oauth_refresh_api.go:186`, `backend/internal/service/oauth_refresh_api.go:187`, `backend/internal/service/oauth_refresh_api.go:188`).
- Sub2API does not keep a previous-refresh-token grace slot in the credential map; the inspected credential builders emit only the current token fields and the merge helper preserves old values only when the provider omits a field (`backend/internal/service/openai_oauth_service.go:336`, `backend/internal/service/openai_oauth_service.go:341`, `backend/internal/service/oauth_refresh_api.go:186`, `backend/internal/service/oauth_refresh_api.go:188`).
- Race recovery depends on DB reread detecting that `refresh_token` changed after an invalid-grant response (`backend/internal/service/oauth_refresh_api.go:122`, `backend/internal/service/oauth_refresh_api.go:171`, `backend/internal/service/oauth_refresh_api.go:172`, `backend/internal/service/oauth_refresh_api.go:176`).

HUAKAI-DESIGN: Preserve "only replace refresh token when upstream returns a non-empty replacement", but add an encrypted previous-token tombstone or audit field with a short retention window only if legal/security review approves. The reason is operational diagnosis, not replay.

## 8. Token Persistence Atomicity

- The persistence helper mutates the in-memory account copy before repository persistence by assigning a cloned credentials map (`backend/internal/service/account_credentials_persistence.go:9`, `backend/internal/service/account_credentials_persistence.go:14`, `backend/internal/service/account_credentials_persistence.go:21`, `backend/internal/service/account_credentials_persistence.go:25`).
- If the repository implements `UpdateCredentials`, the helper calls that narrower update path; otherwise it falls back to the full account update path (`backend/internal/service/account_credentials_persistence.go:15`, `backend/internal/service/account_credentials_persistence.go:16`, `backend/internal/service/account_credentials_persistence.go:18`).
- The repository `UpdateCredentials` path directly updates the account row by id and sets the credentials JSON, with no visible version predicate in that method (`backend/internal/repository/account_repo.go:407`, `backend/internal/repository/account_repo.go:408`, `backend/internal/repository/account_repo.go:409`, `backend/internal/repository/account_repo.go:410`).
- The DB reread before refresh uses `GetByID`, whose inspected path queries by id and returns the account without a `FOR UPDATE` lock in that method body (`backend/internal/repository/account_repo.go:133`, `backend/internal/repository/account_repo.go:134`, `backend/internal/repository/account_repo.go:146`).
- The main race mitigations are the local mutex, distributed refresh lock, DB reread, secondary freshness check, `_token_version`, and invalid-grant reread recovery; they are not a database compare-and-swap commit (`backend/internal/service/oauth_refresh_api.go:76`, `backend/internal/service/oauth_refresh_api.go:83`, `backend/internal/service/oauth_refresh_api.go:99`, `backend/internal/service/oauth_refresh_api.go:111`, `backend/internal/service/oauth_refresh_api.go:138`, `backend/internal/service/oauth_refresh_api.go:171`).
- Race window: if the distributed lock is unavailable or degraded, two processes can both refresh under only process-local mutexes, and the later DB write can overwrite the earlier credential map because the inspected persistence method lacks a version predicate (`backend/internal/service/oauth_refresh_api.go:83`, `backend/internal/service/oauth_refresh_api.go:85`, `backend/internal/repository/account_repo.go:407`, `backend/internal/repository/account_repo.go:410`).

HUAKAI-DESIGN: Upgrade credential persistence to a DB transaction with row lock or CAS on credential version. A safe shape is: reread row in transaction, verify current credential version / refresh-token fingerprint, write new encrypted credential set, append audit event, invalidate cache, and publish scheduler update atomically.

### 8.1 Atomicity Race Window Simulation

- Worker A and worker B can both enter the shared refresh coordinator for the same account if distributed locking is degraded or if they run in separate processes and lock state is unavailable; the shared coordinator explicitly continues after lock acquisition errors under only a local mutex (`backend/internal/service/oauth_refresh_api.go:83`, `backend/internal/service/oauth_refresh_api.go:85`, `backend/internal/service/oauth_refresh_api.go:94`).
- Both workers reread the account before refresh, but the reread is a normal repository `GetByID` query rather than a transactional row lock in the inspected method (`backend/internal/service/oauth_refresh_api.go:109`, `backend/internal/repository/account_repo.go:147`, `backend/internal/repository/account_repo.go:148`).

## 20. HUAKAI Target Contract

- HUAKAI-DESIGN: F-AUTH-001 token refresh MUST be provider-side credential management only; it must not affect user-facing JWT auth.
- HUAKAI-DESIGN: Every Provider Account OAuth credential set MUST carry an encrypted current refresh token, encrypted access token, expiry, provider id, credential version, refresh status, last refresh attempt, last refresh error class, and audit pointers.
- HUAKAI-DESIGN: Every refresh attempt MUST use a provider adapter that returns a structured result: refreshed, skipped, lock-held, retryable failure, non-retryable failure, token-rotated, access-token-only, expiry, and sanitized operator message.
- HUAKAI-DESIGN: Request path MAY refresh only inside bounded latency budgets. Background refresh MUST handle normal refresh load, and request path MUST fail over or use existing token according to explicit provider policy.
- HUAKAI-DESIGN: All credential writes MUST be atomic with credential version checks, cache invalidation intent, and audit event generation.
- HUAKAI-DESIGN: All OAuth errors MUST pass through a sanitizer before logs, temp-unsched reasons, account status, Admin Ops UI, or client responses.
- HUAKAI-DESIGN: Provider-wide storm controls MUST include concurrency caps, randomized early refresh windows, endpoint-level circuit state, and per-provider metrics.
- HUAKAI-DESIGN: Claude Code compatibility behavior MUST be feature-flagged, auditable, and reviewable as a compatibility adapter.
