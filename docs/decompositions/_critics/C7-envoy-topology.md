## A. Coverage gaps (specifier likely missed these)
- C-001: Generated-resource ownership is a live ops hazard, not just CRD translation. The upstream API says an AI Route generates a Gateway HTTP route and a per-namespace host-rewrite filter, both in the AI Route namespace, and says operators may patch generated resources with Envoy Gateway policy APIs. HUAKAI must specify reconciliation conflict behavior when an operator patch, route edit, and controller resync race against each other; otherwise an implementer may treat generated routes as static output.
- C-002: Cross-namespace backend references need a tenant authorization model, not only a ReferenceGrant checkbox. Upstream allows AI Route backend references to cross namespaces with a referent-side grant. HUAKAI DR-001 needs this decomposed into tenant boundary checks, grant ownership, audit events, and denial status; Kubernetes namespace consent is not enough for SaaS tenant isolation.
- C-003: InferencePool backend support is structurally narrower than normal backends. Upstream documents that an AI Route rule may use only one InferencePool backend, must not mix it with AIServiceBackend references in the same rule, and ignores model override, header mutation, body mutation, weight, and priority for InferencePool. A spec that simply says "AI Route can route to InferencePool" will overpromise weighted rollout, mutation, and fallback behavior.
- C-004: Model-based routing depends on body parsing and an internal synthetic route header. Upstream exposes `x-ai-eg-model` as available in rule matching after the gateway extracts model from request content. HUAKAI must cover malformed JSON, unsupported endpoint bodies, streaming bodies, body size limits, missing model, and tenant-supplied header spoofing. This is a fail-closed routing decision, not a normal HTTP header match.
- C-005: Default timeout behavior is AI-specific and easy to miss. Upstream says an unset request timeout becomes 60s instead of Envoy Gateway's 15s, with streaming requiring longer values. HUAKAI must define edition defaults, operator override, streaming idle timeout, and accounting timeout separately; otherwise long-running requests can either be killed early or consume tenant quota indefinitely.
- C-006: Rate limiting is split across dynamic metadata and external Gateway policy. Upstream captures token costs into Envoy dynamic metadata and demonstrates BackendTrafficPolicy buckets keyed by a tenant header. HUAKAI needs an explicit trust boundary for tenant identity, signed/account-derived tenant context, and PostgreSQL-backed usage reconciliation; a client-provided tenant header is unacceptable as the billing or quota key.
- C-007: GatewayConfig sharing creates blast-radius coupling. Upstream allows multiple Gateways to reference one GatewayConfig and gives GatewayConfig environment variables precedence over controller globals. HUAKAI needs change rollout, audit, dry-run, and edition scoping so one shared config update cannot silently change unrelated tenants' external processor resources or telemetry settings.
- C-008: Status semantics are too weak for production recovery. Upstream API status conditions are described as at most one Accepted/NotAccepted condition for AI Route, BackendSecurityPolicy, and GatewayConfig. HUAKAI needs structured per-parent, per-backend, per-policy, and per-tenant condition reasons; a single accepted flag cannot drive admin repair workflows.
- C-009: Two-tier topology is aspirational in README but not a full product contract. The README describes Tier One for auth/top routing/global rate limit and Tier Two for self-hosted model access with endpoint picker. HUAKAI must decompose routing ownership between outer Gateway, inner Gateway, Account Hub, quota, provider credentials, and Admin Ops; upstream docs do not define tenant onboarding, per-account policy propagation, or cross-tier rollback.
- C-010: Standalone/local and Kubernetes modes leak into the same mental model. Release notes and docs mix CRD-controlled Gateway behavior with CLI/standalone capabilities. HUAKAI dual editions need an explicit portability contract: which AI Route capabilities exist in Personal Edition without Kubernetes, and which require SaaS control-plane services.

## B. Flattering errors (looks simple, isn't)
- F-001: "Create an AI Route and route by model" hides request body dependency. The guide says no manual header is needed because the gateway extracts model names, while the API describes matching on `x-ai-eg-model`. That implies a preprocessing path before route selection, with security implications for spoofed headers and parsing failures.
- F-002: "Inference optimization" hides an extra control plane. The InferencePool guide installs Gateway API Inference Extension CRDs, a controller, endpoint picker services, an EndpointPickerConfig, pod-read RBAC, and token/subject access review RBAC. HUAKAI should treat this as an optional integration module with health and readiness gates, not as a simple backend type.
- F-003: "Fallback" is not a field-level guarantee. Upstream says AIServiceBackend fallback can be achieved by combining multiple backends with Envoy Gateway policies, while InferencePool fallback is delegated to the endpoint picker. HUAKAI must define fallback semantics in its own domain: provider failover, tenant quota exhaustion, unhealthy model pool, billing continuity, and audit record ordering.
- F-004: "Gateway-scoped configuration" hides precedence and tenancy questions. GatewayConfig env values override global controller flags and can be shared by multiple Gateways. HUAKAI must specify whether per-tenant config can override platform config and which keys are forbidden for tenant-level control.
- F-005: "Unified AI API" hides version churn. Release notes show prior fields were deprecated or removed across 0.2, 0.3, 0.4, and 0.5: targetRefs to parentRefs, schema removal from route, BackendSecurityPolicy attachment changes, endpoint prefix changes, and external processor resource config migration. HUAKAI implementer-lane needs an explicit compatibility and migration section, not a snapshot of one upstream version.

## C. Upstream's own drift
- D-001: README claims Tier One handles authentication, top-level routing, and global rate limiting, but the API docs place backend authentication in BackendSecurityPolicy, token cost capture in AI Route/GatewayConfig dynamic metadata, and rate-limit enforcement in Envoy Gateway BackendTrafficPolicy. The docs describe one topology, while the implementation model distributes responsibility across several resources.
- D-002: API reference says AI Route generates a same-name HTTPRoute and an HTTPRouteFilter, but also calls that an implementation detail subject to change. This is a direct drift between documented observable resources and stability expectations.
- D-003: The docs claim v1beta1 is preferred for new resources, while latest API still documents v1alpha1 resources including QuotaPolicy and MCPRoute alongside v1beta1 core routing. A specifier may accidentally mix maturity levels unless the decomp marks alpha-only capabilities separately.
- D-004: Release notes describe migration away from old route schema and targetRef patterns, while older API reference versions still show those fields as required or deprecated. HUAKAI must not cite a single version page as canonical without noting version-specific behavior.
- D-005: The InferencePool guide says mixed backends can be combined "in the same route based on model name", but the API says an individual rule cannot mix InferencePool and AIServiceBackend references. The valid pattern is multiple rules under one AI Route, not mixed backend references inside one rule.

## D. Things HUAKAI should NOT copy
- N-001: Do not copy tenant identity from request headers into quota or billing keys. Upstream examples use a distinct tenant header for token buckets. HUAKAI should derive tenant/account/channel identity from authenticated Account Hub context and persist usage in PostgreSQL.
- N-002: Do not copy the "generated HTTPRoute is patchable reference output" operating model without ownership rules. HUAKAI should expose first-class policy APIs or validated overrides, because patching generated data-plane resources creates drift and support ambiguity.
- N-003: Do not copy single-condition status. HUAKAI Admin Ops needs structured, queryable health per Gateway, route rule, backend, credential policy, quota policy, tenant, and edition.
- N-004: Do not copy shared GatewayConfig precedence as-is. HUAKAI should gate mutable runtime/env/resource settings by edition and tenant ownership, with audit and rollback.
- N-005: Do not copy the InferencePool RBAC shape blindly. The guide grants endpoint picker components pod reads plus authentication and authorization review creation. HUAKAI should minimize cluster privileges, isolate per tenant or pool, and surface RBAC failures as actionable ops events.
- N-006: Do not copy implicit model-header injection as a public contract. HUAKAI should model routing keys as internal request attributes with explicit anti-spoofing behavior and parser-failure outcomes.
- N-007: Do not copy version churn into HUAKAI's public contract. HUAKAI should publish stable OpenAPI/admin contracts and keep Kubernetes-style CRD compatibility behind adapters or plugins.
- N-008: Do not copy Kubernetes namespace as the product tenancy primitive. HUAKAI DR-001 requires tenant_id from day 1; namespace may be a deployment isolation mechanism, not the authority for account isolation.

## E. Smells found
- S-001: Single point of failure - the InferencePool guide's custom endpoint picker Deployment is shown with one replica, while it is in the routing path for model-pool selection.
- S-002: Hidden global state - GatewayConfig can be shared across multiple Gateways, and its env vars override controller globals; the effective runtime config is spread across controller flags plus referenced resources.
- S-003: Magic constants without operator-safe decomposition - default AI request timeout is 60s, sample endpoint picker ports are fixed at 9002/9003/9090, and processing mode defaults to duplex. HUAKAI needs documented defaults per edition and override constraints.
- S-004: Fail-open risk - InferencePool annotation `allow-mode-override: true` permits the external processor to override processing mode. HUAKAI should default fail-closed for body processing and require privileged operator approval for overrides.
- S-005: Tenant data leakage potential - cross-namespace backend references and examples using client-visible model names can expose or select backends across administrative boundaries if grants, model catalog visibility, and route matches are not tenant-scoped.
- S-006: Inconsistent error taxonomy - upstream status is Accepted/NotAccepted while runtime failures can come from parser failure, ReferenceGrant denial, endpoint picker unready, generated route conflict, credential policy conflict, or external processor config mismatch. HUAKAI needs normalized reasons.
- S-007: Operational recovery gap - generated resource patching, endpoint picker deployment readiness, Envoy Gateway restart requirements, and CRD installation order appear in docs, but there is no unified recovery workflow.

## F. Synthesis recommendations
- Top-3 things specifier MUST address before this decomp can be cited by implementer-lane: define fail-closed model extraction and anti-spoofing behavior; split AIServiceBackend and InferencePool semantics including unsupported mutation/weight/priority/fallback fields; document generated-resource ownership, reconciliation, status reasons, and operator override behavior.
- Top-3 HUAKAI-specific divergences this decomp must call out: tenant/account identity must come from HUAKAI auth context and PostgreSQL-backed Account Hub, not headers or namespaces; GatewayConfig and policy overrides need edition-aware audit/rollback/approval; InferencePool/EPP must be a pluginized optional module with HA, RBAC minimization, and explicit health gates.
