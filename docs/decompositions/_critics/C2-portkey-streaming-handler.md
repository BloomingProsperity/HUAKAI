## A. Coverage gaps (specifier likely missed these)
- C-001: Streaming "success" is not just provider HTTP 200. The response dispatcher treats both 200 and 246 as success for stream transformation, while the hook layer can rewrite a streaming response with failed non-denying checks to 246 and pass the body through. HUAKAI must specify whether a tenant-visible SSE stream with policy failures remains consumable, is metered as success, and is eligible for fallback. Evidence: response dispatch defines success as `[200, 246]` and enters streaming mode for those statuses; hook post-processing rewrites failed streaming checks from 200 to 246 while keeping the response body (`responseHandlers.ts` lines 883-1001 and 1228-1255 in GitHub view).
- C-002: Output guardrail denial is structurally weak for live SSE because the post-response hook path receives no completed JSON payload for streams. For streaming responses it can only mark a failed check status and reuse the live body; it cannot reliably stop already-forwarded unsafe chunks. HUAKAI must separate pre-stream checks, inline chunk checks, terminal checks, and operator policy for fail-closed cancellation.
- C-003: Stream timeout behavior is under-specified. The request retry layer documents request-level abort behavior, but the streaming reader path is a separate lifecycle after the provider response is accepted. A stalled provider stream after headers can hang unless the forwarder has a per-chunk idle timeout, heartbeat policy, and cancellation propagation. Evidence: the source index places text stream reading at `streamHandler.ts` lines 139-209 and retry timeout support at `retryHandler.ts` lines 1-50/65-220, so timeout and stream-drain concerns are separate source paths.
- C-004: Fallback/retry semantics after partial SSE emission are missing. Once HUAKAI has sent the first tenant chunk, fallback cannot replay transparently without duplicate content, bad usage accounting, and inconsistent trace state. The upstream routing/retry docs are request-level; the streaming dispatch returns a live body and no JSON result for the rest of the lifecycle.
- C-005: Cache-hit streaming is a different product behavior from live provider streaming. The response dispatcher converts cached JSON to SSE for streaming clients, but that path has different pacing, headers, hook timing, chunk IDs, and termination behavior than provider-native SSE. HUAKAI must specify exact parity rules for cache-hit stream reconstruction and mark any differences in trace/audit output.
- C-006: Backpressure and client disconnect are likely glossed over. A correct forwarder must cancel the upstream reader when the tenant disconnects, stop metering at a defensible boundary, close audit spans, and free buffers. The upstream behavior exposed in the source-indexed stream reader is chunk-loop forwarding; the decomposition must require disconnect and cancellation tests.
- C-007: AWS-style binary event streams are not just "SSE." The upstream has a separate binary stream reader for Bedrock-style events and a text stream reader for delimiter-based streams. HUAKAI must model this as provider stream normalization, not one generic SSE proxy. Evidence: source index places AWS binary stream reading at `streamHandler.ts` lines 61-137 and text stream reading at lines 139-209.
- C-008: Streaming observability is split from non-streaming observability. The response dispatcher returns `responseJson: null` for streaming, while non-streaming returns parsed response JSON and original JSON. HUAKAI's logs, billing, policy decisions, and replay tooling need a stream accumulator or explicit "stream has no terminal body" contract.

## B. Flattering errors (looks simple, isn't)
- F-001: "Forward SSE chunks" hides protocol normalization. The upstream has provider-specific split patterns, transformation functions, JSON-to-stream conversion for cache hits, and a separate AWS binary parser. HUAKAI should not let implementer-lane reduce this to `pipe(provider.body, client.body)`.
- F-002: "Guardrails work with streaming" is a flattering read. In the visible source path, streaming can be status-marked after hook evaluation but the body is still reused; chunk-level fail-closed enforcement is not proven by the upstream source path.
- F-003: "Request timeout" looks like it covers streaming, but it primarily covers the provider fetch attempt. A long-lived stream needs first-byte timeout, idle timeout, max stream duration, max bytes/chunks, and client disconnect cleanup.
- F-004: "OpenAI-compatible streaming" is not one format. Responses API docs promise provider-agnostic semantic events, while the gateway source also supports chat/completion chunk streams and cached JSON stream synthesis. HUAKAI needs per-route event contracts, not a single streaming handler spec.
- F-005: "Cache saves cost for streams" hides audit and billing complexity. A cached JSON response streamed later must not be counted as fresh provider completion, but must still be tenant-metered according to HUAKAI policy and traceable as cache-origin output.

## C. Upstream's own drift
- D-001: Docs market all gateway features as working with streaming provider adapters, but the source path treats streaming as body pass-through with `responseJson: null`, which weakens output hooks and final-body observability compared with non-streaming responses.
- D-002: Public docs describe consistent Responses API event streams across providers; the source-indexed gateway behavior includes multiple stream modes: delimiter-based text streams, AWS binary streams, and cached JSON-to-stream synthesis. That is not one lifecycle and should be decomposed as multiple HUAKAI contracts.
- D-003: README-level reliability language emphasizes retries and fallbacks, but streaming response dispatch returns a live response body once successful headers arrive. Reliability after first emitted chunk cannot behave like ordinary retry/fallback without explicit replay semantics.
- D-004: Release history includes a specific fix for streaming response headers on cached results, which indicates cached streaming had correctness edge cases despite looking like a small adapter path. HUAKAI should treat cached stream reconstruction as a separate test class.

## D. Things HUAKAI should NOT copy
- N-001: Do not copy status 246 as a pseudo-success contract. HUAKAI should use a clear internal policy verdict plus standard tenant-facing status/error taxonomy, because DR-001 multi-tenant operations need unambiguous dashboards, alerts, and billing state.
- N-002: Do not copy live-body reuse after failed streaming checks as the final policy model. HUAKAI should fail closed for configured deny policies before emission where possible, and use inline chunk scanning or buffered moderation for high-risk tenant routes.
- N-003: Do not copy route/provider stream handling as a loose set of transformer functions without tenant-scoped persistence. DR-006 PostgreSQL means stream lifecycle events, terminal reasons, disconnects, policy verdicts, and metering corrections should be recorded durably.
- N-004: Do not copy a single open-source/hosted feature story. DR-002 dual editions require explicit edition gates: community-safe streaming proxy, enterprise streaming audit/retention, and optional policy plugins without silently dropping behavior.
- N-005: Do not copy cache-hit streaming unless HUAKAI defines deterministic headers, chunk pacing, terminal events, and usage metadata. Cached streams must be visibly cache-origin and must not leak another tenant's response or trace metadata.
- N-006: Do not copy provider-specific binary stream parsing into core routing without a pluggable provider adapter boundary. HUAKAI needs a normalized stream event interface with provider adapters isolated from policy, billing, and tenant audit code.

## E. Smells found
- S-001: Inconsistent error taxonomy. A failed non-denying hook can become HTTP 246 with a streaming body, while denying hooks can become 446 JSON errors on non-streaming paths. HUAKAI should not expose mixed policy states as transport status quirks.
- S-002: Fail-open risk. For streaming responses without a completed JSON body, hook failure can preserve the stream body and only change status metadata. If a tenant configured output deny, HUAKAI must prove no unsafe chunk is emitted before denial.
- S-003: Magic status constants without operator contract. 246 and 446 are nonstandard operational statuses that need explicit operator documentation, alerting rules, and SDK behavior. HUAKAI should prefer typed policy results and mapped tenant responses.
- S-004: Hidden lifecycle state. Streaming returns `responseJson: null`, leaving downstream accounting and hooks dependent on side-channel span/context behavior rather than a durable terminal response object.
- S-005: Tenant data leakage potential. Cached JSON-to-stream conversion is a high-risk boundary: if cache keys, headers, or reconstructed metadata are not tenant-scoped, one tenant could receive another tenant's generated content or trace headers.
- S-006: Single-lifecycle assumption. The feature actually spans provider fetch, stream read, transform, policy, cache replay, client disconnect, and terminal accounting. Treating it as one handler is a design smell for HUAKAI.

## F. Synthesis recommendations
- Top-3 things specifier MUST address before this decomp can be cited by implementer-lane: define stream lifecycle phases and terminal states; specify fail-closed output policy behavior before and after first chunk; specify retry/fallback/cache-hit behavior after partial emission.
- Required test spine before citation: idle provider stream, malformed chunk boundary, client disconnect, transformer exception, cache-hit stream reconstruction, binary event stream normalization, and partial-emission accounting.
- Top-3 HUAKAI-specific divergences this decomp must call out: replace upstream pseudo-status policy signaling with HUAKAI error taxonomy; add DR-001 tenant-scoped durable stream audit and cache isolation; split DR-002 community and enterprise streaming policy capabilities without dropping feature parity.
- Required HUAKAI ops design before implementation: PostgreSQL-backed lifecycle/audit rows for stream start/end/abort; chunk-level or buffered policy enforcement options for high-risk routes; explicit operator recovery workflow for stuck streams, partial billing corrections, and replay-safe cache invalidation.
