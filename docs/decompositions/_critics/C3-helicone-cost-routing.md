## A. Coverage gaps (specifier likely missed these)
- C-001: Cheapest-provider routing is not just a sort by static price. Upstream docs say the gateway finds all providers for a requested model, prioritizes BYOK before managed credits, selects the cheapest provider, load-balances equal-cost providers, and fails over on provider errors. HUAKAI must spec the full chain: candidate discovery, tenant-owned key priority, managed pool fallback, price tie behavior, and post-error retry ordering.
- C-002: Failover trigger semantics are broad and risky. Upstream docs list 429, 401, 400 context-length, 408, and 500+ as triggers for trying another provider. A spec that treats this as generic "provider failure" will miss security and tenant-account hazards: 401 can mean a bad tenant credential, 400 can mean a malformed request, and retrying those into another provider may mask operator errors or leak a request outside the intended account/channel.
- C-003: Provider locking and exclusion rules create compliance edge cases. Upstream docs allow a model string to force one provider, use a deployment ID, specify a manual fallback chain, or exclude providers. HUAKAI needs explicit conflict handling when an exclusion conflicts with a manual chain, when all candidates are excluded, and when a compliance lock removes failover.
- C-004: Unknown-model routing is an important negative path. Upstream docs say unknown models route only through BYOK deployments. HUAKAI must require fail-closed behavior for unknown model plus no tenant deployment, not an automatic global pool fallback.
- C-005: "Always cheapest" is underspecified for streaming and token uncertainty. Cheapest provider can only be known from pricing dimensions before the call; actual total cost depends on output tokens, modality, cache hit/miss, batch pricing, region/deployment pricing, and provider-specific billing units. HUAKAI should require deterministic estimated-cost selection plus post-call actual-cost reconciliation.
- C-006: Runtime recovery is not covered by README-level claims. When model registry data, pricing tables, provider health, or tenant key status are stale, the router needs an operator-visible degraded mode and an audit trail explaining why a non-cheapest provider won.
- C-007: Horizontal scaling changes behavior. Source-level workspace layout includes routing crates for latency and weighted balancing, but docs also claim health/rate-limit awareness. Any in-memory health, latency, or equal-cost load-balance state will diverge across gateway replicas unless HUAKAI persists or externalizes the state.
- C-008: Custom-rule routing via compact model-string grammar is easy to misparse. The docs expose slash/comma/exclamation syntax in a single model field. HUAKAI needs parser acceptance tests for provider names, deployment IDs, provider exclusions, duplicate candidates, whitespace, unknown tokens, tenant-specific aliases, and maliciously long route strings.

## B. Flattering errors (looks simple, isn't)
- F-001: The README-level phrase "cost optimization (cheapest option)" hides a multi-source decision: provider registry, tenant credentials, managed credits, price catalog, failover taxonomy, and equal-cost distribution all participate.
- F-002: "Zero configuration required" is true only for the managed-credit happy path. In HUAKAI SaaS Edition, tenants need explicit account/channel binding, data-residency policy, budget/quota policy, and provider allow/deny policy before a cheapest route may be safe.
- F-003: "Manual fallback chain" looks like a list, but it is a policy object. It must answer whether retries preserve idempotency, whether streaming partial responses can retry, whether tool-call side effects can retry, and whether a lower-priority provider is allowed after a tenant budget is exhausted.
- F-004: "Equal-cost providers are load balanced" sounds harmless, but equal advertised price does not imply equal tenant cost. HUAKAI must account for volume discounts, Azure commitments, pass-through billing, exchange-rate drift, regional SKUs, and enterprise contract overrides.
- F-005: "Provider-aware model names" look like ergonomic API syntax, but they become a policy surface. A request-level model string can override admin routing intent unless HUAKAI clearly defines which tenant/admin policy wins.

## C. Upstream's own drift
- D-001: License metadata is inconsistent. GitHub's repository page presents GPL-3.0, while the visible workspace manifest and README/package text present Apache-2.0-style wording. HUAKAI should treat the target as non-MIT/non-clean-room source for this decomp and keep implementation lanes away from source details.
- D-002: README config examples drift across channels. The GitHub README sample uses a `model-latency` strategy and model list, while npm README text shows earlier-style latency targets. Specifier should not cite either sample as a stable contract without identifying version and edition.
- D-003: Public docs claim "automatic failover" and "your request succeeds even when providers fail," but the same docs say locking to one provider disables automatic failover. The decomp must call this out as conditional, not absolute.
- D-004: Public docs say 401 authentication errors trigger failover. That conflicts with a secure interpretation where tenant credential failure should usually fail closed and notify the tenant/operator, not silently use another account.
- D-005: Public docs claim 400 context-length errors trigger failover. That can only help if candidate providers have different context windows and the router knows them. Otherwise it is retry amplification for a deterministic client/request error.

## D. Things HUAKAI should NOT copy
- N-001: Do not copy compact routing syntax as the authoritative policy model. HUAKAI should parse request hints into a typed routing policy and then evaluate tenant/account/channel rules from PostgreSQL-backed policy tables.
- N-002: Do not let request-level provider exclusions override tenant or admin compliance policy. HUAKAI must make admin deny rules stronger than user hints.
- N-003: Do not fail over on authentication errors by default. For HUAKAI, credential/auth/account failures should fail closed unless an explicit tenant policy marks the failed account as replaceable and the next account is still tenant-authorized.
- N-004: Do not treat static public price as the single cheapest-provider criterion. HUAKAI should support effective-cost ranking: tenant key priority, contract price, regional price, input/output/cache/batch modality, quota headroom, and budget state.
- N-005: Do not rely on per-process router state for health, latency, cooldown, or equal-cost rotation in SaaS Edition. DR-001 and DR-006 imply tenant-scoped durable state, or at least shared Redis/PostgreSQL-backed coordination with audit records.
- N-006: Do not expose "no rate limits" language as product behavior. HUAKAI must preserve quota and billing enforcement even when provider routing can avoid upstream provider rate limits.
- N-007: Do not merge provider selection, fallback, and compliance into one implicit model-field grammar. HUAKAI needs separate API-visible request hints, tenant policy, provider health, and operator override layers.

## E. Smells found
- S-001: Inconsistent error taxonomy. Upstream docs group rate limit, auth failure, context length, timeout, and server errors as failover triggers, even though HUAKAI should classify them as retryable, terminal client error, terminal credential error, policy violation, or capacity failure.
- S-002: Fail-open risk. Public docs state managed keys/credits are fallback after BYOK and unknown models only use BYOK deployments; the safe boundary is conditional and must be enforced explicitly to prevent fallback into a global pool where tenant policy forbids it.
- S-003: Hidden global state risk. Cheapest routing depends on global model registry and pricing data; health-aware routing depends on shared provider status. If these are process-local or centrally mutable without tenant scoping, SaaS tenants can observe inconsistent routing decisions.
- S-004: Tenant data leakage potential. Automatic fallback from a tenant-controlled provider to a managed provider can move prompts across account, region, or contractual boundary unless every candidate is pre-authorized for that tenant and request class.
- S-005: Magic constants / undocumented thresholds. Public marketing claims mention health/rate-limit awareness and third-party/marketing text mentions fixed health-check and error-rate thresholds, but public docs do not expose operator override semantics. HUAKAI must not inherit opaque routing thresholds.
- S-006: Spec drift smell. README, docs, npm, and repository metadata do not present one stable versioned routing contract. Specifier must pin evidence to commit/version/date and separate product docs from actual source behavior.

## F. Synthesis recommendations
- Top-3 things specifier MUST address before this decomp can be cited by implementer-lane: define exact routing precedence among tenant BYOK, managed credits, manual chain, provider lock, provider exclusion, and unknown-model behavior; define failover error taxonomy with fail-closed credential/compliance paths; define cost-ranking inputs and audit fields beyond static public price.
- Top-3 things specifier MUST address before this decomp can be cited by implementer-lane: add negative scenarios for all-candidates-excluded, unknown model without tenant deployment, provider auth failure, context-window mismatch, streaming partial failure, and stale price/registry data; require deterministic parser tests for the slash/comma/exclamation custom routing grammar; require multi-replica tests for health/latency/load-balance state consistency.
- Top-3 things specifier MUST address before this decomp can be cited by implementer-lane: explicitly mark source-level implementation details as non-transferable under clean-room rules; record the upstream license drift as a risk; ensure implementer-lane receives only HUAKAI behavior contracts, not upstream crate/module structure or algorithmic code.
- Top-3 HUAKAI-specific divergences this decomp must call out: DR-001 requires every routing candidate to be tenant-scoped and auditable before evaluation; DR-002 requires Personal Edition to have local/simple safe defaults while SaaS Edition uses durable policy and admin override controls; DR-006 requires PostgreSQL-backed policy, decision logs, effective-cost snapshots, and operator recovery records for production routing.
- Top-3 HUAKAI-specific divergences this decomp must call out: HUAKAI should use a typed policy model rather than request-string grammar as the source of truth; HUAKAI should fail closed on auth/compliance/unknown-account errors; HUAKAI should separate price optimization from quota/billing enforcement so "cheapest" never bypasses spend limits.
