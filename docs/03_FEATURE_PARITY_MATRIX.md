# Feature Parity Matrix

## Purpose

This matrix tracks reference-derived features and ensures full feature parity or better. It is a living control document, not a wishlist.

## Valid Dispositions

| Disposition | Meaning |
| --- | --- |
| `Implemented` | The feature exists with equivalent behavior. |
| `Implemented Better` | The feature exists with materially stronger behavior, safety, UX, or operability. |
| `Merged Equivalent` | Multiple reference features are covered by one broader capability. |
| `Safe Equivalent` | The same user outcome is delivered with a safer clean-room design. |
| `Plugin` | The feature is supported through a plugin boundary. |
| `Feature Flag` | The feature exists but is gated for rollout, risk, or deployment policy. |
| `Mandatory Roadmap` | The feature is not implemented yet but is required before parity closure. |

Invalid dispositions: `Dropped`, `Ignored`, `Not Needed`, `Too Risky`, `License Risk`, `Out of Scope`.

## Disposition vs Status

The **Disposition** column is the **target** disposition: the planned shape the feature will take when delivered at its target level (L1/L2/L3/L4 in [17_FEATURE_LEVEL_MATRIX.md](17_FEATURE_LEVEL_MATRIX.md)). It is set when the feature is mined and only changes when the design intent changes.

The **Status** column reflects the **current** implementation state: `Open` (not yet built), `Built`, `Released`, `Mitigated`, etc. A feature can have Disposition `Implemented Better` and Status `Open (L1 MVP)` simultaneously — that means "we plan to deliver this with stronger behavior than the reference, and we have not built it yet." Release-readiness gates check the Status column; design-intent audits check the Disposition column.

This separation is intentional. If we forced Disposition to track Status (e.g. all unbuilt rows must say `Mandatory Roadmap`), we would lose the design-intent metadata that distinguishes a planned `Plugin` from a planned `Implemented Better` from a planned `Safe Equivalent`. Instead, both axes are preserved.
