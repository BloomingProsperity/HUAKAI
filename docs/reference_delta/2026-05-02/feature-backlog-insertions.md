# Feature backlog insertions

This file is a suggestion list only. It does not modify `docs/03_FEATURE_PARITY_MATRIX.md` or `docs/17_FEATURE_LEVEL_MATRIX.md`.

These items come from a first-pass source evidence review. They are strong enough for backlog insertion and Claude-facing planning, but high-risk items still need clean-room behavior specs before implementation.

## Highest priority commercial gaps

| Feature ID | Feature | Source projects | User outcome | Risk | HUAKAI local capability | Level | Acceptance-test direction |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `F-REQ-001` | Request body compression decode guard | one-api | Valid compressed clients work; oversized decompressed payloads fail safely. | Decompression bomb, memory pressure, misleading request size metrics. | Decode supported encodings behind bounded reader; enforce post-decode byte limit and ratio guard; log sanitized rejection. | L1/L2 | Send normal gzip body, oversized gzip body, high-ratio bomb fixture, and malformed gzip; assert status, logs, and no upstream call. |
| `F-ERR-001` | Upstream error sanitization | Sub2API, Portkey, LiteLLM | Operators see useful errors without leaking provider keys, account ids, cookies, or raw upstream internals. | Secret leakage, support confusion, compliance exposure. | Adapter boundary maps upstream errors into public error, internal reason, retry class, and redacted evidence. | L1 | Simulate 401/quota/5xx/invalid JSON with secrets in body/header; assert response and logs redact secrets but preserve retry class. |
| `F-EXEC-001` | Multi-attempt executor policy | Sub2API, Portkey, one-api | Failed provider/account can retry/fallback predictably and show attempt history. | Retry storms, duplicate billing, hidden partial failures. | Status-code fallback, retry-after respect, cooldown, idempotency key, attempt trace, per-tenant retry budget. | L1/L2 | Chain three mock providers with retryable/non-retryable errors; assert attempts, cooldown, final billing, and admin trace. |
| `F-ACC-HEALTH-001` | Provider account health operations | Sub2API, one-api | Admin can test, recover, temporarily offline, bulk import/export, and see account health. | Bad accounts remain in pool; manual DB edits; support downtime. | Account health state machine, temp-unschedulable, schedulable reset, check/sync/test/recover, bulk action audit. | L1/L2 | Mark account unhealthy, route around it, recover it, batch import invalid accounts, assert audit and pool state. |
| `F-USER-SELF-001` | User self-service key/usage/balance console | Sub2API, one-api | User can inspect keys, usage, remaining balance, redeem/subscription state without admin. | Support load, billing disputes, poor trust. | Read-only usage/balance/key UI plus safe key lifecycle and API. | L1/L2 | User creates/rotates key, views usage after request, sees balance change, cannot access another tenant. |
| `F-PAY-ORDER-001` | Payment order lifecycle recovery | Sub2API, Helicone, New API | Failed/duplicate webhooks and resumed checkout can be reconciled. | Money loss, double credit, refund disputes. | Order state machine, provider webhook idempotency, resume token, refund request/review, payment audit. | L2 | Replay webhook, verify resume token, cancel stale order, request refund, assert ledger idempotency. |
| `F-CH-MON-001` | Channel monitor templates/history/rollups | Sub2API | Admin can see channel failure trend before customers report it. | Silent provider degradation. | Monitor templates, probes, daily rollups, history, failure reason, notification hook. | L2 | Scheduled probe writes history/rollup; failing channel marks warning; admin resolves and history remains. |
| `F-LOG-RET-001` | Usage/system log retention and cleanup | Sub2API, Helicone | Logs stay searchable without unbounded storage growth. | Database bloat, slow admin, missing forensic trail. | Retention policy, cleanup task, audit of cleanup, export window, indexes/TTL where applicable. | L2 | Create old/new logs, run cleanup, assert only expired data removed and cleanup audit recorded. |

## Billing, quota, and pricing

| Feature ID | Feature | Source projects | User outcome | Risk | HUAKAI local capability | Level | Acceptance-test direction |
