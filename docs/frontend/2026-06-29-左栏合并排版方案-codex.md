## 1. 修正结论

上一版拆得太细。正确方向不是“把每个功能都放进左栏”，而是：

- 左栏只放用户会反复回来的工作区入口。
- 同一对象的 CRUD、状态、测试、日志、导出放同一个页面内。
- 同一条运营链路里的小功能合并成 tabs，不拆成多个一级菜单。
- 详情、危险动作、一次性配置放抽屉或详情页，不占左栏。
- 当前已有独立路由不等于必须在左栏独立出现。

最终建议：用户门户 5 个入口，运营台 6 个入口。

## 2. 代码证据

### 2.1 HUAKAI 当前前端已经具备“合并入口”的基础

当前 `PIPELINE_NAV` 已经不是一页一路由式侧栏。用户侧已经把 API Key 与 Playground 合并，把钱包、订单、订阅、兑换、签到、推广合并，把资料、通知、活动合并。证据见 `frontend/src/app/nav.ts:31-91`。

运营侧当前分为上游账号池、路由与池、用户与租户、模型与定价、计费运营、内容与公告、系统、安全审计。证据见 `frontend/src/app/nav.ts:93-186`。这一版的问题不在“不能合并”，而是合并边界还偏技术模块：系统、安全、内容、风控、告警之间对操作员来说会来回跳。

前端真实页面路由已经超过左栏适合承载的数量：用户侧有 overview、keys、usage、usage-records、media-tasks、subscriptions、orders、wallet、redeem、checkin、affiliate、available-channels、my-groups、profile、notifications、activity；运营侧有 accounts、routing、users、models、orders、subscriptions、vouchers、affiliates、announcements、moderation、pricing、groups、model-registry、model-sync、version、logs、system、ops、health、security、alerting、risk、backup、proxies。证据见 `frontend/src/app/router.tsx:66-109`。

### 2.2 HUAKAI 后端也支持按工作流合并

推理调用、模型列表、API-key 维度用量、session 维度用量、审计与收据都在网关主路由里形成同一条“开发者使用与用量核验”链路。证据见 `backend/cmd/gateway/routes.go:93-184`。

用户门户的配额、用量明细、签到、活动日志、发票、Key 汇总、邀请、分组、返利、兑换记录都挂在 `/v1/me` 下，说明用户侧可以按“我的使用 / 我的权益 / 我的账户”聚合，而不是拆成大量左栏入口。证据见 `backend/cmd/gateway/routes.go:185-228`。

后台管理的账号池、计费、余额、模型同步、兑换码、支付、订阅、返利、争议、公告、路由、TLS 指纹、告警、风控、内容审核、用量、审计、DLQ、L2 缓存集中在管理路由段，适合做少数运营工作区。证据见 `backend/cmd/gateway/routes.go:1010-1120`。

用户管理本身已经包含列表、创建、删除、解锁、2FA、passkey、分组、备注、状态、余额历史、社交解绑，应该落在“用户”一个入口里。证据见 `backend/internal/adminuserhttp/routes.go:145-158`。

代理管理是列表、创建、详情、更新、删除、状态、测试一组完整资源操作，不应作为孤立一级入口；它更适合放进“资源/账号池”的出口能力页签。证据见 `backend/internal/proxyadminhttp/routes.go:64-73`。

告警规则、告警事件、静默规则是一套监控工作流，不应拆散。证据见 `backend/internal/alertinghttp/mount.go:35-45`。

### 2.3 sub2 给出的可借鉴点

sub2 用户侧把常用个人功能放在一条用户导航中，并通过 feature flag 与 simple mode 控制可见性；管理侧对渠道、分销、订单等复合功能使用可展开父项或子项承载。证据见 `/home/ubuntu/refs/sub2api/frontend/src/components/layout/AppSidebar.vue:657-688` 与 `/home/ubuntu/refs/sub2api/frontend/src/components/layout/AppSidebar.vue:717-788`，当前读取提交为 `e34ad2b`。

抽象成 HUAKAI 规则：左栏可以有父入口，但不要把所有小功能展开为一级项；同一业务链路的小功能应进入父入口内部。

## 3. 用户门户合并版左栏

建议用户门户只保留 5 个入口：

```text
概览
开发
用量
钱包
账户
```

### 3.1 概览

落地路由：`/overview`

页面内区域：

- 余额与配额摘要
- 今日请求与成本
- 最近 API Key
- 最近用量
- 快捷操作：创建 Key、去调试、充值、查看明细

合并理由：概览不是功能集合，而是入口页，承担“我现在账户是否正常”的第一眼判断。

### 3.2 开发

主路由建议：`/keys`

合并进入：

- `/keys` 我的密钥
- `/playground` 在线调试台
- `/available-channels` 可用渠道
- `/my-groups` 分组与倍率

页面内 tabs：

```text
开发
  密钥
  调试
  可用模型/渠道
  分组与倍率
```

合并理由：用户创建 Key、看可用渠道、看分组倍率、在线调试，本质都是“我要把 API 接起来”。这些不应该分散在用量、API Key、模型三个地方。

### 3.3 用量

主路由建议：`/usage`

合并进入：

- `/usage` 用量概览
- `/usage-records` 请求明细
- `/media-tasks` 媒体任务
- `/v1/receipts/*` 收据与核验入口，前端可后续补 tab
- `/v1/me/disputes` 争议入口，前端可后续补 tab

页面内 tabs：

```text
用量
  概览
  请求明细
  媒体任务
  收据/争议
  导出
```

合并理由：请求明细、媒体任务、收据、争议都围绕“这次调用发生了什么、扣了多少、有没有问题”。放在一个入口里，用户查账时不用跨菜单。

### 3.4 钱包

主路由建议：`/wallet`

合并进入：

- `/wallet` 钱包与充值
- `/orders` 我的订单
- `/subscriptions` 订阅套餐
- `/redeem` 兑换码
- `/checkin` 每日签到
- `/affiliate` 推广返利

页面内 tabs：

```text
钱包
  余额/充值
  订单
  订阅
  兑换/签到
  推广返利
```

合并理由：订单、订阅、兑换、签到、返利最终都影响用户权益或余额。它们可以在钱包内合并，左栏不需要拆成多个入口。

### 3.5 账户

主路由建议：`/profile`

合并进入：

- `/profile` 个人资料与安全
- `/notifications` 站内信
- `/activity` 安全日志

页面内 tabs：

```text
账户
  资料
  安全
  通知
  活动日志
```

合并理由：资料、安全、通知、活动日志都是用户账户治理，不需要拆开。

## 4. 运营台合并版左栏

建议运营台只保留 6 个入口：

```text
总览
资源
用户
模型
交易
运营
```

如果 Owner 希望更像传统后台，可以把“运营”拆成“运维”，但我建议先保持 6 个入口以内。

### 4.1 总览

主路由建议：`/ops`

合并进入：

- `/ops` 运维大屏
- `/health` 系统健康摘要
- 关键告警摘要
- 今日交易摘要
- 今日用量摘要

页面内区域：

```text
总览
  请求量
  成本/收入
  账号池健康
  告警
  最近异常
```

合并理由：总览只放读态，不放复杂配置。操作员先判断平台是否正常，再进入资源、用户、交易等工作区。

### 4.2 资源

主路由建议：`/accounts`

合并进入：

- `/accounts` 上游账号
- `/routing` 路由与池
- `/admin/groups` 分组
- `/admin/proxies` 出口代理
- `/v1/admin/tls-fingerprint-profiles` TLS 指纹
- provider/account 健康、测试、绑定、冷却状态

页面内 tabs：

```text
资源
  上游账号
  路由/池
  分组
  出口代理
  TLS 指纹
  健康测试
```

合并理由：这些共同回答一个问题：“请求会打到哪个上游资源，为什么，是否健康”。账号池、路由、分组、代理、TLS 指纹拆开会让排障路径变长。

### 4.3 用户

主路由建议：`/users`

合并进入：

- `/users` 用户列表与详情
- 用户状态、分组、备注
- 用户余额历史
- 2FA 与 passkey 管理
- 社交身份解绑
- 用户活动日志入口

页面内 tabs：

```text
用户
  用户列表
  权限/状态
  余额
  安全
  活动
```

合并理由：用户治理不要和计费、审计、账号池混在多个入口里。用户详情页内应该能看到这个用户的余额、安全、活动、Key、用量跳转。

### 4.4 模型

主路由建议：`/models`

合并进入：

- `/models` 模型列表
- `/admin/pricing` 定价设置
- `/admin/model-registry` 模型注册
- `/admin/model-sync` 厂商同步
- `/available-channels` 的后台对应视角

页面内 tabs：

```text
模型
  模型列表
  定价
  注册
  厂商同步
  可用性
```

合并理由：模型、定价、注册、同步是同一个模型目录的不同编辑面。拆开会让价格、同步、展示状态彼此脱节。

### 4.5 交易

主路由建议：`/admin/orders`

合并进入：

- `/admin/orders` 订单
- `/admin/subscriptions` 订阅
- `/admin/vouchers` 兑换码
- `/admin/affiliates` 分销
- `/v1/admin/payments` 支付配置与支付记录
- `/v1/admin/disputes` 争议
- admin export
- `/admin/v1/balances` 余额调整
- `/admin/v1/billing` 计费策略

页面内 tabs：

```text
交易
  订单
  订阅
  兑换码
  分销
  退款/争议
  余额/计费
  导出
```

合并理由：这些都围绕“钱、权益、账”。兑换码和分销不应单独在左栏占位置；它们是交易运营的子功能。

### 4.6 运营

主路由建议：`/system`

合并进入：

- `/system` 系统设置
- `/admin/announcements` 公告
- `/admin/moderation` 内容审核
- `/admin/risk` 风控
- `/admin/alerting` 告警
- `/security` 审计
- `/admin/backup` 备份
- `/admin/version` 版本
- `/admin/logs` 日志诊断
- `/admin/v1/dlq/*` 死信队列
- `/admin/v1/cache/l2/*` L2 缓存

页面内 tabs：

```text
运营
  系统设置
  公告/通知
  审核/风控
  告警
  审计
  备份
  版本/日志
  队列/缓存
```

合并理由：这些是平台运营维护功能。单独拆成“系统、内容、安全审计、监控告警、风控”会让侧栏膨胀。真正需要区分的是页面内风险等级和权限确认，而不是左栏入口。

## 5. 左栏与页面内承载规则

| 功能类型 | 放置方式 | 例子 |
| --- | --- | --- |
| 每天都会进入的工作区 | 左栏一级入口 | 开发、用量、资源、交易 |
| 同一对象的多种操作 | 页面内 tabs | 用户的安全/余额/活动，模型的定价/同步 |
| 危险动作 | 详情页按钮或确认抽屉 | 删除用户、重置 2FA、强制恢复账号 |
| 低频维护项 | 运维/运营入口内 tab | 版本、备份、日志、缓存 |
| 状态查看 + 手动处理 | 同一 tab 内列表和行内动作 | 告警事件与手动解决、DLQ 与 replay |
| 报表导出 | 相关业务页的操作按钮 | 订单导出、用量导出 |

## 7. 与当前 `nav.ts` 的差异

| 当前入口 | 建议去向 | 理由 |
| --- | --- | --- |
| 用户侧 `API Key` | 改为 `开发` | Key、Playground、渠道、分组同属接入工作流。 |
| 用户侧 `用量与配额` | 保留为 `用量`，移出可用渠道/分组 | 用量页只处理调用、明细、媒体任务、收据争议。 |
| 用户侧 `充值与权益` | 改为 `钱包` | 更短、更贴近用户心智。 |
| 运营侧 `上游账号池` + `路由与池` | 合并为 `资源` | 账号、路由、分组、代理、TLS 指纹是同一资源调度链路。 |
| 运营侧 `模型与定价` | 保留为 `模型` | 定价、注册、同步是模型目录的 tabs。 |
| 运营侧 `计费运营` | 改为 `交易` | 订单、订阅、兑换码、分销、争议、余额、计费都属钱和权益。 |
| 运营侧 `内容与公告` + `安全审计` + `系统` | 合并为 `运营` | 公告、审核、风控、告警、审计、备份、日志、版本都是平台运营维护面。 |

## 8. Open questions

1. `审计` 是否需要从 `运营` 中拆成独立入口，取决于 Owner 是否把可验证审计作为前台强卖点。如果是合规/信任中心主功能，可独立；如果主要给管理员排障，就留在运营内。
2. `总览` 主路由用 `/ops` 还是新建 `/admin`，需要实现阶段决定。现在已有 `/ops`、`/health`、`/system`，文档层建议先用 `/ops` 做运营台总览。

## 9. Owner 摘要

这版把左栏重新压缩：用户门户 5 个入口，运营台 6 个入口。没有功能缩水，原来的路由都被映射到某个入口内的 tab、详情页、抽屉或行内动作。clean-room 风险低，只引用 sub2 的菜单组织行为和代码位置，不复制其源码或文案。安全风险低，本次只写文档不改代码；真正实现时需要在危险动作、审计、计费、用户安全操作上保留权限确认和审计记录。下一步建议先按此方案修改 `frontend/src/app/nav.ts` 的标签与分组，再逐页把 tabs 合并，而不是一次性重写所有页面。
