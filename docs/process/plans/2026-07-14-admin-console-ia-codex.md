## 一、主张：侧栏按经营动作推进，而不是按资源堆放

HUAKAI 运营台的主线应是：**先看今天发生了什么 → 服务用户并促成收入 → 备齐上游供给 → 编排并出售服务 → 监控交付并止损 → 清账与恢复 → 管好团队权限 → 配置系统底座**。

这条顺序把最高频的“用户台”提到最前，把账号池作为可运营供给单列，把设置固定沉底。角色不会改变这条骨架；权限只决定同一骨架内哪些入口可见、哪些动作可执行。

### 1.1 运营台侧栏精确顺序

标记说明：

- **新增**：当前 `nav.ts` 没有，后续需要契约和实现，不做假占位。
- **提级**：从混合分区提升为更高频或独立控制入口。
- **移动**：保留当前路由和能力，只改变所在阶段与顺序。
- **改名**：路由不变，用更符合真实能力或任务的文案。

### 1.2 现有 60 个登录后入口的完整归位证明

源码事实是 `nav.ts` 有 **59** 个侧栏路径，而不是 60 个：运营台 40 个、终端用户自助壳 19 个。`router.tsx` 另有登录后根入口 `/`，合计正好 60 个登录后入口。本稿的处理如下：

- 运营台 40 个侧栏路径：已在 1.1 中逐项且只出现一次。
- 登录后根入口 `/`：作为壳入口；运营身份进入 `/ops`，终端用户身份进入 `/overview`，不生成第三个“首页”菜单。
- 终端用户自助壳 19 个路径：继续与运营台物理分离，顺序和归属见下表；它们不是运营者侧栏，也不是本稿所称“用户台”。

| 自助壳分区 | 精确顺序 | 处置 |
|---|---|---|
| 概览 | `/overview` | 保留在终端用户自助壳 |
| 我的账户 | `/keys` → `/profile` → `/notifications` → `/activity` | 保留在终端用户自助壳 |
| 用量与计费 | `/usage` → `/usage-records` → `/wallet` → `/orders` → `/subscriptions` → `/redeem` → `/my-groups` | 保留在终端用户自助壳 |
| 更多工具 | `/integration` → `/playground` → `/media-tasks` → `/available-channels` → `/trust` → `/checkin` → `/affiliate` | 保留在终端用户自助壳 |

`router.tsx` 的 `/users/:id`、`/accounts/:id` 是两个登录后详情路由，分别归入“用户台”和“上游账号”；它们不应在侧栏重复出现。11 个公开路由 `/setup`、`/login`、`/oauth/callback`、`/forgot-password`、`/reset-password`、`/email-verify`、`/device-confirm`、`/rankings`、`/key-usage`、`/welcome`、`/legal` 继续留在壳外，不纳入运营侧栏。

## 二、账号池控制区：先建立可用供给，再做流量编排

账号池不是一个叫“账号池”的孤立列表，而是一条需要逐级校验的运营链：

1. **厂商**：在 `/admin/catalogs?tab=providers` 选择已发布能力，查看协议族、发布态和适用地区；不把 Experimental/Scaffold 伪装成可发流量。
2. **渠道**：在 `/admin/catalogs?tab=channels` 绑定厂商、协议与 endpoint，展示所属租户、状态和最近验证时间。
3. **账号**：在 `/accounts` 创建和筛选上游账号，必须先确定 tenant scope；列表首屏显示厂商、渠道、池归属、启用状态、健康、限流状态和最后活动。
4. **凭证**：从 `/accounts/:id?tab=credentials` 管理该账号的凭证，`/admin/credential-renew` 只承接跨账号续期队列。秘密默认掩码、永不列表回显；新增/轮换只显示一次，复制动作留审计。
5. **健康**：`/admin/channel-health` 汇总账号与渠道健康，支持查看详情、暂停、恢复和强制激活；危险动作必须说明影响范围并二次确认。
6. **代理**：`/admin/proxies` 绑定出站代理，展示密钥脱敏、健康、所属账号和测试结果，不允许绕过 SSRF/代理策略。
7. **指纹**：`/admin/tls-fingerprints` 管理 profile，实际绑定仍在 `/accounts/:id` 完成，必须展示当前绑定、漂移和最近探测。

随后才进入“编排并出售服务”：`/admin/groups` 组建账号池，`/routing` 将模型绑定到池，`/admin/route-rules` 定义选择与故障切换，`/admin/quota-policies` 和 `/admin/pricing` 决定可售边界。

账号详情顶部固定呈现：账号名、tenant、厂商/渠道、所属池、发布态、流量许可、启用状态、健康、凭证到期、限流、代理/指纹和最后一次成功请求。这样运营者无需先进入七个页面才能判断“这个账号现在能不能承接请求”。

## 三、以人为中心的用户台

### 3.1 入口与列表

`/users` 更名为“用户台”，默认按“需要处理”排序，而不是仅按创建时间。列表必须具备搜索、筛选、排序、分页和批量选择，关键列为：用户身份、状态、所属 tenant/代理节点、余额、当前订阅、近 30 天消耗、最后活动、2FA、安全风险和待处理事项。

点击用户进入 `/users/:id`，页面上下文锁定为这一个人。跨 Tab 操作必须保留用户 ID、tenant 和代理归属，禁止因搜索条件或返回列表而误操作其他用户。

### 3.2 详情页顶部

顶部固定区从左到右放：

1. **身份**：显示名、邮箱、用户 ID、备注、注册时间、所属 tenant/代理节点。
2. **状态**：正常/冻结/已软删、组/角色、2FA、Passkey、最后登录和最后 API 活动。
3. **经营摘要**：可用余额、当前订阅与剩余额度、本月消耗、近 24 小时请求/失败、未结订单或争议。
4. **主动作**：充值/调额、签发 Key、派发订阅三项高频动作。
5. **更多危险动作**：封禁、解锁、强关 2FA、删除 Passkey、解绑身份、软删除。危险动作不平铺；执行前展示对象、影响、权限依据，要求原因和确认，完成后生成审计事件。

### 3.3 Tab 与动作清单

#### Tab 1：经营概览

- 展示余额、订阅进度、近 30 天用量/消费、Key 数、失败率、安全状态和最近事件。
- 给出“余额不足”“订阅将到期”“全部 Key 停用”“2FA 风险”“异常失败率”等可操作提示。
- 所有卡片下钻到本页其他 Tab，不跳去全局列表后丢失用户上下文。

#### Tab 2：余额与充值

- 查看当前余额与余额变动历史。
- 运营者代客创建充值订单、确认到账、取消或重试订单。
- 正向/负向调额，必须填写原因并展示调整前后余额。
- 查看退款请求、退款结果、收据和与该用户相关的计费追补记录。
- 金额动作按权限分级；大额或负向调整进入复核，所有动作不可静默覆盖账务历史。

#### Tab 3：API Key

- 查看该用户全部 Key 的名称、掩码、状态、到期、最近使用和用量摘要。
- 签发、编辑、单个停用/撤销和批量撤销；秘密只在创建成功后显示一次。
- 设置每个 Key 的配额、组、IP allowlist/blacklist 和模型 allowlist。
- 从 Key 直接下钻该 Key 的请求明细，但保持用户上下文。

#### Tab 4：订阅与权益

- 查看当前和历史订阅、套餐、周期、剩余额度、续期状态与变更记录。
- 派发或批量规则外单独派发订阅，支持改档、延长、重置额度、取消续订和退订/撤销。
- 任何会丢失权益或重置额度的动作展示生效时间、剩余额度处理方式和审计原因。

#### Tab 5：用量与请求

- 按时间、Key、模型、状态、路由和上游账号筛选用量明细，支持分页与导出。
- 展示 token、金额、延迟、缓存命中、错误和请求 ID。
- 单请求串联用户、Key、路由、账号池、上游账号、用量、收据和审计证明；可进入争议流程，但不在此直接改账。

#### Tab 6：安全与账号

- 修改状态、组和备注；查看 OAuth/Telegram 等身份绑定。
- 封禁/解封、解锁、强制关闭 2FA、删除全部 Passkey、解绑指定外部身份。
- 查看会话与设备；具备相应后端契约后允许撤销会话，不用“重置密码”冒充会话失效。
- 展示 2FA、Passkey、最后登录、异常活动与安全处置历史。

#### Tab 7：通知与触达

- 查看和代管该用户的通知偏好。
- 查看已发送站内信及读取状态，向该用户发送单人通知。
- 广播仍在全局“用户触达”处理，避免单人页误发全站。

#### Tab 8：操作审计

- 统一展示对该用户发生的资料、状态、余额、Key、订阅、安全和通知操作。
- 每条记录展示操作者、角色、作用域、时间、原因、变更前后摘要、请求 ID 和证明/导出入口。
- 审计记录只读；运营者不能在用户台删除或改写历史。

## 四、权限分级与单层租户结构

### 4.1 管理台组织方式

权限治理不是按角色复制多套侧栏。所有运营角色共享同一条经营动线，系统在入口和动作两层授权：

- **运营成员**：成员账号、状态、所属组织/代理节点、角色集合、最后活动和 2FA。
- **角色与权限**：角色定义、权限矩阵、数据作用域、条件、成员绑定和变更审计。
- **租户能力与资源分配**：部署者查看和管理单层下级租户，为租户分配功能、上游账号使用权和经营额度；租户不能继续创建租户。
- **平台凭证**：系统对系统的管理员 token，独立于人类运营成员，也独立于终端用户 API Key。

### 4.2 授权模型主张

权限判断采用五元组：**主体（部署者操作主体/租户侧管理账号/服务账号）× 作用域（平台/单个 tenant）× 资源 × 动作 × 条件**。明确拒绝优先于允许，所有查询和导出都受数据作用域约束，不能只在前端藏按钮。租户侧管理账号只是代表租户操作，不构成第四种产品身份。

内置角色模板固定为：

1. **平台所有者**：全平台治理和角色委派；高风险能力仍需强确认。
2. **平台管理员**：日常全平台运营，不可转移所有权或绕过审计。
3. **用户运营**：用户资料、Key、订阅与触达；默认无账务负向调整、角色授权和上游秘密权限。
4. **财务运营**：订单、充值、调额、退款和台账；默认无凭证读取、路由发布和角色授权。
5. **供给运营**：厂商、渠道、账号池、凭证状态、健康、路由和模型发布；秘密仍默认不可回显。
6. **安全审计**：风险、审核、审计与导出；默认只读，处置动作单独授权。
7. **只读观察者**：在指定作用域内只读且不能查看秘密明文。

角色模板可复制为自定义角色，但关键动作必须拆成独立权限，例如 `balance.adjust`、`refund.approve`、`credential.rotate`、`route.publish`、`user.security.force_disable_2fa`、`role.assign`，禁止用一个宽泛的 `admin` 布尔值包办。

### 4.3 三身份与单层租户边界

- HUAKAI 只存在系统部署者、系统用户和下级租户三种身份。
- 租户创建的客户仍然是用户，只是归属于该租户。
- 只有部署者可以创建、启用和停用租户；租户不能创建租户。
- 部署者通过平台治理接口分配能力、账号使用权和经营额度，不通过租户业务接口代替租户经营。
- 租户只管理自己的客户用户、已分配账号和可分发额度。
- 用户邀请返利属于同一经营边界内的用户增长能力，不产生租户层级。
- 权威合同见 `docs/process/plans/2026-07-16-three-role-single-level-tenant-model-codex.md`。

## 五、与两条禁用招牌骨架的差异

### 5.1 不采用“角色分层 + 自用菜单双处复用 + 折叠父项”

1. **不按角色切侧栏段落**：用户运营、财务、供给、安全看到的是同一经营动线，权限只裁剪入口和动作，不生成角色专属骨架。
2. **不复用终端用户自助菜单**：`/overview`、`/keys`、`/wallet` 等 19 个终端用户入口留在独立自助壳；运营者通过 `/users/:id` 的聚合 Tab 代管用户，不把“我的 Key”换个标题塞进运营台。
3. **不使用只能展开的父项**：阶段标题只是静态分区标签，不可点击、不替代页面；每个菜单项都是明确任务入口，详情通过表格行或上下文下钻。
4. **不限制成至多两段**：分区数量由真实经营阶段决定，保持稳定顺序并允许权限裁剪，但不因角色切换重排。

### 5.2 不采用“公开模型广场置顶 + 下钻替换整块侧栏”

1. **顶部是经营总览，不是模型橱窗**：运营者先看到收入、用户诉求、供给健康与告警。
2. **模型处于发布流程中段**：`/models` 被定义为“检查在售模型”，前面有上游供给、账号池、同步和登记，后面有路由、限额和定价。
3. **下钻不替换侧栏**：模型、用户、账号详情在主内容区打开，左侧经营阶段保持稳定；面包屑和返回列表维持上下文。
4. **公开目录与运营控制分离**：终端用户看到的可用模型/渠道属于自助壳；运营台管理的是供给是否可用、如何路由、如何定价和谁能购买。

## 六、HUAKAI 的侧栏排序签名

**HUAKAI 侧栏排序签名 = 以“看经营 → 服务人 → 备供给 → 发服务 → 守交付 → 清异常 → 控权限 → 配底座”为固定节拍的运营闭环。**

## 风险与验收边界

- 当前后端没有 tenant 生命周期管理接口，本稿不虚构“租户管理”菜单；tenant 只作为现有运营动作的显式作用域。
- 当前“模块”只有只读知识、“备份”只有 manifest；导航必须按真实能力改名，未来能力另走规格和验收。
- 账号创建仍有 `tenant_id`、`serving_readiness` 和凭证组合校验等 P0/P1 缺口；IA 只能提高可发现性，不能替代这些实现修复。
- 用户台聚合会跨用户、Key、订单、订阅、用量和审计域。后续实现必须先定义聚合读取、逐动作授权和失败恢复，禁止用前端并发拼接掩盖部分成功。
- 金额、身份安全、凭证、路由发布、DLQ 重放等危险动作必须权限化、确认、填写原因并审计；秘密默认脱敏。

验收时必须证明：现有 59 个侧栏路径无遗漏；运营者能从一个用户详情完成 Owner 指定的全套动作；任一请求可追到用户、Key、路由、账号、用量、账务与审计；不同角色在同一 IA 下受到服务端数据与动作授权；代理节点无法越过子树边界；终端用户自助壳与运营台无菜单复用。
