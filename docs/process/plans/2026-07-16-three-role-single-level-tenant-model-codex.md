## 一、权威身份模型

HUAKAI 只存在三种身份：

### 1. 系统部署者

系统部署者负责运行和治理整个系统，拥有平台级控制面：

- 创建、启用、停用租户。
- 决定租户能够使用哪些平台功能。
- 给租户分配可操作的上游账号或账号使用额度。
- 给租户分配经营余额、配额或可再分发额度。
- 管理平台安全策略、全局配置、系统健康和审计。
- 查看平台级汇总和租户分配结果。

系统部署者不是任意租户的业务操作员，不应通过租户业务接口：

- 创建、修改或删除租户的客户用户。
- 替租户创建客户 API Key。
- 替租户调整某个客户的余额。
- 读取租户客户的请求正文、凭据明文或私有业务数据。
- 冒充租户管理员执行日常经营动作。

部署者对租户进行账号、能力和余额分配属于平台治理行为，不属于代替租户经营。

### 2. 系统用户

用户是最终消费 API 服务的客户账号。用户必须属于且只属于一个服务经营边界：

- 部署者直属用户属于部署者直接经营的用户域。
- 租户创建的客户也仍然是用户，只是 `tenant_id` 指向该租户。

用户只能操作自己的资源，例如：

- 自己的 API Key。
- 自己的余额、订阅、额度和用量。
- 自己的请求记录、通知和安全设置。

“租户的客户”不是第四种身份，也不是下级租户。

### 3. 下级租户

下级租户是租用部署者部分系统能力的独立经营主体。它不是部署者的普通用户，也不是可以继续发展租户层级的代理节点。

租户实际登录时可以有一个或多个租户管理账号，但这些账号只是代表该租户执行操作的凭据，不构成第四种产品身份。

租户可以：

- 创建、停用和管理自己的客户用户。
- 给自己的客户创建 API Key。
- 在部署者分配的账号和能力范围内经营。
- 给自己的客户分发余额、额度、分组、模型权限和其他租户内权益。
- 查看自己的经营数据、账号状态、客户用量和租户内审计。

租户不能：

- 创建新的租户。
- 访问部署者直属用户。
- 访问其他租户及其用户。
- 操作部署者未分配给它的上游账号。
- 修改平台全局配置或其他租户的能力授权。
- 获得上游账号凭据明文，除非未来某种明确能力必须如此且经过独立安全决策。

## 二、唯一允许的层级

```text
系统部署者
├── 部署者直属用户
└── 下级租户
    └── 该租户的客户用户
```

结构约束：

1. 只有一层租户。
2. 租户下面只能创建用户，不能创建租户。
3. 不存在“上级代理”“下级代理”“二级租户”或递归租户子树。
4. 不需要跨租户委托管理模型。
5. 不从商业关系推导后台权限。

## 三、资源与权限边界

| 资源/动作 | 系统部署者 | 下级租户 | 用户 |
| --- | --- | --- | --- |
| 创建/停用租户 | 允许 | 禁止 | 禁止 |
| 开通租户功能 | 允许 | 只能使用已开通功能 | 禁止 |
| 分配上游账号给租户 | 允许 | 禁止转租，只能使用 | 禁止 |
| 操作已分配上游账号 | 只做平台分配、回收和安全治理 | 允许，限已分配账号和已授权动作 | 禁止 |
| 创建客户用户 | 可创建直属用户 | 允许，限本租户 | 禁止 |
| 管理客户 API Key | 只管理直属用户边界 | 允许，限本租户用户 | 仅自己的 Key |
| 给客户分发余额/额度 | 只处理直属用户或给租户分配经营额度 | 允许，限本租户和可用经营额度 | 禁止 |
| 查看客户请求和用量 | 只看直属用户或平台级脱敏汇总 | 允许，限本租户 | 仅自己 |
| 操作其他租户 | 禁止代经营；仅执行平台治理 | 禁止 | 禁止 |
| 创建下级租户 | 不适用，部署者直接创建租户 | 禁止 | 禁止 |

## 四、数据模型原则

后续 schema 和鉴权设计必须满足：

1. `tenant_id` 继续作为租户业务资源的强制隔离键。
2. 用户只属于一个租户经营边界。
3. 不增加 `parent_tenant_id`，不建立递归租户关系。
4. 平台能力授权单独表达“某租户可以使用什么功能”，默认未授权。
5. 上游账号必须区分平台所有权与租户使用权；分配不等于泄露凭据或转移所有权。
6. 租户经营额度必须能解释来源、可用额、已分发额、回收额和结算状态。
7. 部署者操作主体和代表租户的管理账号必须使用不同授权语义；租户管理账号仍归属于下级租户，不构成第四种身份。不能继续让所有 `users.role='admin'` 自动成为跨租户平台管理员。
8. 所有租户业务 handler 从认证上下文取得 tenant scope，不接受部署者通过请求参数指定任意 tenant 后代操作。

## 五、历史错误方案处置

历史 `feat/reseller-phase1` 的以下设计不符合当前产品定性：

- `parent_tenant_id` 租户父子树。
- 递归读取和管理后代租户。
- 把租户父子关系直接转换为跨租户管理权限。
- 分销商、多级代理和继续创建子租户的产品语义。

处置原则：

1. `0185_reseller_phase1_tenant_hierarchy` 只保留为不可改写的 migration 历史；最新 schema 必须由后续前向 migration 移除其结构，运行时不得接入。
2. 当前分支删除以代理树为目标的调研与计划文件。
3. 历史分支只作为错误方案证据，不作为实现来源。
4. 是否删除远端历史分支、清理包含该提交的集成分支或改写历史，必须作为独立破坏性操作由 Owner 明确确认。

## 六、后续落地顺序

### 阶段 1：身份和鉴权拆分

- 已完成最低边界：`HUAKAI_DEFAULT_WORKING_TENANT_ID` 对应部署者自营租户；该租户的明确 admin 会话映射为平台身份。
- 已完成最低边界：其他租户的明确 admin 会话只映射为本租户 `tenant_operator`，不新增第四种产品身份。
- 已完成状态联动：用户或所属租户停用、软删除后，既有 admin session 每次请求都会重新校验并立即掉权。
- 保持最终用户身份只访问自己的资源。
- 已移除“任意 admin session 自动成为跨租户平台管理员”的语义。
- 为部署治理接口和租户业务接口建立不可混用的授权门。

本次只完成身份分流；部署治理接口与租户业务接口的彻底拆分仍需独立 PR。

### 阶段 2：租户能力授权

- 部署者按租户开通或撤销功能。
- 默认未授权。
- 租户管理员只在本租户内执行已授权能力。
- 授权、撤销、拒绝和实际执行分别记录审计。

### 阶段 3：上游账号分配

- 平台拥有上游账号和凭据。
- 部署者把账号使用权或配额分配给租户。
- 租户只能看到和操作被分配账号的允许字段与动作。
- selector、健康、冷却、凭据刷新和回收必须识别分配边界。

### 阶段 4：余额和额度分发

- 部署者向租户分配可经营额度。
- 租户只能从自己的可用经营额度给客户分发。
- 客户消费、租户可用额和平台结算形成可核对的责任链。
- 回收、退款、超额、坏账和并发必须先形成资金合同，再修改 ledger。

该阶段涉及资金和配额，执行前必须由 Owner 决定结算模型。

### 阶段 5：运维界面

- 部署者看到租户状态、已开能力、账号分配、额度分配和平台级汇总。
- 租户看到自己的客户、已分配账号、余额池、客户用量和租户内审计。
- 用户只看到自己的 Key、余额、用量和安全设置。
- 界面不出现代理层级、租户树或委托管理入口。

## 七、验收条件

1. 租户无法创建租户。
2. 租户管理员无法访问其他租户或部署者直属用户。
3. 部署者无法调用租户客户管理、客户 Key 和客户余额业务接口代操作。
4. 部署者可以通过独立平台治理接口分配和回收租户能力、账号和经营额度。
5. 租户只能操作已授权能力和已分配账号。
6. 租户给客户分发的总额度不能超过自身可分发额度。
7. 用户只能访问自己的资源。
8. 所有拒绝、授权、分配、回收和资金变化均可审计。
9. 代码、OpenAPI、测试和前端规格中不再出现多级代理或递归租户树语义。

## 八、执行前检查单

1. 枚举所有部署级管理入口和租户业务入口。
2. 核对 session、admin token、API key 三条身份解析链。
3. 建立部署者、租户管理员、用户的完整权限矩阵。
4. 核对所有接受 `tenant_id` 的 handler 是否可能被部署者用于代操作。
5. 设计租户能力授权合同。
6. 设计账号所有权、分配和回收合同。
7. 设计经营额度、客户余额和平台结算合同。
8. 写正常、越权、撤权、回收、并发和恢复验收测试。
9. 高风险实现拆分为独立 PR，逐个交叉审查，未经 Owner 同意不合并。
