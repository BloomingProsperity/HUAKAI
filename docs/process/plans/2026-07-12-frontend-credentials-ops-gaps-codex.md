## 具体执行顺序

1. 建立端点—请求—响应—错误行为证据表，特别确认一次性明文字段、时间字段、分页/筛选参数和用量金额类型。
2. 按现有 feature 模式实现 `platformcredentials` 的类型、API、聚合页面与局部组件；接入管理导航、路由及 shell。
3. 在现有 DLQ 页面原位增加“观测死信”标签页、API、类型和重放状态，不引入跨 feature 新抽象。
4. 在管理员用户详情数据流中接入用量查询，以独立卡片展示核心聚合，并保证其他详情请求失败语义不被改变。
5. 为每个新 API 和关键秘密/确认/空态/错误/重放/用量分支补 Vitest，测试明确断言真实路径、HTTP 方法、请求体及依赖注入调用。
6. 先跑定向测试与 `tsc`，再跑全量 `vitest` 和生产构建；逐项修到全绿。
7. 复核 diff、中文注释、无裸 `fetch`、无后端改动、无依赖变更；将证据行号、文件清单、门禁摘要和自测结果写入指定报告。

## 技能约束落地

- `frontend-ops-ui-review`：秘密默认不可回读；危险动作确认；状态、过期时间和操作结果对运营人员可见；不复制外部项目 UI。
- `acceptance-test-writer`：覆盖正常创建/列表、危险动作确认、API 失败、空数据与重放恢复；断言结果必须能区分正确实现和路径/注入被篡改的实现。
