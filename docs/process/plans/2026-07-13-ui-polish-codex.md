## 范围

### 范围内

- 依据实际代码盘点，整改用户门户高频页面：概览、我的密钥、用量与配额、钱包与充值；将管理员 `Dashboard` 作为 P1 同步收口项。
- 在 `frontend/src/ui/` 增加可复用的 `EmptyState` 与骨架屏基础件，统一空数据、首次加载、局部不可用三类视觉语义；现有业务请求、状态机和权限边界保持不变。
- 在现有 HUAKAI token 与公共样式体系内提高信息密度、视觉层级、卡片内部对齐、窄屏可读性和行动可达性。
- 为公共状态组件及关键页面状态补充组件测试/可访问性断言；运行现有前端测试、类型检查和构建。

### 明确不做

- 不改应用壳、布局框架、侧栏/顶部导航、路由结构、权限跳转和页面 URL。
- 不改现有配色 token、字体 token、间距 token、圆角 token 或阴影 token；不复制任何参考产品的外壳、图形资产、文案或独特布局。
- 不新增运行时或开发依赖，不引入图标库、图表库、CSS 框架或动画库；图形只用现有 CSS、内联 SVG 与文本能力。
- 不改后端 API、数据契约、计费/配额/认证逻辑，不借“质感整改”扩张业务功能。
- 不把“无配额”错误表达为故障，也不为填满页面制造虚假统计值、示例订单或伪造趋势。

## 方案

### 优先级与执行顺序

1. **P0：公共状态语言。** 先建立 `EmptyState`、`Skeleton`/`SkeletonRows`，再迁移页面，避免继续复制局部 `Empty`、`Muted` 和“加载中…”灰字。
2. **P0：概览、密钥、用量。** 这三页承担首次进入、首次创建和用量判断，Owner 点名问题均在其中；先完成零数据与正常数据两条主路径。
3. **P0：钱包。** 收口余额、充值能力、订单空态，避免 money 页面因弱层级造成误读；只改善展示，不触碰开单确认语义。
4. **P1：管理员 Dashboard。** 统一指标加载、经营总览空态和管线入口密度；不改变管理员/用户分流。
5. **P1：一致性与回归。** 清除本波页面内重复状态组件，补齐键盘焦点、语义标签、窄屏和长文本验收。

### 公共组件 API 设计

计划新增 `frontend/src/ui/EmptyState.tsx`，建议 API：

```ts
type EmptyStateTone = 'neutral' | 'positive' | 'unavailable'

interface EmptyStateProps {
  title: string
  description?: React.ReactNode
  visual?: React.ReactNode
  primaryAction?: { label: string; onClick?: () => void; to?: string }
  secondaryAction?: { label: string; onClick?: () => void; to?: string }
  tone?: EmptyStateTone
  compact?: boolean
  className?: string
}
```

- `title` 给出可扫描结论，`description` 解释原因或下一步；业务空态原则上提供 `primaryAction`，只有“健康的无事件状态”（例如暂无告警）可使用 `positive` 且不强塞行动。
- `visual` 接受调用方提供的简单装饰，不绑定第三方图标；默认使用 HUAKAI 自身的几何标记或首字母标记，并设为装饰性、对读屏隐藏。
- `to` 使用路由链接，`onClick` 用于打开创建弹窗/重试；API 约束同一行动不得同时传两者。按钮复用 `hk-btn`，不另造按钮体系。
- `compact` 用于表格内部或半宽子卡；默认态承担整卡空白区域，形成“结论—解释—行动”的纵向层级。
- `unavailable` 是请求失败/权限不可达，不与业务零数据混用；应配重试或替代入口。错误详情仍沿用现有安全归一化策略。

计划新增 `frontend/src/ui/Skeleton.tsx`，提供 `Skeleton`、`SkeletonText`、`SkeletonMetric`、`SkeletonRows` 等有限变体；骨架尺寸贴近最终布局，使用 token、`aria-hidden` 和外层 `aria-busy`。仅首次无数据加载显示骨架；保有旧数据的刷新继续显示旧内容并标注刷新，不制造整页跳动。减少动态效果的系统偏好下关闭闪动。

公共样式预计在 `frontend/src/styles/components.css` 增加约 100—160 行，只组合已有 token；两个公共组件及测试约 180—260 行。不得通过写死新色值绕过 token。

### 统一整改原则

- **空态：** 不再用一句居中灰字占满卡片。业务空态必须回答“发生了什么、为什么、下一步是什么”，并给一个主行动；行动去向必须真实存在。
- **密度：** 优先缩短无信息价值的垂直空白，在卡片头加入状态摘要/辅助操作，在主体使用指标组、定义列表或紧凑表格；不靠无意义装饰填充。
- **层级：** 页面标题说明全局目的，卡片标题说明数据域，主数字/主状态最高，辅助解释退后；同类数字统一等宽字、单位、右对齐与小数精度。
- **加载：** 首屏和大块列表采用结构对应的骨架；按钮内异步仍保留短文本加载态；局部请求失败使用 `unavailable` 状态并给重试，不让“—”承担全部解释。
- **对齐：** 卡片网格、表头/数字列、操作列、表单标签与按钮基线统一；窄屏下网格自然降为单列，表格保留横向滚动，不压扁操作区。
- **真实性：** 无数据不绘制假图，不把失败写成暂无数据，不把“无限额”写成异常。所有摘要只来自现有响应字段。

## 页面清单（带文件路径）

### P0-1 用户概览

文件：`frontend/src/features/overview/OverviewPage.tsx`

实际问题：

- “当前账户未配置配额限制（无上限）”和“暂无可统计的用量”都是局部 `Muted` 灰字，既没有明确的正常/待行动语义，也没有通往用量或密钥页的按钮；卡片剩余面积缺少有效信息层级。
- 四块内容纵向串联，前两卡并排、后两卡通栏，正常数据较少时产生大片空白；配额、密钥数、用量、快捷入口之间主次不够鲜明。
- 三个独立请求都用“加载中…”文字；失败只显示“— + 暂不可用”，没有重试动作，加载与不可用的视觉占位和最终内容尺寸不一致。
- 快捷入口使用普通 `<a>`，视觉上是重复的小卡片，信息价值较低且与站内路由体验不统一；入口与指标缺少上下文关联。
- 用量 SVG 固定标签/轨道宽度，窄屏依靠横向滚动；金额与标签对齐尚可，但空数据时整张图卡没有替代行动。

整改：

- 将首屏组织为紧凑的“账户状态摘要”：配额与 Key 作为主指标卡；用量卡与快捷行动形成 2:1 响应式网格，保持当前页面壳和 token。
- 无配额展示为 `positive` 状态，标题明确“当前无配额上限”，说明仍记录消耗，主行动“查看用量明细”；不能暗示用户可自行配置账户级配额。
- 无活跃 Key 时，用量空态主行动“创建第一个 Key”；有活跃 Key 但无花费时，主行动“查看接入指南”或“管理密钥”，并在实施前核实真实路由。
- Key 数为 0 时在指标卡内给“新建 Key”；非零时补充活跃占比/停用数（仅由现有总数与活跃数推导），提高信息密度但不伪造健康判断。
- 首次加载改为指标骨架、图表行骨架和入口块骨架；失败态提供“重试”并保留进入对应详情页的替代入口。
- 快捷入口改用路由 `Link`，压成带简短结果导向说明的行动列表；不新增图标依赖。

预计规模：页面改动约 180—260 行（含删除重复小组件后的净变更约 80—150 行），测试约 80—120 行。

### P0-2 我的密钥

文件：`frontend/src/features/keys/KeysPage.tsx`；关联弹窗与高密度区：`frontend/src/features/keys/CreateKeyModal.tsx`、`frontend/src/features/keys/EditKeyModal.tsx`、`frontend/src/features/keys/KeyControlsSection.tsx`、`frontend/src/features/keys/KeyIntegrations.tsx`

实际问题：

- 空列表只显示“还没有密钥……”一句文字，虽然提到右上角按钮，但空态本身没有按钮，视线和行动分离。
- 首次加载复用空态文字，表格出现时高度骤变；错误和批量反馈使用各自内联样式，层级不统一。
- 表格列多且全部同权重；状态、最近使用、过期时间和操作的扫描优先级不清晰，操作列与数据列在窄屏容易拥挤。
- 页面说明里实时拼接 `keys.length`，加载期间会先显示 0；这会把“尚未加载”误呈现为真实计数。
- 编辑弹窗的高级控制内容多、字段密，接入区有大量内联样式；本波只需统一间距/分组/状态，不重做业务流程。

整改：

- 表格空态使用 `EmptyState`，主按钮直接打开 `CreateKeyModal`，副行动进入真实接入文档；说明创建后会获得一次性明文，降低首次创建疑虑。
- 首次加载展示与表头、5—6 行记录相匹配的表格骨架；加载完成后才在页头显示真实总数，并用小型状态摘要显示活跃/停用分布。
- 加强名称列主层级，前缀作为次级等宽信息；数字/日期对齐，状态保持徽章；操作列固定最小宽度并在窄屏保持可用。
- 把错误、成功、批量选中条收敛为一致的通知与工具条外观，仍保留现有确认和不可逆提示。
- 编辑弹窗只做视觉分区：基础信息、高级控制、危险操作层级清晰；`KeyIntegrations` 的复制反馈和字段对齐统一，不改变明文生命周期。

预计规模：主页面约 140—220 行，弹窗/高级区约 80—140 行，测试约 100—160 行；不改变密钥创建、编辑、撤销 API。

### P0-3 用量与配额

文件：`frontend/src/features/usage/UsagePage.tsx`、`frontend/src/features/usage/KeyUsageAnalytics.tsx`、`frontend/src/features/usage/Heatmaps.tsx`

实际问题：

- 配额为空和活跃密钥为空都只是 `hk-empty` 灰字；没有区分“账户无限额”“未创建 Key”“有 Key 但未产生调用”。
- 页面把配额、汇总、Key 级深度分析三块等权纵排；Key 级分析表单和多块图表很重，首屏主任务不够聚焦。
- 配额和汇总共用一个总 `loading`，首次加载使用文字；某个 Key 汇总失败时整行只显示“汇总不可用”，没有重试或上下文说明。
- Key 级分析未查询时，图表子卡仍显示“输入 API Key 后查询最近 30 天”等灰字，形成多个空白盒套空白盒；查询过程也用文本加载。
- 时间序列、热力图、请求列表的空态文案重复，缺少结果摘要；表格数字虽右对齐，但金额精度、Token 分组和缓存读/写可读性仍可统一。

整改：

- 配额无上限用正向状态卡展示“无限额但持续计量”，行动为查看/管理 Key；无活跃 Key 的汇总空态直接进入创建 Key。
- 在配额与密钥汇总前加入紧凑摘要行：窗口数、活跃 Key 数、当前可汇总 Key 数，全部由已取数据推导；避免再发请求。
- 将总加载拆成匹配现有并行数据的可见区块状态，至少保证配额骨架与表格骨架独立；单 Key 失败给局部“重试本行/刷新汇总”策略，实施时避免 N 次无节制重试。
- Key 级分析的未启动状态合并为一个完整引导区，解释为何需要粘贴 Key、只驻留内存以及操作步骤；查询后才展开热力、时序和请求表，减少空盒叠加。
- 时间序列加载用图表骨架，记录加载用行骨架；零结果使用带调整日期范围/清除筛选行动的 `EmptyState`。
- 统一金额、请求数、Token 和缓存列的格式与对齐；不改变统计口径、UTC 范围或 Key 鉴权方式。

预计规模：三文件约 260—400 行，测试约 140—220 行。

### P0-4 钱包与充值

文件：`frontend/src/features/wallet/WalletPage.tsx`

实际问题：

- 余额在加载时显示“—”，累计充值立即显示 `$0.00`，容易把未知状态和真实零值混在一起；两张指标卡跨列规则导致视觉重量不平衡。
- 充值配置加载、配置失败、无支付渠道均为一行文字；无渠道虽说明联系管理员，但没有明确行动或替代路径。
- 最近订单空态只有“还没有订单”，没有引导回充值操作；订单加载仍是文字，表格出现时跳动明显。
- 充值表单信息层级较平：金额范围、预设金额、渠道、确认说明和提交按钮都挤在一个纵向流里；成功指引与一般提示的视觉区分有限。
- money 页面需要更清楚而不是更花哨；任何视觉改动都不能弱化金额、币种、渠道、待支付与人工确认语义。

整改：

- 余额与累计充值统一指标骨架和真实零值展示规则，补充“可用余额/累计完成充值”的口径说明；卡片在常规宽度等高对齐。
- 充值区按“选择金额—选择渠道—确认创建”形成清晰步骤层级；预设金额保留为快捷操作，当前选择有明确状态，但不改二次确认。
- 无可用渠道使用 `unavailable` 空态，提供进入支持/订单页的真实按钮；若不存在支持路由，只保留可复制/可理解的联系说明，不制造死链接。
- 最近订单空态主行动滚动/聚焦到充值区；表格采用行骨架，状态和金额提高层级，单号退为次要信息。
- 开单成功指引突出“待支付、不会即时到账、下一步”，并保留后端返回内容，不改订单状态语义。

预计规模：页面约 180—280 行，测试约 100—160 行。因涉及 money 展示，实施完成后须进行金额/币种/状态语义专项回归，但不触碰后端 money path。

### P1 管理员控制台总览

文件：`frontend/src/pages/Dashboard.tsx`、`frontend/src/features/dashboard/DashboardMetrics.tsx`、`frontend/src/features/dashboard/OperatorOverview.tsx`

实际问题：

- 身份加载时整个页面返回 `null`，会短暂白屏；指标卡加载显示“…”、不可用显示“—”，没有结构骨架或解释。
- 经营统计卡数量随独立请求到达而变化，网格会跳动；趋势少于两个点时直接消失，告警空态/失败态仅是一行灰字。
- 顶部指标、经营指标、趋势、告警、8 个管线导航卡连续堆叠，卡片外观相近且主次弱，信息密度看似高但扫描路线不清晰。
- 管线入口每张卡重复“阶段/标题/说明”，占用较大面积；导航仍需保留，但可改为更紧凑的编号行动网格。
- `Dashboard.tsx` 用自定义 padding/标题样式，和用户页 `hk-page`/`hk-pagehead` 基线不完全一致。

整改：

- 身份加载期显示页面壳骨架，仍等待权限判定，不提前渲染管理员数据或改变跳转。
- 指标区预留稳定槽位，经营数据按“业务量—质量—健康”分组；请求未完成时显示对应骨架，不因异步顺序重排。
- 趋势无数据使用紧凑 `EmptyState` 并给用量/日志入口；暂无告警用 `positive` 状态表达“当前没有告警事件”，失败态提供重试/告警控制台入口。
- 管线导航压成紧凑两列/多列行动列表，保留阶段编号、名称与一句提示；不改 `PIPELINE_NAV`、导航顺序或路由。
- 页面外层与标题对齐公共页面基线，减少内联重复样式；保持现有 token。

预计规模：三文件约 220—340 行，测试约 120—180 行。

### 公共 UI 基线

文件：`frontend/src/ui/ErrorFallback.tsx`、`frontend/src/ui/StatusBadge.tsx`、拟新增 `frontend/src/ui/EmptyState.tsx`、拟新增 `frontend/src/ui/Skeleton.tsx`、`frontend/src/styles/components.css`

实际问题：

- `frontend/src/ui/` 当前只有路由错误回退和状态徽章等少量基础件，没有 EmptyState、局部错误/重试或骨架屏；页面因此各自定义 `Empty`/`Muted`/`Dash`。
- 全局 `.hk-empty` 仅为大 padding、居中、低对比灰字，无法表达业务零数据、正常无事件、不可用三种语义，也没有标题、描述和行动区域。
- `StatusBadge` 的 `info` 语气仍含硬编码色值；本波不扩展配色 token，实施时仅避免 EmptyState/Skeleton 新增硬编码颜色，不顺带扩大 token 重构范围。
- `ErrorFallback` 已有“结论—说明—行动”结构，可作为 HUAKAI 内部一致性参考，但它是路由级错误，不应直接复用为普通空态。

整改：

- 建立公共状态组件与最小样式 API；迁移本波页面后删除页面内部重复的 `Empty`/`Muted`，`Dash` 仅在确有紧凑降级需求时由公共 unavailable 变体替代。
- 组件测试覆盖标题/说明、路由行动、点击行动、紧凑模式、ARIA、骨架 busy/hidden 与减少动态效果。
- 公共组件保持无业务文案、无业务路由、无请求逻辑；页面负责决定空态原因和下一步。

## 具体实施批次与前置检查

1. 确认双计划已独立产生并完成交叉讨论，Owner 批准合成计划；若优先级或页面边界冲突，以 Owner 选择为准。
2. 记录整改前桌面/窄屏截图与页面状态矩阵：首次加载、真实零数据、正常数据、局部失败；不得用假数据冒充生产事实，可使用测试夹具验证组件。
3. 第一提交只增加公共 `EmptyState`/骨架与测试、公共样式，不迁移业务页；通过组件测试、类型检查和构建。
4. 第二提交迁移概览与密钥，重点验证创建入口、一次性明文、撤销确认和窄屏表格。
5. 第三提交迁移用量与钱包，重点验证状态判别、金额/币种/配额口径、Key 仅驻留内存和失败降级。
6. 第四提交（P1）收口 Dashboard 与视觉一致性，并做全页面截图回归；如 Owner 决定缩小本波，可独立延后，不影响 P0 闭环。
7. 每个提交按项目规则先测试、暂存、执行 Codex 未提交变更审查，再按 S0/S1 门处理；本计划本身不执行任何 Git 操作。

## 成功标准

- 本波涉及的每个页面都具备可验证的四态：加载、真实零数据、正常数据、失败；四态之间不混淆，且不会以“—”或一句灰字作为整块内容的唯一表达。
- 概览无配额、概览无用量、密钥为空、用量无活跃 Key、Key 分析未启动/零结果、钱包无订单、钱包无渠道、Dashboard 无趋势/无告警均有明确标题和说明；需要用户采取行动的状态至少有一个可用按钮，按钮指向真实路由或真实页面动作。
- 首次加载的大指标、表格、图表均使用与最终布局近似的骨架；按钮提交等局部动作仍使用短文本状态。加载完成前不展示误导性的 `0`、`$0.00` 或“暂无”。
- 桌面宽度 1440px 下首屏有效信息密度明显提升：概览核心状态与主行动无需滚动即可看到；同组卡片等高/基线对齐，无因一句空态造成的大块裸白。
- 768px 与 375px 下无页面级横向溢出；允许表格容器内部横向滚动。行动按钮可触达，长 Key 名、前缀、订单号和金额不会覆盖相邻操作。
- 键盘可遍历所有行动；焦点样式沿用现有体系；空态的装饰不进入读屏顺序；加载容器有 `aria-busy`，骨架本身对读屏隐藏；状态不能只靠颜色表达。
- 不新增依赖，不修改路由、导航、布局壳或 token 定义，不产生硬编码新品牌色；代码搜索确认本波页面不再新增局部 `Empty`/`Muted` 克隆。
- 现有创建/编辑/撤销 Key、配额读取、Key 级分析、充值开单及管理员权限跳转行为不变；现有测试、类型检查、构建全部通过，并新增针对状态判别与行动按钮的判别性测试。
- 截图验收至少覆盖每个 P0 页的桌面正常态、桌面空态、375px 空态；钱包另覆盖开单成功指引，密钥另覆盖一次性明文/接入区，用量另覆盖查询后图表态。
- clean-room 验收：成品只使用 HUAKAI 现有 token 和内部组件语言，没有复制参考控制台的源码、独特结构、文案、图标或素材；成熟度通过信息架构与状态完整性实现，不通过“换皮”。

## 爆炸半径

### 可能受影响区域

- 公共 `components.css` 与新增 UI 组件会影响所有迁移调用方；若选择修改现有 `.hk-empty` 而非新增类，可能意外改变大量未纳入本波的后台页面。因此实施应新增命名明确的类，暂不全局重定义 `.hk-empty`。
- 概览、用量都依赖 Key 与配额数据；错误的状态判别可能把请求失败显示为零数据，或把无上限显示为异常。
- 钱包视觉层级若处理不当，可能弱化金额、币种、待支付和人工入账提示；该页按 money 敏感展示回归处理，但不触碰交易逻辑。
- Dashboard 独立请求较多；固定骨架槽位若与最终卡片数量不一致会造成跳动或错误占位，权限加载骨架也不得泄露管理员模块信息给普通用户。
- 表格密度调整可能降低触控目标尺寸或导致窄屏操作不可见；需用最小触控尺寸、内部滚动和操作列验收约束。

### 失败模式与缓解

- **空态按钮成为死链或越权入口：** 实施前逐项核对路由和权限；不可达时改为当前页真实动作或不提供虚假按钮。
- **为了密度而过度拥挤：** 使用响应式分栏与渐进披露；375px 验收失败即回退为单列，不压缩字体到不可读尺寸。
- **骨架造成闪烁或动画不适：** 仅首次无缓存加载显示，设置稳定最小尺寸并尊重 `prefers-reduced-motion`。
- **公共组件过度抽象：** API 只覆盖本波已观察到的状态，不加入推测性插槽；业务状态判断留在页面层。
- **视觉整改改变业务语义：** 以现有请求/状态字段为唯一事实来源，针对未知、零值、失败分别写测试；money、配额、密钥安全路径做专项回归。
- **范围膨胀到全站换皮：** 只迁移清单文件，其他页面沿用旧组件并进入后续路线图；P1 Dashboard 可独立延期，但 P0 不缩水。

## 假设、风险与 Owner 确认点

- 假设现有 `/keys`、`/usage`、接入指南/支持相关路由可作为行动去向；实施必须从实际路由表核实，不能仅凭文案猜测。
- “账户无配额上限”被视为正常、非错误状态；若 Owner 希望引导用户申请/配置配额，需要先确认用户是否有相应权限和真实入口。
- 计划估算包含公共组件、页面迁移与测试，不包含视觉设计稿生产、全站后台页面迁移和跨浏览器自动化基础设施建设。
- 无功能缩水：所有现有入口、数据字段、表格能力、确认流程和失败降级均保留；P1 延后只改变整改批次，不删除 Dashboard 能力。
- clean-room 风险低：本计划仅依据 HUAKAI 内部代码与 Owner 的质感目标，不读取或引用非 MIT 参考项目源码；实施不得以截图临摹或复制外部控制台组件。
- 安全风险低到中：视觉代码本身低风险，但密钥明文、Key 粘贴和充值金额属于敏感展示；必须保持“不持久化/不日志记录”、二次确认及错误归一化边界。
- Owner 需在执行前确认：P0/P1 边界、无上限空态语气、各行动按钮真实去向、Dashboard 是否进入本次整改波，以及双计划合成后的最终实施顺序。
