## 0. 一句话

Go 管线已覆盖 15 步链路里约 13 步、主干扎实,差 7 个洞、都是周级补丁。Rust 不再追求做完整数据面(那要先建一个不存在的控制面、数月级),改做一件别人做不好的事:字节级 TLS/HTTP2 伪装的高性能出站传输。两者通过 **gRPC over UDS** 契约连接 —— 契约设计成**可降级**,Rust 这一跳坏了 Go 自动回退原生 transport、网关照常服务,这就是 Owner「交互不能出问题」的工程答案。

**第一原则:Go↔Rust 契约的可靠性,优先于任何单点性能优化。** 契约若不能可靠处理崩溃、版本不一致、流中断、背压、取消、计费原子性,Rust sidecar 就不进生产主链路。

## 2. Go 管线补 7 个洞

### 2.1 优先级与波次

| 波次 | 洞 | 理由 |
|---|---|---|
| P0 | ② 单请求内重试 + 账号 failover;⑥ 跨池多候选编排 | Go 作「大脑」的核心。不做 = 遇任何上游瞬时错误就丢请求,不是能用的网关 |
| P0 | ④ OAuth token 热路径即时刷新 | 否则 retry/failover 被过期凭据噪音污染,产生无意义上游失败 |
| P1 | ③ 非流式 Anthropic Messages 翻译 | 可见 501 桩;独立包,可与 P0 并行另起 lane |
| P1 | ① 应用层 cloaking 接线 | 差异化强;须在协议翻译 + retry 语义稳定后接,默认 feature flag 保守 |
| P1 | ⑦ bcrypt 鉴权瓶颈(新增) | 真扩展瓶颈;auth 包独立,可并行 lane;修法待定 |
| P2 | ⑤ 调用方 tenant/api-key 限流 | 生产保护必需;先单机内存版 |

②⑥ 一起设计、分 PR 落地(⑥ 是 router 的输入扩展,② 是 handler 的消费方式)。③①⑦ 互相独立、与 P0 不同包,可各起并行 lane。

### 2.2 洞 ② + ⑥ — 单请求内重试 + 账号 failover + 跨池编排【P0】

- **现状**:`internal/router` 用 `NewDefaultRouter()`,只取第一个 pool candidate、单次 attempt;handler 写死 `AttemptSeq: 1`;上游一错就甩客户端。
- **改哪些包**:`internal/router`(替换 DefaultRouter 策略,从 `ResolvedModel.PoolCandidates` 生成多 `AttemptPlan`)、`internal/gatewayhttp`(抽「单次 attempt 执行函数」+ 外包 attempt 循环 + AttemptSeq 用 index)、`internal/pool`、`internal/gateway`、`internal/channelhealth`、`internal/billing`/结算路径、`internal/transport`(后续接 Rust)、`cmd/gateway/wiring.go`。
- **思路**:① 预读缓冲请求体(可重放;超阈值大体标记不可重试)。② router 跨池生成候选序列(排健康/容量/能力/sticky + `AttemptBudget`)。③ handler attempt 循环:每次换候选、排除已失败账号(failover 状态跨 attempt 维护);成功或「已向客户端开始交付」即结束;**交付前**失败才进下一 attempt。④ 错误 taxonomy 前置:上游 5xx/连接超时/TLS失败/429 可重试,401/403 先走洞④刷新再决定,客户端 4xx 不重试。⑤ ClaimGate 幂等键跨 attempt 稳定,一个 client request 只一次最终结算,失败 attempt 释放在途记录。
- **风险【高】**:触及 billing/quota/claim 结算语义 —— **执行前单独报 Owner**;请求体缓冲内存;错误分类不准会打多账号;流开始后禁 failover(硬规则)。
- **回归面**:全部流量。多账号 failover 只结算一次 / 流式中途失败不伪装成 200 / selector 在途计数释放 / 幂等不写多份。
- **估时**:5-6.5 天(②)+ 4-5.5 天(⑥,与②部分重叠)。

### 2.3 洞 ④ — OAuth token 热路径即时刷新【P0】

- **现状**:只有后台 scheduler 刷新;热路径 `CredentialVault.Resolve` 遇过期凭据不同步刷新 → 拿过期 token 打上游 → 401。
- **改哪些包**:`internal/provider`、`internal/credentialworker`、`internal/credentialstore`、`internal/auth`、`internal/gatewayhttp`。
- **思路**:加 `RefreshingCredentialVault` 包装层(不改底层 store 契约)—— resolve 遇 `ErrCredentialExpired` 或临近过期则调 `AccountCredentialRefresher`,刷新后重新 resolve;复用现有 refresh lock/storm controller,同账号同时只一个热刷新(singleflight 语义);与洞②联动:上游 401 若分类为 token 过期 → 同号刷新 + 同号重试一次,刷新失败才换号。
- **风险【高】**:涉及 upstream credential/auth material —— **执行前单独报 Owner**;热路径刷新加延迟;多实例下 refresh lock 须以 store/DB 级语义为准。
- **回归面**:active token 正常 / expired 刷新后 dispatch / 并发 N 请求只触发一次实际刷新 / 401 后同号刷新重试一次。
- **估时**:3-3.5 天。

### 2.4 洞 ③ — 非流式 Anthropic Messages 响应翻译【P1,独立 lane】

- **现状**:`chat_completions_handler.go` 对 buffered Anthropic 响应是 501 桩(流式已真)。
- **改哪些包**:`internal/proto/anthropic`、`internal/proto`、`internal/gatewayhttp`、`internal/gateway`。
- **思路**:实现 Anthropic buffered response parser(status/headers/body → HCSF/canonical,含 content blocks / stop reason / usage / model)→ 复用现有 client response translator 输出给调用方。非 2xx 走错误 taxonomy,不当成功翻译;buffer 有大小上限 + 502/413 映射。
- **风险**:低-中。content block 形态多(tool_use/empty 易漏);usage 缺失时计费走缺失/估算策略不静默成功。
- **估时**:2.5-3.5 天。

### 2.5 洞 ① — 应用层 cloaking 接线【P1】

- **现状**:`ApplyMimicryPlan` / system rewrite / cache_control / 工具名改写全实现,但只有测试调用 = 死代码;真实出站 body 原样转发。
- **改哪些包**:`internal/gatewayhttp`、`internal/gateway`、`internal/proto/*`、`internal/provider`、policy/config 读取路径。
- **思路**:加 `MimicryPolicyResolver`(输入 tenant/model/vendor/account/protocol/risk mode → 输出 `MimicryPlan`);接线点在**协议翻译之后、dispatch 之前**,只改 provider-bound body,原始 client body 仍用于幂等/审计摘要;streaming 与 non-streaming 同一 planner;默认 feature flag 保守(per-tenant/per-provider 开,默认 no-op);审计只记启用了哪些 step / profile id / body hash,禁记 prompt/tool schema/credential。
- **风险**:cloaking 改 body 可能变模型行为/token 数/cache 命中;接错位置会破坏幂等;按 vendor 分阶段开。
- **估时**:2.5-3.5 天。

### 2.6 洞 ⑦ — bcrypt 鉴权瓶颈【P1,新增,独立 lane】

- **现状(已核实)**:`backend/internal/auth/api_key_resolver.go:135` —— 每个入站请求按 16 字符 prefix 查 ≤5 候选行,逐行 `bcrypt.CompareHashAndPassword`(`MaxBcryptFanout=5`)。bcrypt cost 10 ≈ 每次 50-100ms CPU,高并发下吃满 CPU、压死单机吞吐。
- **根因**:bcrypt 为**低熵密码**设计(故意慢以抗暴破);API key 是**高熵随机串**,根本不需要 bcrypt 的慢。
- **修法(待定,另开 #10 平行 + Owner 确认)**:
  - 方案 A(创可贴):验证结果 LRU 缓存 + TTL。冷路径仍付 bcrypt;有吊销延迟(撤销的 key 缓存内仍有效到 TTL)= 安全副作用。
  - 方案 B(根治):API key 改存快哈希(SHA-256/HMAC),登录变一次索引精确查、零 bcrypt、无 fanout。可平滑迁移(加列,下次成功鉴权时手上有明文、顺手补快哈希,旧 key 自然过渡,无 flag day)。**动 auth 核心 + DB schema = 高风险,需 Owner 确认。**
- **改哪些包**:`internal/auth`、`internal/db/auth`、(方案 B)`sql/migrations`。
- **估时**:方案 A ≈ 1-1.5 天;方案 B ≈ 3-4 天(含迁移)。修法定了再估准。

### 2.7 洞 ⑤ — 对调用方 tenant/api-key 限流【P2】

- **现状**:无按 tenant/api-key 的 QPS/并发 gate(`internal/rate` 偏上游账号 cooldown,不是调用方限流)。
- **改哪些包**:`internal/auth`、`internal/gatewayhttp`、新包 `internal/callerlimit`、`cmd/gateway`;(阶段 B)`sql/migrations`。
- **思路**:阶段 A 无 schema 内存版,默认 disabled —— `APIKeyResolver` 出 tenant/api-key id 后进 `CallerLimiter`,对 `(tenant_id, api_key_id)` 做 token-bucket QPS + weighted-semaphore 并发(streaming 占并发到响应结束/取消);policy 来自 config,未配置不限制;超限 429 + Retry-After。阶段 B(Owner 批准 schema 后)持久/分布式策略,多实例强一致须 Redis/PG advisory lock。
- **风险**:内存版只保护单实例(文档/UI 须明确标注、不夸大);streaming 长连接占并发,配置过低误伤。
- **估时**:阶段 A 2-3 天;阶段 B 3-6 天(取决于 Owner 是否批 schema)。

## 3. Rust core_gateway 重定位为传输 sidecar

### 3.1 保留并强化

L1/L2 TLS/HTTP2 伪装(核心价值)、连接池、流式 relay、传输超时(P6:connect/TLS/header/body-idle/downstream-write)、过载保护(P4)、`/healthz` `/metrics`、自研 serve loop + SIGTERM(P6)。

### 3.2 退役 / legacy 化(不直接删码,先退到 legacy feature/bin)

`account_planner`(账号选择归 Go)、`route.proto` 的 `RouteService`(Go 没这个控制面、实现它就把 Rust 又推回完整数据面)、`route_client` 调 CP、`attempt_reporter` 上报 CP(降为非权威 local metrics)、对外 `listener` client API(入口归 Go gatewayhttp)、Rust 解析 tenant/model header 决定 route。

### 3.3 最终形态

```text
Client
  → Go gatewayhttp
       鉴权 / 调用方限流 / 协议翻译 / 账号路由
       凭据解析+热刷新 / 应用层 cloaking / 重试+failover / 计费
       → Rust transport sidecar  (gRPC over UDS)
            TLS/H2 伪装 / 代理 / 连接池 / 传输超时 / 流式 relay
       ← 响应流回 Go
     usage 抽取 / 响应翻译 / 结算
  ← Client
```

Rust binary 启动 mode 明确为 `transport-sidecar`;Docker 不暴露 public 端口,只暴露 UDS。

## 4. Go ↔ Rust gRPC-over-UDS 契约【命脉】

### 4.1 可降级核心设计(「交互不能出问题」的工程答案)

Rust 传输层是 Go `transport.Factory` 的一个 backend,与现有「standard」Go 原生 transport 并列。Rust 不可达/崩溃/版本不符 → Go **默认自动回退 standard transport**(打 metric + audit),网关功能不受影响、只损失这一跳的伪装增强。Go↔Rust 这条缝**永远不是关键路径上不可缺的一环**。

例外:强伪装 profile 可逐 profile 标 `mandatory` —— 这类 attempt 不许静默降级,Rust 不可用就 fail-fast 进 retry/failover。

### 4.2 正常路径

Go 调 Rust 前必须已完成:客户端鉴权 → 调用方限流 → 模型 resolve → route plan + attempt 选择 → 池内账号选择 → 凭据 resolve/热刷新 → 协议翻译 → 应用层 cloaking → retry budget/deadline 计算。Go 交给 Rust 的是「已完全指定的上游请求」。

### 4.3 契约草图(v1)

```text
TransportRequest v1
  contract_version / request_id / attempt_seq
  tenant_id(仅指标/审计标签,可脱敏)
  provider / provider_account_id(Rust 不据此取凭据,只用于池隔离/指标)
  upstream_method / scheme / authority / path_query / headers(含 Authorization,日志强脱敏)
  body_stream
  response_mode(buffered / sse / raw)
  deadline_unix_ms / connect_timeout_ms / header_timeout_ms / body_idle_timeout_ms
  transport_profile_ref / profile_params(只传 profile 安全参数,不传 prompt)
  proxy_ref / required_features(如 h2_profile / boring_tls / sni_strategy)

TransportResponse v1
  response_headers / body_stream
  terminal_state(complete / upstream_error / transport_error / cancelled)
  transport_error_class / upstream_status
  bytes_from_upstream / bytes_to_go / timing_breakdown / profile_applied
```

边界硬约束:Rust 不选账号、不读 DB、不刷凭据、不做最终 usage/billing 判断、不直接向 client 写响应;Go 必须看到完整 response 字节流**或**明确 terminal error。

### 4.4 九个失败模式 × 应对

| # | 失败模式 | 应对 |
|---|---|---|
| ① | Rust 未启动/崩溃/不可达 | Go sidecar client 维护 health cache + circuit breaker;dial timeout 50-100ms;默认回退 standard transport;`mandatory` profile 则 fail-fast 进 failover。禁无限等待;禁流开始后再回退 |
| ② | Go/Rust 版本不符 | 契约带 `contract_version` + `capabilities`;Go 启动 + 周期 `GetCapabilities`;optional 字段未识别忽略;required feature 未识别 → `unsupported_contract` → 回退/fail-fast |
| ③ | 流式中途失败 | Rust 流必须有 terminal state;Go 不把「EOF 但无 complete terminal」当成功;失败在写 client header 前 → 可换 attempt;已写出后 → 不重试、结算进 ambiguous/partial、审计记 `stream_terminal_missing` |
| ④ | 背压 | gRPC HTTP/2 flow control + bounded message;Rust relay channel 深度小值(1-16),无界队列禁;Go 读 Rust 节奏绑定写 client 节奏 |
| ⑤ | 超时归属 | Go 拥有整体 deadline + retry budget,为每 attempt 算 `attempt_deadline` 传 Rust;Rust 只持 connect/TLS/header/body-idle/downstream-write 子超时,且被 Go deadline 截断 |
| ⑥ | 错误分类 | Rust 回结构化 `transport_error_class`,见 §4.5;未知类 Go 保守按不可重试 |
| ⑦ | 取消传播 | client context 是根 cancel;Go 检测 client 断连 → 取消 attempt context → gRPC cancel 传到 Rust → Rust abort 上游 + 释放连接/凭据;记 `cancelled_by_go`,不计费 |
| ⑧ | 计费-传输原子性 | **Go 持计费权**;Rust 纯传输、响应字节原样回 Go,Go 抽 usage;无 terminal 的 EOF 不算成功;Rust advisory metrics 不作收费依据 |
| ⑨ | 进程生命周期 | Docker 监督 Rust(`restart: unless-stopped`),Go 不 fork Rust;Go 运行时探测 sidecar;Rust SIGTERM 优雅停机(P6)保证重启排空在途 |

### 4.5 Rust → Go 错误分类表

| Rust error class | retry/failover 建议 |
|---|---|
| `dns_error` / `connect_timeout` | 可换 attempt,健康降权 |
| `tls_handshake_failed` | 可换 attempt;降权 profile/proxy |
| `upstream_header_timeout` | 可重试,受幂等/未交付限制 |
| `upstream_body_idle_timeout` | 未交付可重试;已交付 → ambiguous 不重试 |
| `upstream_429` | 记 cooldown,换 account/pool |
| `upstream_5xx` | 按 policy 重试 |
| `upstream_401_403` | 先触发热刷新(洞④)或 account disable;不盲目多池打满 |
| `profile_unsupported` / `contract_mismatch` | 回退或 fail-fast,不重试同 sidecar/版本 |
| `sidecar_overloaded` | 回退 Go native 或快速 503;不扩大到更多 Rust attempt |

### 4.6 Docker 拓扑

双容器、同 compose、同机 UDS:`huakai-gateway-go` 与 `huakai-transport-rust` 共享 named volume `/var/run/huakai`,Rust 绑 `unix:///var/run/huakai/transport.sock`(mode 0660,同组访问)。不同容器 → 便于单独限 CPU/mem/FD;不跨主机(跨主机要 mTLS + 凭据传输策略,后置 Enterprise 选项)。

## 6. 分阶段执行

| Phase | 内容 | 估时 | 依赖 |
|---|---|---|---|
| 0 | 本权威稿 + Go↔Rust gRPC 契约 spec 草案(只写 spec 不实现) | 2-3 天 | Owner 过目 |
| 1 | Go P0:洞②⑥ 重试/failover/跨池 | 5-8 天 | Owner 确认 billing 改动范围 |
| 2 | Go P0:洞③ Anthropic buffered + 洞④ OAuth 热刷新 | 4-6 天 | Phase 1 的 retry taxonomy |
| 3 | Go P1:洞① cloaking + 洞⑤ 调用方限流 + 洞⑦ bcrypt | 6-9 天 | 洞⑦ 修法先 #10 平行定 |
| 4 | Rust sidecar 最小 transport API(`Forward`/`GetCapabilities`/`Health`,UDS,gRPC) | 5-7 天 | Phase 0 契约 |
| 5 | Go↔Rust 集成 + 9 失败模式 gates | 6-9 天 | Phase 1 错误 taxonomy + Phase 4 |
| 6 | Docker 化(双容器 / UDS volume / healthcheck / restart) | 2-4 天 | Phase 5 最小闭环 |

**总估时 ≈ 7-11 周。** Phase 1-3 是 Go-only,期间已做的 Rust C 档稳定不动、无 churn。Phase 1 单独交付就是一个正确网关里程碑。

依赖主线:`Phase 0 → Phase 1 → {Phase 2, Phase 4} → Phase 5 → Phase 6 → Phase 7`;Phase 3 在 Phase 1 的 attempt executor 形态稳定后可并行。

**为什么先 Go 后 Rust**:Rust sidecar 只能转发 Go 已选好的账号和凭据;Go 仍单 attempt / 无热刷新 / 无响应翻译时,Rust 接进来只是把缺口外包到另一个进程;且 Go 的 retry/错误 taxonomy 是 Rust 契约的消费方,必须先成形。
