# Gap Design: Per-request relay log subsystem

_Author: HUAKAI senior backend architect_
_Date: 2026-06-03_
_Status: READY FOR IMPLEMENTATION_

---

## Summary

**Current state (verified in codebase):** `usage_records` is the immutable Tx2
money-path table that carries token counts, cost, and timing columns. It is
accessible to relay-key callers only through `GET /v1/me/usage`
(`internal/meusagehttp`), which surfaces billing-aggregate records. No separate
per-request "relay log" table exists, and the billing query
(`ListUsageRecords` in `sql/queries/observability.sql`) folds channel, user,
group, quota, and latency fields together with money fields in a single
read path whose primary contract is billing correctness, not log search.

**Gap:** The reference behaviour (one-api `model/log.go:80`,
`router/api.go:107`; Portkey `src/handlers/services/logsService.ts:165`) is a
**separate, write-once per-request log row** that carries:

- model (requested + upstream), channel/provider, user identity, api-key, group
- token counts (input, output, cache-creation, cache-read), latency (TTFT ms,
  total ms), quota hint (was request quota-denied?), endpoint family, stream flag
- user-searchable: filter by model, channel, time range, relay-key (self); paginate
  with keyset cursor; relay-key callers may only see their own rows

**What HUAKAI needs:**

1. A new table `relay_request_logs` — one row per completed relay request,
   written at Tx2 settle time inside the billing settler, populated entirely from
   fields already present in `billing.SettleRequest` and `gateway.UsageRecordDraft`.
   No credentials, no raw upstream payloads.
2. New sqlc queries for insert and list/search.
3. A new service package `internal/relaylog` — domain types and the writer
   interface.
4. A new HTTP handler package `internal/relayloghttp` — `GET /v1/me/logs`
   (relay-key auth, self-scope only).
5. Migration `0077_relay_request_logs.up.sql`.
6. Wire-up: `billing.DefaultSettler` receives a `relaylog.Writer` and calls it
   inside Tx2; `cmd/gateway/routes.go` mounts the new handler.

No new files in FROZEN packages (`internal/gatewayhttp`, `internal/gateway`,
`internal/proto`). The existing `internal/billing` is modified minimally (add
`RelayLogWriter` field to `DefaultSettler`, call it in `Settle`). The existing
`internal/meusagehttp` is unchanged; the new endpoint is `/v1/me/logs`, not
`/v1/me/usage`.

## Package layout

All files are kept under 500 lines; all functions under 80 lines.

```
internal/relaylog/
    types.go          (~80 ln)   Domain types: LogRecord, Writer interface,
                                 filter/pagination params. No DB or HTTP imports.
    writer.go         (~120 ln)  PostgreSQL-backed WriterImpl; wraps
                                 dbrelaylog.Queries. Single public method:
                                 Write(ctx, LogRecord) error.
    writer_test.go    (~140 ln)  Discriminating unit tests (see §Discriminating tests).

internal/relayloghttp/
    handler.go        (~260 ln)  GET /v1/me/logs handler. Auth via AuthResolver
                                 (same interface as meusagehttp). Parses query
                                 params (from/to/cursor/limit/model/channel),
                                 calls relaylog.Reader, maps rows to JSON.
    cursor.go         (~80 ln)   Keyset cursor encode/decode (base64+JSON,
                                 same pattern as meusagehttp.usageCursor).
    handler_test.go   (~230 ln)  Discriminating tests for filter, pagination,
                                 auth rejection, and tenant isolation.

internal/db/relaylog/           (generated by sqlc, not hand-written)
    query.sql.go                 Generated from sql/queries/relay_log.sql.
    models.go                    Generated row structs.

sql/queries/relay_log.sql       (~90 ln)   InsertRelayLog, ListRelayLogs sqlc queries.
sql/migrations/
    0077_relay_request_logs.up.sql   (~70 ln)  CREATE TABLE + indexes.
    0077_relay_request_logs.down.sql (~10 ln)  DROP TABLE.
```

Every file is under 500 lines. The writer, HTTP handler, cursor helper, and
domain types are each in their own file so no single file accumulates multiple
responsibilities.

## Schema / migrations

### Migration 0077_relay_request_logs.up.sql

```sql
-- HUAKAI relay log subsystem.
-- One row per settled relay request; written inside Tx2 by billing.DefaultSettler.
-- Immutable after insert (no UPDATE path; reconciliation appends separate rows).
-- CMB invariants: credentials and raw upstream payloads NEVER stored here.
-- Money amounts are NOT stored here (use usage_records for billing).

BEGIN;

CREATE TABLE IF NOT EXISTS relay_request_logs (
    id                  bigserial       PRIMARY KEY,
    tenant_id           bigint          NOT NULL REFERENCES tenants(id),
    -- Request identity
    request_id          text            NOT NULL,   -- logical_request_id from billing_ledger_claims
    claim_id            bigint          NOT NULL REFERENCES billing_ledger_claims(id),
    api_key_id          bigint          NOT NULL,
    user_id             bigint          NOT NULL,
    user_group          text            NOT NULL DEFAULT '',
    -- Channel / provider
    provider            text            NOT NULL DEFAULT '',  -- provider code, e.g. "openai"
    channel_id          bigint,                               -- provider_account_id
    -- Model
    requested_model     text            NOT NULL,
    upstream_model      text            NOT NULL DEFAULT '',
    endpoint_family     text            NOT NULL DEFAULT '',  -- 'chat','messages','openai_responses'
    stream              boolean         NOT NULL DEFAULT false,
    -- Token counts (mirrored from usage_records; no money fields)
    tokens_input        integer         NOT NULL DEFAULT 0,
    tokens_output       integer         NOT NULL DEFAULT 0,
    cache_creation_tokens integer       NOT NULL DEFAULT 0,
    cache_read_tokens   integer         NOT NULL DEFAULT 0,
    -- Latency
    first_token_latency_ms bigint       NOT NULL DEFAULT 0,
    total_latency_ms    bigint          NOT NULL DEFAULT 0,
    -- Outcome
    end_class           text            NOT NULL DEFAULT '',
    quota_denied        boolean         NOT NULL DEFAULT false,
    -- Timestamps
    requested_at        timestamptz     NOT NULL,
    settled_at          timestamptz     NOT NULL DEFAULT now()
);

-- Relay-key self-serve search: filter by api_key_id + time range.
CREATE INDEX IF NOT EXISTS idx_relay_logs_key_settled
    ON relay_request_logs (tenant_id, api_key_id, settled_at DESC, id DESC);

-- Model filter.
CREATE INDEX IF NOT EXISTS idx_relay_logs_key_model_settled
    ON relay_request_logs (tenant_id, api_key_id, requested_model, settled_at DESC, id DESC);

-- Admin cross-tenant queries.
CREATE INDEX IF NOT EXISTS idx_relay_logs_tenant_settled
    ON relay_request_logs (tenant_id, settled_at DESC, id DESC);

COMMENT ON TABLE relay_request_logs IS
    'Per-request relay log row. Written at Tx2 settle. Immutable. '
    'No credentials, no raw upstream payloads (CMB invariant).';

COMMIT;
```

### Migration 0077_relay_request_logs.down.sql

```sql
BEGIN;
DROP TABLE IF EXISTS relay_request_logs;
COMMIT;
```

## Invariants honored

**CMB-1 (credentials never logged):** `relay_request_logs` stores no credential
fields. The `api_key_id` is an internal surrogate; the plaintext bearer is never
present. The writer receives a `LogRecord` that has no credential or raw payload
fields. This is enforced by the type system: `relaylog.LogRecord` has no
`[]byte` payload fields.

**CMB-5 (raw upstream payloads never logged):** `LogRecord` carries token counts
and latency only. Request/response bodies are absent. The writer cannot log what
it is never given.

**CMB-2 (router reads no credentials, writes nothing):** The log write is
performed by `billing.DefaultSettler` inside Tx2, not the router or
`gatewayhttp`. The router layer is untouched.

**Fail-closed on ambiguity:** If `relaylog.Writer.Write` returns an error, the
settler logs the failure via `privacy.LogSystem` and continues — the log row is
best-effort observability and must not abort a committed billing transaction.
This is the same pattern as the audit ledger DLQ path in `submitAuditLedgerEntry`.

**Tx2 atomicity is preserved:** The relay log write happens *after* the Tx2
commit of `usage_records` + `billing_events`. It is NOT inside the Tx2
serializable transaction (to avoid extending the serializable lock scope). The
pattern is: Tx2 commits successfully → settler calls `relaylog.Writer.Write`
outside the transaction → error is logged but not propagated to the caller.
This is explicit in the `Settle` return: money-path correctness is never gated
on the relay log write succeeding.

**Tenant isolation (self-scope):** `ListRelayLogs` always filters on
`(tenant_id, api_key_id)` from the resolved `auth.Identity`. The caller cannot
supply their own `api_key_id` filter; it is hardcoded from the auth result.

**Money fields excluded:** The relay log row stores NO cost fields
(`actual_cost`, `predicted_cost`, etc.). Billing figures remain the exclusive
domain of `usage_records`. This prevents confusion between the log view
(latency/model/token observability) and the billing view (money, reconciliation).

**Modularity:** `internal/relaylog` and `internal/relayloghttp` are entirely new
packages. The FROZEN packages (`internal/gatewayhttp`, `internal/gateway`,
`internal/proto`) receive zero new files. The only modification to an existing
package is a single optional field `RelayLogWriter relaylog.Writer` added to
`billing.DefaultSettler` (the unexported struct that implements `billing.Settler`),
with a nil-guard so existing tests pass without wiring.

## Discriminating tests

Each test is structured so that introducing the specific defect it guards
against causes the test to fail. A trivially-passing test is not acceptable.

### relaylog package

**`TestWriter_WritePersistsAllFields`**
Inserts a `LogRecord` with every field populated, then reads back the row via
`SELECT *`. Asserts each field matches exactly (including `user_group`,
`first_token_latency_ms`, `total_latency_ms`, `end_class`, `quota_denied`).
Defect guarded: field silently dropped from the INSERT query.

**`TestWriter_TenantIsolation`**
Two tenants with overlapping `api_key_id` values (by construction in the test
DB). After writing one log for tenant A, verifies that a `ListRelayLogs` call
scoped to tenant B returns zero rows. Without the `tenant_id` filter in the
query, this test fails.

**`TestWriter_NilDoesNotPanic`**
Calls `billing.DefaultSettler.Settle` with `RelayLogWriter = nil`. Asserts no
panic and a successful settle outcome. Defect guarded: nil-dereference when
relay log is not wired.

### relayloghttp package

**`TestHandler_AuthRejectsUnknownBearer`**
Sends `Authorization: Bearer sk-unknown` to `GET /v1/me/logs`. Expects HTTP
401. Without the `validBearerFormat` check the test passes with 200, so the
test fails if the guard is removed.

**`TestHandler_SelfScopeOnly`**
Creates two API keys for the same tenant. Logs rows for key A. Authenticates as
key B. Expects the response `items` array to be empty (not key A's rows).
Defect guarded: handler uses `ident.TenantID` only, ignoring `ident.APIKeyID`.

**`TestHandler_ModelFilter`**
Inserts three log rows: two with `requested_model = "gpt-4o"`, one with
`"claude-3-5-sonnet"`. Queries with `?model=gpt-4o`. Expects exactly two items.
Defect guarded: model filter not applied in SQL.

**`TestHandler_CursorPaginates`**
Inserts 5 rows for the same key with distinct `settled_at` timestamps. Requests
`limit=3`, asserts 3 items returned and `next_cursor` non-empty. Follows cursor,
asserts remaining 2 items and empty `next_cursor`. Defect guarded: cursor
off-by-one or cursor never terminates.

**`TestHandler_InvalidCursorRejects400`**
Sends `?cursor=notbase64!!`. Expects HTTP 400 with code `"invalid_cursor"`.
Defect guarded: handler ignores cursor parse error and silently returns all rows.

**`TestHandler_DependencyNilReturns503`**
Constructs handler with `Deps{Store: nil}`. Expects HTTP 503. Defect guarded:
nil dereference rather than graceful 503.

**`TestCursor_RoundTrip`**
Encodes a cursor with known `settled_at` and `id`, decodes it, asserts exact
field equality. Also tests that a cursor with wrong `k` field returns an error.
Defect guarded: cursor kind field not validated, allowing cross-endpoint cursor
confusion (the meusagehttp cursor kind is `"me_usage"`; relay log cursor must
use `"relay_log"`).

## Parity-or-better vs reference

### one-api `model/log.go` (songquanpeng/one-api@8df4a2670b98:model/log.go:80)

**Behavior:** One row per completed relay request. Fields include channel ID,
token input/output, model name, user ID, type (text/image/etc.), prompt/completion
token split, elapsed time (ms), quota consumed.

**HUAKAI parity:** `relay_request_logs` carries all equivalent fields:
`channel_id` (= `provider_account_id`), `tokens_input`, `tokens_output`,
`requested_model` + `upstream_model`, `user_id`, `first_token_latency_ms` +
`total_latency_ms`. Quota consumption is represented via `end_class` and the
`quota_denied` boolean (better than one-api which uses a numeric `quota` field
that doubles as both token cost and denial signal).

**Better:** HUAKAI adds `user_group`, `cache_creation_tokens`, `cache_read_tokens`,
`endpoint_family`, `stream`, and `request_id` (traceable to trust-chain audit
entries). one-api's log row has no cache token breakdown.

### one-api `router/api.go` (songquanpeng/one-api@8df4a2670b98:router/api.go:107)

**Behavior:** `GET /api/log` — user self-serve log list, filtered by token_name,
model, start_timestamp, end_timestamp; page + per_page offset pagination.

**HUAKAI parity:** `GET /v1/me/logs` with `from`/`to`/`model`/`channel`/`limit`
filters. Auth is relay-key (`hk_live_…`) rather than session cookie; same
self-scope guarantee.

**Better:** HUAKAI uses keyset cursor pagination (stable under concurrent inserts,
no offset drift) instead of page+offset (which drifts when new rows arrive).

### Portkey `src/handlers/services/logsService.ts` (Portkey-AI/gateway@d2ea41f4e1:src/handlers/services/logsService.ts:165)

**Behavior:** Log search service with filter by model, provider, status, metadata;
returns paginated log items with request latency, token counts, and metadata.

**HUAKAI parity:** Equivalent filter fields (`model`, `channel`/provider, `from`,
`to`). Token counts and latency in response items. Cursor pagination maps to
Portkey's offset-based pagination with HUAKAI's keyset improvement.

**HUAKAI intentional omission:** Portkey logs raw request/response bodies (metadata
payloads). HUAKAI deliberately omits these to honor CMB-5. The log row carries
observability signals (tokens, latency, model) without payload content.

## Risks

**R1 — Tx2 log write failure causes no alerting by default.**
The relay log write is best-effort (outside Tx2). A persistent DB error could
silently drop log rows with no operator signal. Mitigation: `privacy.LogSystem`
with `SeverityError` on write failure, plus a Prometheus counter
`relay_log_write_errors_total` incremented on failure. A runbook alert on this
counter closes the gap.

**R2 — sqlc regeneration breaks existing generated code.**
Adding `sql/queries/relay_log.sql` and running `sqlc generate` regenerates all
packages under `internal/db/`. If any existing generated file has a hand-edit
or if the sqlc config lists a non-existent query file it errors. Mitigation:
add the new query file to `sqlc.yaml` under a separate `output` stanza pointing
to `internal/db/relaylog/` so it generates into a new package, not the existing
`internal/db/billing/` or `internal/db/auth/` packages.

**R3 — `api_key_id` self-scope is the only isolation boundary.**
If the resolver returns an incorrect `api_key_id` (e.g. auth misconfiguration
where `APIKeyID = 0`), all rows for the tenant become visible. Mitigation:
add a guard in the handler: if `ident.APIKeyID <= 0`, return 503
`"gateway_not_configured"`, same pattern used in `meusagehttp.NewHandler`.

**R4 — Table grows unboundedly in high-volume tenants.**
`relay_request_logs` has no TTL or partition. At 10k req/s per tenant, one month
of rows = ~26B rows. Mitigation: add a `COMMENT` noting the table requires a
per-tenant retention policy (matching `usage_records`). Phase-1 implementation
leaves TTL to a follow-up migration; the gap design documents this as a known
debt.

**R5 — Latency fields sourced from `UsageRecordDraft` only cover stream path.**
`TotalDurationMillis` and `FirstTokenLatencyMillis` are populated by the
streaming forwarder (`internal/gateway/forwarder.go:247,510`). For non-streaming
requests these are 0 unless the caller computes elapsed time before settling.
Mitigation: the settler measures wall-clock elapsed from `SettleRequest.RequestedAt`
to settle time as a fallback `total_latency_ms` when `Draft.TotalDurationMillis == 0`.

**R6 — Relay-key auth is already implemented; no new auth path needed.**
The `auth.APIKeyResolver` resolves `hk_live_…`/`hk_test_…` bearers.
`meusagehttp.AuthResolver` is the same interface. `relayloghttp` reuses this
identical interface — no new auth code required, only injection. If the resolver
interface changes in a future refactor both packages break together (desired
coupling).
