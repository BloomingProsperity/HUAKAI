# Gap Design: Per-API-Key Quota Cap + Group + Batch Revoke + Secure Reveal

**Design date:** 2026-06-03  
**Author:** Senior HUAKAI Backend Architect (design pass)  
**Status:** Implementation-ready — awaiting dispatch  
**Migration range:** 0077–0078 (current max: 0076)

---

## Summary

HUAKAI's `userkey` / `userkeyhttp` packages already implement create-read-revoke for
API keys with per-key expiry and one-time plaintext issuance. Four commercial gaps remain:

1. **Per-key spend/quota cap with calendar-window reset** — key holders can be capped
   independently of the user-level quota engine already wired in `internal/quota`.
2. **Key group assignment** — keys can be tagged to a named group so the inbound
   resolver can apply group-scoped policies (routing, rate-limit, quota) without the
   caller knowing the routing topology.
3. **Batch revoke** — a single authenticated call revokes N keys atomically, with audit.
4. **Secure full-key reveal** — a step-up-gated endpoint returns the stored `key_hash`
   for operator-level forensic use; the plaintext is re-derived only by bcrypt — the
   design clarifies what "full reveal" means in a bcrypt world and delivers the correct
   alternative: a signed short-lived reveal token that re-hashes to a known hash so the
   client can verify ownership without the platform ever recovering plaintext.

All four sub-features live in **two new packages** (`userkeycontrols` and
`userkeycontrolshttp`) plus **two numbered migrations** (0077, 0078) and a set of
discriminating integration tests. The `quota` engine is consumed, not extended; the
`auth` resolver gains a read-only lookup for `key_group_id` via a migration-only column
add to `api_keys` and a generated sqlc query update.

## Schema / migrations

### Migration 0077 — api_keys extended columns

**File:** `sql/migrations/0077_api_key_controls.up.sql`

Adds four columns to `api_keys` and two new tables:

```sql
BEGIN;

-- 1. api_keys: group membership + quota policy link
ALTER TABLE api_keys
    ADD COLUMN IF NOT EXISTS key_group_id   bigint,
    ADD COLUMN IF NOT EXISTS quota_policy_id bigint;

-- key_group_id → api_key_groups(id) FK added after table exists (below).
-- quota_policy_id → quota_policies(tenant_id, id) composite FK added below.

-- 2. Table: api_key_groups
--    Named tag set for keys; groups are tenant-scoped label entities.
--    Purpose: inbound resolver stamps Identity.KeyGroupID so the pool-routing
--    and quota engines can enforce group policies without reading the full key row.
CREATE TABLE IF NOT EXISTS api_key_groups (
    id           bigserial   PRIMARY KEY,
    tenant_id    bigint      NOT NULL REFERENCES tenants(id),
    name         text        NOT NULL,
    description  text        NOT NULL DEFAULT '',
    enabled      boolean     NOT NULL DEFAULT true,
    created_at   timestamptz NOT NULL DEFAULT now(),
    updated_at   timestamptz NOT NULL DEFAULT now(),
    deleted_at   timestamptz,
    CONSTRAINT uq_api_key_groups_tenant_id_id UNIQUE (tenant_id, id)
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_api_key_groups_tenant_name
    ON api_key_groups (tenant_id, name)
    WHERE deleted_at IS NULL;
CREATE INDEX IF NOT EXISTS idx_api_key_groups_tenant_enabled
    ON api_key_groups (tenant_id, enabled)
    WHERE deleted_at IS NULL;

COMMENT ON TABLE api_key_groups IS
    'Named API key groups (0077). keys carry key_group_id; resolver stamps '
    'Identity.KeyGroupID for downstream policy dispatch. No plaintext bearers '
    'ever in this table (CMB-5).';

-- 3. FKs back to api_keys
ALTER TABLE api_keys
    ADD CONSTRAINT fk_api_keys_key_group
        FOREIGN KEY (tenant_id, key_group_id)
        REFERENCES api_key_groups (tenant_id, id)
        DEFERRABLE INITIALLY DEFERRED,
    ADD CONSTRAINT fk_api_keys_quota_policy
        FOREIGN KEY (tenant_id, quota_policy_id)
        REFERENCES quota_policies (tenant_id, id)
        DEFERRABLE INITIALLY DEFERRED;

-- 4. Indexes for resolver and admin list queries
CREATE INDEX IF NOT EXISTS idx_api_keys_group
    ON api_keys (tenant_id, key_group_id)
    WHERE deleted_at IS NULL AND key_group_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_api_keys_quota_policy
    ON api_keys (tenant_id, quota_policy_id)
    WHERE deleted_at IS NULL AND quota_policy_id IS NOT NULL;

COMMIT;
```

**Down migration** `0077_api_key_controls.down.sql`: drops FKs, drops `api_key_groups`,
drops the two columns (in correct FK-drop-before-column-drop order).

### Migration 0078 — reveal_tokens table

**File:** `sql/migrations/0078_reveal_tokens.up.sql`

```sql
BEGIN;

-- Step-up-gated reveal tokens: short-lived, single-use signed tokens that
-- let an authenticated session holder prove key ownership without recovering
-- plaintext. The token embeds api_key_id + an ephemeral nonce; the client
-- can call the resolver with the nonce to confirm it maps to the claimed key.
--
-- CMB-5 invariant: this table stores ONLY the bcrypt hash of the nonce —
-- the nonce plaintext is returned once in the issue response and never stored.
-- Neither key_hash nor bearer plaintext appear here (they are orthogonal).
CREATE TABLE IF NOT EXISTS api_key_reveal_tokens (
    id            bigserial   PRIMARY KEY,
    tenant_id     bigint      NOT NULL REFERENCES tenants(id),
    api_key_id    bigint      NOT NULL,
    user_id       bigint      NOT NULL,
    nonce_hash    text        NOT NULL,        -- bcrypt(nonce); CMB-5
    expires_at    timestamptz NOT NULL,
    used_at       timestamptz,                 -- NULL = unused; set on first verify
    created_at    timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_reveal_tokens_tenant_id_id UNIQUE (tenant_id, id)
);
CREATE INDEX IF NOT EXISTS idx_reveal_tokens_key_expires
    ON api_key_reveal_tokens (tenant_id, api_key_id, expires_at)
    WHERE used_at IS NULL;

COMMENT ON TABLE api_key_reveal_tokens IS
    '0078: step-up reveal nonces. nonce_hash is bcrypt; nonce plaintext is '
    'one-time response only (CMB-5). Reveal does not recover bearer plaintext — '
    'it proves key identity to the session holder.';

COMMIT;
```

**Down migration** `0078_reveal_tokens.down.sql`: `DROP TABLE IF EXISTS api_key_reveal_tokens;`

## Endpoints

All endpoints require the `auth.SessionMiddleware` outer wrapper (session bearer).
The table below lists additional per-endpoint requirements.

| Method | Path | Auth scope | Description |
|--------|------|-----------|-------------|
| `PUT` | `/v1/api-keys/{id}/quota` | session + own key | Set or clear per-key quota cap. Body: `{metric, window_kind, limit_usd, mode}`. Creates or updates a `quota_policies` row with `scope_kind=api_key`, links `api_keys.quota_policy_id`. Uses quota engine's existing policy upsert path. |
| `GET` | `/v1/api-keys/{id}/quota` | session + own key | Read current per-key quota policy. Returns policy view (no bearer, no hash). |
| `PUT` | `/v1/api-keys/{id}/group` | session + own key | Assign or clear key group. Body: `{group_id}` (int64 or null). Validates group belongs to same tenant. |
| `GET` | `/v1/api-keys/{id}/group` | session + own key | Read current group assignment. |
| `POST` | `/v1/api-keys/batch-revoke` | session | Revoke up to `BatchRevokeMaxKeys=50` keys in one call. Body: `{api_key_ids: [...], reason: "..."}`. Returns per-key outcome. Atomic per-key (each key is individually revoked in a single transaction; partial success possible, each result carries `ok`/`already_revoked`/`not_found`). |
| `POST` | `/v1/api-keys/{id}/reveal-token` | session + step-up challenge | Issue a reveal nonce. Body: `{step_up_proof}`. Returns `{reveal_token_id, nonce, expires_at, notice}`. Nonce is shown once (CMB-5 pattern). |
| `POST` | `/v1/api-keys/{id}/reveal-token/verify` | session + own key | Consume (verify) a nonce; marks `used_at`. Returns `{api_key_id, key_prefix, verified: true}`. Does NOT return bearer plaintext — proves key identity only. |

### Step-up for reveal

No existing step-up framework exists in HUAKAI. For the MVP slice the step-up proof is:
the session holder re-presents their **session bearer** (already in Authorization header)
plus a **short-lived HMAC challenge token** issued by the reveal-token endpoint in a
first call with no body. The two-call protocol:

1. `POST /v1/api-keys/{id}/reveal-token` with empty body → `{challenge_token, challenge_expires_at}` (not the nonce yet).
2. `POST /v1/api-keys/{id}/reveal-token` with `{step_up_proof: "<challenge_token>"}` → `{reveal_token_id, nonce, expires_at, notice}`.

The challenge token is HMAC-SHA256 over `(api_key_id || user_id || timestamp)` with a
server-side secret (config key `reveal_challenge_secret`). This is a forward-compatible
design: when a real TOTP/WebAuthn step-up ships, the `step_up_proof` field accepts
either the HMAC-challenge or a TOTP code verified by the same handler via a strategy
interface.

## Invariants honored

| Invariant | How honored |
|-----------|-------------|
| **CMB-5: credentials never logged** | `reveal.go` never logs `nonce`, `nonce_hash`, or any bearer. `IssueRevealResult.String()` redacts nonce using the same pattern as `userkey.IssueResult.String()`. |
| **CMB-5: raw upstream payloads never logged** | Not applicable to this feature (no upstream calls). |
| **CMB-7: router reads no credentials** | `userkeycontrols` is not imported by `gateway`, `gatewayhttp`, or `proto`. The resolver only reads the new `key_group_id` column — not the nonce table. |
| **Fail-closed on ambiguity** | If `quota_policy_id` FK lookup fails at request time, the quota engine defaults to deny (it already does: `ErrStoreNotConfigured` / missing policy = allow-by-default is a ModeObserve outcome; setting `mode=enforce` makes it deny). The reveal handler: missing `reveal_challenge_secret` config → 503, never 200. |
| **Money path Tx1/Tx2** | Per-key quota is enforced through the existing `quota.Service.Reserve` / `quota.Service.Settle` Tx1/Tx2 path. The new `userkeycontrols.SetKeyQuota` call only writes a `quota_policies` row (admin write, not on the request hot-path). No new money-path Tx is introduced. |
| **shopspring/decimal for money** | `SetKeyQuotaRequest.LimitUSD` is `decimal.Decimal`; stored as `numeric(20,8)` via quota_policies.limit_value (existing column). |
| **golang-migrate numbered migrations** | New migrations are 0077 and 0078. Each file has a matching `.down.sql`. |
| **No new files in frozen packages** | `gatewayhttp`, `gateway`, `proto` are not touched. |
| **Modularity / no god-files** | 10 files, largest ~220 lines. Single responsibility per file. |
| **Advisory lock in Issue** | `batch_revoke.go` acquires per-key advisory lock (same `userkey:tenantID:userID` scheme) before each revoke to avoid races with concurrent `userkey.Service.Revoke`. |
| **Ownership enforcement** | Every handler reads `(tenant_id, user_id)` from `SessionIdentity`. All SQL uses `AND tenant_id = $1 AND user_id = $2` guards. Group assignment validates `api_key_groups.tenant_id = session.TenantID`. |
| **Soft-delete / parent-active join** | All queries JOIN `tenants` + `users` with `deleted_at IS NULL AND status='active'` (same pattern as `userkey.Service.List`). |

## Discriminating tests

Each test must fail if the specific defect it defends is removed.

### `userkeycontrols` integration tests (`pg_integration_test.go`)

| Test | Defect defended |
|------|----------------|
| `TestSetKeyQuota_CreatesPolicy_ScopeAPIKey` | If `scope_kind` is set to `user` instead of `api_key`, the policy would apply to all keys of the user. Test asserts `scope_kind = 'api_key'` AND `scope_id = strconv.FormatInt(apiKeyID, 10)`. |
| `TestSetKeyQuota_UpdatesExisting_DoesNotDuplicate` | If upsert logic does an INSERT instead of UPDATE on second call, two rows would exist. Test asserts exactly one `quota_policies` row after two `SetKeyQuota` calls on same key. |
| `TestSetKeyQuota_LimitUSD_Decimal_Precision` | If `decimal.Decimal` is truncated to `float64` before write, sub-cent values lose precision. Test sets `LimitUSD = "0.00000001"` and reads back the exact value from DB. |
| `TestSetKeyGroup_RejectsWrongTenantGroup` | If tenant_id check is absent, a user could assign a group that belongs to a different tenant. Test creates group in tenant-B, calls `SetKeyGroup` as tenant-A; expects `ErrGroupNotFound`. |
| `TestSetKeyGroup_ClearsWithNilGroupID` | If nil group_id is not handled, clearing a group assignment could silently fail. Test sets group, then clears with nil, confirms `key_group_id IS NULL`. |
| `TestBatchRevoke_PartialOwnership_OnlyRevokesOwned` | If ownership check is skipped in batch path, caller could revoke other users' keys. Test mixes own + other-user key IDs; asserts only own keys appear in `revoked` outcome. |
| `TestBatchRevoke_ExceedsMax_Rejected` | If max-size check is absent, unbounded batch could lock many rows. Test sends 51 IDs; expects `ErrBatchTooLarge` before DB access. |
| `TestBatchRevoke_Idempotent_AlreadyRevoked` | If idempotency logic is absent, a second batch revoke could error. Test revokes same set twice; second call returns `AlreadyRevoked=true` for each key, no error. |
| `TestRevealToken_ChallengeRequired_RejectsNoProof` | If step-up check is absent, anyone with a session can issue reveal nonce without re-auth. Test POSTs reveal with empty body; expects `{challenge_token}` back (step 1), not the nonce. |
| `TestRevealToken_ExpiredChallenge_Rejected` | If expiry is not enforced, a replayed challenge works indefinitely. Test uses challenge token with `now() - 6 minutes` (TTL = 5 min); expects `ErrChallengeExpired`. |
| `TestRevealToken_NonceSingleUse` | If `used_at` is not set on verify, nonce can be reused. Test calls verify twice; second call expects `ErrRevealTokenUsed`. |
| `TestRevealToken_NeverReturnsBearerPlaintext` | If reveal response accidentally includes a `key_hash` or any bearer field, CMB-5 is broken. Test asserts response JSON has no `key_hash`, `plaintext`, `bearer`, `secret` keys at any depth. |
| `TestRevealToken_WrongOwner_NotFound` | If ownership check is absent in verify, any session can consume another user's reveal token. Test issues token as user-A, verifies as user-B; expects `ErrRevealTokenNotFound` (same ambiguity policy as ErrNotFound in userkey). |

## Parity-or-better vs reference

All reference comparisons are behavioral only (clean-room policy, docs/05_CLEAN_ROOM_POLICY.md).

| Reference behavior | Reference location (behavior cite) | HUAKAI disposition |
|---|---|---|
| Per-key quota cap with named window (daily/monthly/custom) reconciled against account balance; key holder sees "balance OK but key out" only after window reset | E-OAI-005 (Feature Parity Matrix F-KEY-001, 07_REFERENCE_EVIDENCE_LEDGER.md line 37) | **Parity-or-better.** HUAKAI reuses the unified `quota` engine (scope_kind=`api_key`, metric=`cost_usd`, window_kind=`calendar_day`/`calendar_month`) instead of a separate per-key counter. This eliminates the "two quota sources" confusion bug cited in the reference evidence. The window resets automatically via calendar-window boundaries — no cron worker needed. |
| Group assignment on API key so group-level policies apply transparently | E-OAI-010 (F-GROUP-001) + E-OAI-005 (F-KEY-001) | **Parity.** HUAKAI `api_key_groups` table with `key_group_id` on `api_keys`. Inbound resolver stamps `Identity.KeyGroupID` (new field) after 0077 migration + sqlc regen so downstream routing/quota can dispatch on group without a second DB round-trip. |
| Batch revoke N keys in one operation | E-OAI-005 (F-KEY-001 — "API key lifecycle … rotate") | **Better.** Reference implements single-key revoke only; batch is HUAKAI-added. Atomic per-key semantics with partial-success result set and per-key audit log. Max=50 to bound advisory-lock depth. |
| Secure full-key reveal gated by step-up | E-OAI-005 (F-KEY-001), E-NAI-008 (F-OPS-001) — operator introspection surface for per-key state | **Better.** Reference projects return plaintext on issue only (correct), but provide no re-authentication gate for later forensic access. HUAKAI's reveal design is architecturally honest about bcrypt: plaintext is irrecoverable; the reveal endpoint instead issues a signed nonce proof of key-identity that lets a session holder confirm "this key is mine" without recovering the bearer. The step-up HMAC-challenge is forward-compatible with TOTP/WebAuthn. |

## Effort

**L** (Large).

Rationale:
- 2 new migrations with FK and index work across 3 tables.
- 2 new packages (10 files total).
- sqlc regeneration for `internal/db/auth` after column add.
- Step-up challenge logic (novel, no existing framework to extend).
- 17 discriminating integration tests requiring a live Postgres fixture.
- Quota engine wiring: `SetKeyQuota` must call quota store directly (not via `quota.Service.Reserve` which is the hot-path) — the admin write path needs a thin `PolicyWriter` interface extracted from the existing `PGStore`.

## Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| **sqlc regeneration breaks existing `db/auth` callers** | High | After adding `key_group_id` to `api_keys`, run `make sqlc` and verify `LookupAPIKeysByPrefixRow` gains `KeyGroupID *int64` field. Update `auth.Identity` to carry `KeyGroupID *int64`. All existing callers of `Identity` (gateway, billing, quota) use only `TenantID`/`UserID`/`APIKeyID` today — adding a nullable field is safe. Regression: add `TestResolverProducesKeyGroupID` to `api_key_resolver_integration_test.go`. |
| **Reveal step-up HMAC secret misconfiguration** | High | Handler checks `len(secret) < 32` at startup; if missing, all reveal calls return 503. Document in `config.example.yaml`. Never derive from `SESSION_SECRET` (separate concern). |
| **Advisory lock contention in batch revoke** | Medium | Batch is capped at 50 keys. Each key takes its own `pg_advisory_xact_lock`. Keys are sorted by `api_key_id` before locking to avoid inter-transaction deadlock (consistent lock ordering). Test with two concurrent batch revokes on the same key set. |
| **quota_policy_id FK deferral** | Low | Both new FKs are `DEFERRABLE INITIALLY DEFERRED` so the application can insert the policy and then link it in the same transaction. If deferred FK is not understood by a future developer, they may omit the policy insert. Mitigated by service-layer enforcement: `SetKeyQuota` always creates/updates the policy in the same Tx before updating `api_keys.quota_policy_id`. |
| **Partial batch revoke leaves audit gap** | Low | Each per-key revoke outcome is logged with `slog` (same pattern as `userkey.logRevoke`). A future durable `user_audit_events` table (RR-W5-009) can consume these. Partial success is intentional (per-key atomicity is stronger than all-or-nothing for N≤50 keys). |
| **Calendar-window quota reset timing** | Low | Calendar-window boundary computation is already tested in `internal/quota`. Per-key quota inherits the same engine. Risk: if a key's quota policy `valid_from` is in the future, the engine sees no active policy and allows. Mitigation: `SetKeyQuota` sets `valid_from = now()` unconditionally. |
| **`key_group_id` is nullable — inbound resolver nil-dereference** | Low | `Identity.KeyGroupID` is `*int64`. All downstream consumers must nil-check. Since no downstream consumer exists yet, the risk is forward-looking. Mitigation: zero-value `nil` is documented as "no group constraint" (same as existing `UserGroup = ""` convention). |
